# 安全设计与已知风险

本文件记录平台当前的安全边界、已做出的取舍，以及后续加固方式。改动安全相关代码时请同步更新本文件。

最后更新：2026-09-22

## 已知风险清单

### 1. SSH 主机指纹默认不校验（可配置开启）

- **现状**：`OPS_SSH_STRICT_HOST_KEY` 默认 `false`，连接任何主机都直接接受其公钥（`ssh.InsecureIgnoreHostKey`）。
- **风险**：内网被劫持或 DNS/ARP 投毒时，平台可能把主机登录凭据发给伪造的 SSH 服务端（中间人攻击）。
- **决策**：接受。批量纳管存量主机时预置指纹成本过高，默认关闭以保证可用性。
- **开启方式**：
  ```powershell
  $env:OPS_SSH_STRICT_HOST_KEY="true"
  ```
  开启后的行为（`server/internal/sshx/sshx.go` 的 `hostKeyCallback`）：
  - 主机记录中还没有公钥：首次连接信任并写入 `hosts.host_key`（TOFU，Trust On First Use）
  - 已有公钥：必须完全一致，否则拒绝连接
  - 修改主机的地址或端口：`hosts.host_key` 自动清空，下次连接重新记录
- **残留问题**：TOFU 的首次连接本身仍不受保护。要彻底消除，需要在纳管阶段用带外渠道（配置管理、镜像模板）预先写入指纹。

### 2. 登录凭据的落库加密（哪些已加密、哪些还没）

- **已纳入 AES-GCM 加密**（配了 `OPS_SECRET_KEY` 时，密文带 `enc:v1:` 前缀），共 16 列：
  - 登录到主机 / 集群 / 库：`credentials.secret`、`credentials.passphrase`、`hosts.secret`、
    `kube_clusters.kubeconfig`（**平台权限最大的一份凭据**，通常等同 cluster-admin）、`db_instances.secret`
  - 对外系统凭据：`ldap_servers.bind_password`、`im_apps.app_secret`、`cloud_accounts.access_key_secret`、
    `build_servers.token`、`model_upstreams.api_key`、`notify_channels.secret`、`notify_channels.header_value`、
    `metric_sources.header_value`、`log_sources.header_value`、`trace_sources.header_value`、
    `sys_configs` 里 `key='smtp.password'` 的那一行
- **仍是明文、刻意留到后面的两项**（体检页会标成「尚未纳入」）：
  - `users.totp_secret`：动它就动了登录路径，迁移中途出错会让所有绑过 2FA 的人一起登不进来，
    需要连备用码与解绑兜底一起单独做一轮
  - `alert_sources.token`：这是别人往平台推送告警时用的令牌，界面上必须能看到原文复制给对方，
    加密了也得解回来展示，收益有限
  - `api_tokens` 存的是 SHA-256 哈希而不是令牌本身，本来就不需要加密
- **顺带修掉的一处泄露**：配置列表接口以前会把 `smtp.password` 原文回传给前端，任何能打开配置页的人
  都能从响应里读到它。现在密钥类配置项**不回传取值**，只回一个 `hasValue`，提交空串表示「不修改」。
- **不加密存储是被允许的配置**：`OPS_SECRET_KEY=off`（也接受 none / plain / disabled）即明文落库。界面会在体检卡片上把当前状态写成
  「不加密存储」并说清代价（拿到库文件就等于拿到全部凭据），但平台不拿安全顾虑去堵这个选择 ——
  内网自用、不想额外保管一把密钥的部署，这是个合理取舍。
- **默认值是演示密钥 `demo`**：这样带演示数据的库文件开箱即用（演示库里的凭据就是用它加密的）。
  代价说清楚：`demo` 写在仓库里，人人可见，**等于没加密**；因此 prod 模式带着它启动会被直接拒绝
  （与 `OPS_JWT_SECRET` / `OPS_ADMIN_PASSWORD` 的默认值同一处理）。正式部署换成 32 字节以上随机串时，
  走下面的「更换密钥」，不要直接改环境变量。
- **加密开关不是单向路**：凭证库页「密钥加密体检 → 更换密钥 / 取消加密」（`POST /api/v1/secrets/rekey`）
  可以换成另一把密钥，也可以解回明文。三件事按顺序做：
  1. **先整库备份**，备份失败就中止 —— 这是唯一能把人从「新旧密钥各一半」里救回来的东西
  2. 逐列逐行解开再写回。用当前密钥**解不开的行原样留着并计为失败**，绝不覆盖成空值
     （否则「密钥配错」会变成「凭据被清空」的不可逆事故）
  3. 换掉**进程内存里**的密钥，平台立刻就能继续用，不必先停机
  代价说清楚：这个接口改不了部署配置。返回里会明确要求把 `OPS_SECRET_KEY` 同步改成新值（或删掉），
  不改就重启会拿旧设置去读新数据。启动时若发现「库里有密文但进程没密钥」，日志会直接点出来。
- **没配 `OPS_SECRET_KEY` 就全是明文**，界面照实显示，不做「看起来加密了」的暗示。
- **加密是在读写点显式调用的，不是 GORM 钩子**：钩子在 `Save` 全列写回、`Updates(map)`、
  `Select(...).Updates(struct)` 这几种形态下行为差别很大，一处理解错就会把密文再加密一次或把明文写回去，
  而这种 bug 在库里是不可逆的。显式调用的代价是「可能漏一条写路径」，因此配了**加密体检**：
  它按前缀直接数每列还有多少明文行，漏了就看得见（`GET /api/v1/secrets/audit`）。
  解密统一放在读取漏斗上（`buildTarget` / `kubeClient` / `dbTarget` / `ldapTarget` / `jenkinsRequest` /
  `openUpstream` / `openChannel` / `requireMetricSource` / `requireLogSource` / `requireTraceSource` /
  `configSecret`），这么做安全是因为 `cryptox.Open` 对没有前缀的值原样返回，多解一次不会坏。
- **清单本身也会错**：这一轮扩字段时发现上一版「尚未纳入」的清单漏登记了 4 处
  （通知渠道鉴权头、日志源与链路源请求头、SMTP 口令）。**漏登记比没加密更危险**，因为体检页会显得一切正常；
  所以新接一个外部系统时，密钥列要同步加进 `handler/secret_audit.go` 的 `secretFields`。
- **存量数据要手动迁移一次**：体检页的「加密存量数据」把明文行重写成密文（值不变、幂等、
  已是密文的行跳过）。平台不在启动时自动改写历史数据 —— 那种"悄悄改库"出问题时没人解释得清。
- **风险边界**：密钥能被平台解密使用，所以**同时拿到数据库与 `OPS_SECRET_KEY` 的人仍能拿到全部凭据**。
  加密挡的是「只拿到库文件或备份」那类场景。备份是整库文件快照（`VACUUM INTO`），所以备份里也是密文。
- **必须配套的控制措施**：
  - 严格限制数据库文件的系统权限，仅平台进程用户可读
  - `OPS_SECRET_KEY` 与数据库备份**分开保管**。这个值要换或要退回明文，走凭证库页的
    「更换密钥 / 取消加密」，**不要直接改环境变量** —— 直接改等于让现有密文全部解不开
    （平台会明确报错，不会假装成「口令错误」）
  - 不要把生产主机凭据录入非生产部署的平台实例
- **后续加固**：TOTP 密钥那一轮；再往后是 SSH CA 签发短期证书的「凭据不落地」方案，
  那能同时解决凭据泄露与凭据轮换两个问题。



### 3. Web 终端令牌通过 URL 查询参数传递

- **现状**：浏览器 WebSocket 无法自定义请求头，令牌以 `?access_token=` 传给 `/api/v1/hosts/:id/terminal`。
- **已有防护**：`Origin` 白名单校验（`server/internal/handler/terminal.go` 的 `upgrader`），来源不在 `OPS_ALLOW_ORIGINS` 内的握手直接拒绝，可阻断跨站 WebSocket 劫持。
- **决策**：以 Origin 白名单作为防护即可，不再引入一次性 ticket 机制。
- **残留问题**：令牌会出现在反向代理与网关的 access log 中。若日志被广泛访问，需要在网关侧过滤该查询参数，或改用短 TTL 的一次性 ws ticket。

### 4. 命令审计与拦截是 PTY 层面的启发式手段

- **现状**：Web 终端会话在服务端还原键盘输入的命令行，按 `command_rules` 表的正则判定；命中 `block` 规则时不下发回车、改发 Ctrl-U 清空当前行，命中 `warn` 规则仅记录并提示。实现见 `server/internal/bastion/auditor.go`。
- **能挡什么**：`rm -rf /`、`mkfs`、误敲 `shutdown` 这类直接输入的高危命令，以及事后追责所需的命令流水。
- **挡不住什么**：
  - `vim` 里的 `:!cmd`、`less` 的 `!cmd` 等交互式程序内部执行
  - `echo cm0gLXJmIC8K | base64 -d | sh` 这类编码绕过
  - 写进脚本再执行、通过别名或变量拼接命令
  - Tab 补全的结果只在远端产生，服务端缓冲看不到，补全后的命令可能与审计记录不一致
- **决策**：接受。定位是「记录 + 阻断常见误操作」，不是强制访问控制。
- **如果需要强约束**：应改为受限 shell（rbash + 白名单命令目录）、`sudo` 策略或容器化跳板环境，把管控点放在被管主机上，而不是代理层。

### 5. 会话录像包含终端输出全文

- **现状**：录像以 asciinema v2 格式存放于 `OPS_RECORD_DIR`（默认 `server/recordings`），文件权限 0640，目录 0750。只记录输出流，不记录键盘输入，因此不回显的口令不会进录像。
- **风险**：命令输出里可能出现配置文件内容、连接串、令牌等敏感信息，录像文件等同于敏感数据。
- **控制措施**：录像目录与数据库同等对待（权限收紧、备份视为敏感资产）；`session:replay` 权限只授予需要审计的角色，默认只有管理员角色持有。
- **待办**：录像保留期已可配置（`session.record_keep_days`，0 表示永久保留），但清理只在服务启动时执行一次；长期运行的实例需要重启或后续补一个定时清理任务。

### 5.1 会话审计检索没有权限码，也没有数据范围

- **现状**：`GET /sessions`、`GET /sessions/:id`、`GET /sessions/:id/commands`、`GET /sessions/commands`、`GET /sessions/commands/export` 都只过 `Auth` 中间件，**没有 `RequirePerm`、也不按数据范围过滤**。能看到「会话审计」菜单（ID 206）的人就能读到全平台所有操作人在所有主机上敲过的每一条命令。只有录像回放（`/sessions/:id/replay`）另外要 `session:replay`。
- **风险放大点**：
  - 命令文本里常常夹着口令与令牌（`mysql -uroot -pXXX`、`curl -H "Authorization: Bearer ..."`、`export AWS_SECRET_ACCESS_KEY=...`）。这些是**键盘输入**，录像里没有，但命令明细里有。
  - 跨会话检索 + CSV 导出让这些内容变得可批量带走：一次 `keyword=password` 就能横扫历史，导出上限 10000 条。导出动作本身是 GET，**不进操作审计**（审计只记写操作）。
- **决策**：接受（内网自用，见本文开头的部署定位）。需要收紧时的顺序是：给这几个接口加独立权限码（如 `session:audit` / `session:export`）→ 按数据范围过滤主机 → 对导出单独留痕。
- **不做的事**：不对命令文本做自动脱敏。正则猜口令会既漏又误删，审计数据被悄悄改写比明文更糟；真正的解法是让人别把口令敲在命令行里（用配置文件或凭据代理）。



### 6. 文件管理与定时任务的风险边界

- **文件管理**：走 SFTP，权限完全等同于主机资产里配置的登录账号；平台侧只做三件事——路径必须是绝对路径、拒绝删除根目录、目录删除仅允许空目录（递归删除需到终端显式执行）。上传单文件上限 512MB。
- **下载即数据外带**：`file:read` 权限等于允许把主机上任意可读文件拖到本地，授权时按此理解。所有上传、下载、删除、重命名、新建目录都写入 `file_audits`，包括连接失败的尝试。
- **定时任务**：以任务创建者的身份、按主机配置的账号执行命令。命令内容在**保存时**就按命令规则校验（命中拦截级规则不允许保存），目标含生产主机时保存时必须确认，调度触发时用的就是保存时的那次确认——细节见第 28 节。仍需注意：触发时无人在场，任务改坏了要等到下一次触发才暴露。
- **建议**：`cron:manage` 权限只给少数人；生产环境的定时任务变更应走代码评审或工单，而不是页面随手改。


### 7. 告警接入地址与通知外发

- **接入地址等同凭据**：`/api/v1/webhooks/alerts/:token` 不校验登录态，Token 直接写在 URL 里，且没有签名校验与来源 IP 限制。拿到地址的人可以任意灌入告警（造成噪声或掩盖真实故障）。控制措施：接入源可单独停用、Token 可一键重置（旧地址立即失效）；建议只在内网暴露该路径，或在网关按来源 IP 白名单放行。
- **通知渠道的 URL 由管理员填写，服务端会主动请求它** —— 这构成 SSRF 面：填内网地址（如云元数据服务、内部管理接口）会让平台代为访问。当前只做了 10 秒超时，没有地址白名单。控制措施：`channel:manage` 权限只给管理员；有条件时在出网侧限制平台可访问的目标。
- **渠道鉴权头值加密落库**（配了 `OPS_SECRET_KEY` 时，见第 2 节；接口一律不返回该字段）。
- **群机器人的 Webhook 地址本身就是凭据**：企业微信的 key、钉钉的 access_token 都在 URL 里，拿到地址的人可以往群里发任何消息。这个字段**会随渠道列表返回给前端**（要在界面上显示投递目标），所以能看到「通知渠道」菜单的人就能拿到它——比鉴权头值宽松，配置时请当成群内公开信息看待。钉钉加签密钥与飞书签名密钥按凭据处理（`json:"-"`，加密落库，编辑留空表示不改）。
- **告警正文会进群**：标题、摘要、标签、当前值都会原样发到群里，群成员范围往往比平台账号宽。别在告警摘要里带凭据或内部敏感标识。
- **@所有人会放大噪声**：勾上之后每条命中该渠道的告警都会 @ 全群，夜间尤其扰民；建议只给 critical 级别单独配一个带 @ 的渠道。
- **通知投递不重试**：失败只落一条 `notify_records` 记录，不做退避重试，避免故障时对接收端造成放大。需要可靠投递时应在接收端做幂等 + 平台侧补重试。

### 8. 数据权限的边界

- **只作用于主机与其他资产**：主机列表、连通性探测、Web 终端、文件管理、批量执行、定时任务，以及数据库资产与固定资产（含台账统计）都会按数据范围校验。会话录像、执行历史、告警、通知记录等列表目前**不做数据范围过滤** —— 有这些菜单权限的人能看到全量记录。
- **数据库资产的凭据同样加密落库**，与主机凭据同等对待（见第 2 节）。
- **探测只验端口不验账号**：数据库连通性探测只做 TCP 拨号，不做协议握手与认证，「端口可达」不等于凭据有效。

- **越权访问返回 404 而非 403**：不区分「无权」与「不存在」，避免通过报文差异探测资产是否存在。
- **多角色取并集**：范围越宽越优先，给用户加一个「全部数据」的角色会覆盖其他角色的收紧配置。
- **范围为空即不可见**：没有任何角色、或角色范围算出来是空集时返回空列表，而不是放开全部。
- **归属为空的主机只有「全部数据」范围能看到**：新建主机时如果没选部门，本部门范围的用户看不到它，注意别把资产漏在外面。
- **平台管理员（`all` 范围）不受限制**，仍能看到全部主机与凭据；数据权限是防误操作与范围隔离，不是对管理员的约束。

### 9. 平台配置的影响面

- **`platform.name` 与 `platform.login_notice` 通过未鉴权接口 `/api/v1/public/branding` 暴露**，登录页需要在登录前读取。不要往登录提示里写内部信息（内网地址、联系人手机号、系统版本细节）。
- **`config:manage` 权限可以改运行期行为**：批量执行并发数、上传大小上限、录像保留天数都由配置驱动，改错会直接影响资源占用与审计留存。这个权限应与管理员同级看待。
- **录像保留天数调小会真实删除文件**：下次服务启动时清理，并把 `sessions.record_path` 清空，回放接口随后提示录像已丢失，操作不可逆。

### 10. 菜单、导航与邮件

- **菜单管理不能越权**：内置菜单的结构字段（父级、路径、组件、类型、权限码）由代码维护，接口层拒绝修改，避免把某个菜单的 `authCode` 改成别的权限码来绕过鉴权。自建菜单可自定义，但**新增权限码本身不会赋予任何后端能力** —— 后端接口的 `RequirePerm` 是写死在路由上的。
- **站点导航只接受 http/https**：拒绝 `javascript:`、`data:` 等协议，避免把导航卡片做成 XSS 跳板。导航地址对所有登录用户可见，不要放带 token 的直链。
- **SMTP 密码加密落库**在配置表里（`sys_configs` 里 `key='smtp.password'` 的那一行，见第 2 节）；
  `config:manage` 权限可改，但**配置接口不再回传它的取值**，只回一个「配过没有」，提交空串表示不修改。
- **邮件正文用 Go text/template 渲染**，模板由管理员维护。text/template 不做 HTML 转义，但邮件按 `text/plain` 发送，不存在 HTML 注入面；模板语法错误在保存时就会被拒绝。

### 11. 资源授权的语义

三层权限必须<strong>同时</strong>满足才放行，缺一不可：

1. **菜单/按钮权限**（`RequirePerm`）—— 能不能用这个功能，写死在路由上
2. **数据范围**（部门/本人）—— 默认能看到哪些资源
3. **资源授权** —— 数据范围之外额外放开的具体资源，可限定动作

- **授权只放开、不收窄**：给某人一条只含 `terminal` 的授权，不会把他在数据范围内本来能做的事情限制成只能开终端。想收紧必须调数据范围，不是加授权。
- **动作粒度只作用于"靠授权拿到"的资源**：数据范围内的主机不受动作限制（与授权前行为一致）。
- **连通性探测按 view 级放行**：只要资源可见（范围内或有任意授权）就能探测。探测会真实建立 SSH/TCP 连接，如果这在你的场景里算敏感操作，需要额外收紧。
- **过期即失效**：`expires_at` 过期后该授权不再参与计算，资源立刻从列表消失、动作立刻被拒；**不做到期提醒**，需要长期授权就别填有效期。
- **授权记录本身没有审批流**：`grant:manage` 权限的人可以直接给自己授权任意资源。这个权限等同于管理员，建议只给平台负责人，并依赖操作审计事后追溯。

### 12. 云账号与台账类模块

- **AccessKeySecret 加密落库**（见第 2 节）；接口不返回该字段，列表页对 AccessKeyID 做脱敏（前后各 4 位）。阿里云账号的密钥**会被「云资源同步」解密并用于调用只读 OpenAPI**（出站目标是公网的固定接入点，权限码与风险面见第 36 节）；其它厂商目前只登记不调用。录入时请使用只需 `Describe*` 的最小权限子账号密钥，不要放主账号 AK。
- **平台不会拿这些 AK 去访问云上资源** —— 没有实现资源同步，密钥只是登记在册。这也意味着密钥泄露的后果完全取决于该密钥自身的权限，与平台无关。
- **盘点批次是快照**：创建后新增/删除资产不影响已建批次；这是为了结果可复查，但也意味着批次里的资产可能已在台账中被删除。
- **收货生成固定资产不可回滚**：`createAssets` 一旦生成就只能到固定资产里逐条删除，已入库的采购单也不再允许修改。

### 13. 构建发布（Jenkins 对接）

- **Jenkins 地址由管理员填写，服务端会主动发起请求** —— 与通知渠道 Webhook 同源的 SSRF 面：拥有 `build:manage` 的人可以把地址指向内网任意 HTTP 服务，让平台代替他去探测。只放开给可信人员，或在网络层限制平台的出站范围。
- **API Token 加密落库**（`build_servers.token`，见第 2 节）；接口不返回该字段，编辑时留空表示不修改。请使用 Jenkins 用户的 API Token 而不是登录密码，并只给该用户需要的 job 权限。
- **触发即放行，平台不做二次确认**：只要有 `build:run` 且任务启用，就会立刻提交到 Jenkins；构建脚本本身做什么、部署到哪个环境，平台不感知也不拦截。生产发布的审批需要在 Jenkins 侧或流程上解决。
- **构建状态需手动同步，平台不轮询**：触发只拿到队列地址，构建号与最终结果要点「同步」才会回填。所以记录里的 `triggered` 不代表构建失败，只代表还没同步过。
- **同步只请求本服务器前缀内的路径**：Jenkins 返回的绝对 URL 会被剥成相对路径再拼接（`apiPathOf`），避免被返回值牵着去请求其他主机。
- **参数原样转发**：默认参数与触发参数合并后直接作为表单提交给 Jenkins，平台不做内容校验（只校验必须是字符串值的 JSON 对象）。参数是否被构建脚本当成命令执行，取决于 job 自身的写法。

### 14. 证书巡检

- **探测目标由管理员填写，服务端主动外联** —— 和 Jenkins、Webhook 同一类出站面：拥有 `cert:manage` 的人可以让平台去连内网任意 TCP 端口。平台只做 TLS 握手、不发送业务数据，但「端口是否开放」这个信息本身就能被用来探测内网。
- **探测刻意关闭了证书校验**（`InsecureSkipVerify`）：否则过期、自签名、主机名不匹配的证书连读都读不到，模块就失去意义。校验结果单独算一遍，落在 `trusted` / `verify_error` 上 —— **「读到了」不等于「可信」**，页面与统计都按这个语义区分。
- **不托管私钥、不签发、不续签**：只读对端公开证书。`自动续签（ACME）`不在实现范围内，到期后需要人工换证。
- **巡检结果会写告警**：指纹按「证书 + 类别（expiring/expired/error）」固定，重复巡检只累加次数；状态回到正常时对三类告警都发恢复。关掉某条证书的「产生告警」后只在页面展示状态。
- **告警接入源会被自动创建**：首次产生告警时自动建一个名为「证书巡检」的接入源，它和用户自建的接入源同表，**token 同样可用于外部推送**，删除后下次巡检会重新创建（token 会变）。
- **定时巡检是代码内置任务**：由 `OPS_CERT_CHECK_SPEC` 控制（默认每天 08:00），不出现在「定时任务」列表里，界面上无法停用，只能改配置后重启。

### 15. 双因子口令（TOTP）

- **保护的是平台登录，不是主机登录**：绑定后登录平台需要口令 + 动态验证码；连到主机用的仍是主机自己的凭据（加密落库，见第 2 节）。双因子不会让「凭据存在库里」这件事变安全。
- **TOTP 密钥仍是明文存库**（`users.totp_secret`，是唯一一个还没纳入加密的凭据类字段，理由见第 2 节），接口不返回。拿到数据库就能算出任意账号的验证码 —— 也就是说**双因子挡的是口令泄露与撞库，挡不住数据库泄露**。
- **没有恢复码**：手机丢了只能由持 `totp:reset` 的管理员重置。这意味着该权限等同于「能替任何人摘掉双因子」，只应给平台负责人；重置动作会进操作审计。
- **同一验证码不可重复使用**：登录时记录命中的时间窗（`totp_last_counter`），小于等于已用窗口的验证码一律拒绝，30 秒内抓到的验证码无法被重放。容忍前后各 1 个窗口（±30 秒）的时钟偏差。
- **强制模式是后端拦截，不是前端引导**：`security.totp.mode=required` 时，未绑定账号除 `/api/v1/me*`（本人资料、菜单、绑定接口）外一律 403，绕过前端直接调接口同样过不去。副作用是这些 `/me` 接口在强制模式下仍然可用 —— 这是为了让人能完成绑定，本身不涉及业务数据。
- **强制模式下不能自行解绑**，避免"开了又关"；策略切回 `optional` 后才能解绑，解绑必须同时给出登录口令与当前验证码（防止会话被劫持后直接摘掉双因子）。
- **已签发的令牌不受影响**：给某个账号开双因子或重置绑定，不会让它已经拿到的 JWT 失效，旧令牌在有效期内（默认 12 小时）仍可用。真要立刻踢下线需要停用账号。

### 16. 容器平台（集群接入与资源改动）

- **kubeconfig 加密落库**（`kube_clusters.kubeconfig`，见第 2 节），里面的客户端证书与私钥通常就是 cluster-admin 凭据 —— **这是本平台目前权限最大的一份存储凭据**，同时拿到数据库与 `OPS_SECRET_KEY` 等于拿到集群。接口不返回该字段，编辑时留空表示不修改。生产环境建议给平台单独签一个权限收敛的 ServiceAccount kubeconfig，而不是直接用 admin 那份。
- **平台开放的写操作只有三种**：服务端 apply（`application/apply-patch+yaml`，`fieldManager=opsone`）、改副本数（`/scale` 子资源）、滚动重启（给 Pod 模板打 `kubectl.kubernetes.io/restartedAt` 注解，与 `kubectl rollout restart` 同一做法）。**不提供 delete、exec** —— 要做这些仍然走 kubectl。
- **资源类型分三档，白名单在 `server/internal/k8s/resource.go` 的 `resourceKinds`**：
  - 可写：Deployment / StatefulSet / DaemonSet / CronJob / Job / Service / Ingress / ConfigMap / PersistentVolumeClaim（只有前三种可滚动重启，前两种可改副本数）
  - 只读：Pod / ReplicaSet / Endpoints / Namespace / Node / PersistentVolume / StorageClass —— 由控制器维护或改动代价过大，apply / scale / restart 在**客户端与 handler 两处**都会拒绝，界面上也不给按钮
  - 脱敏只读：Secret。列表只给「类型 + N 个键」，详情把 `data` / `stringData` 的值换成占位符。**这份 YAML 禁止提交**，否则会把真实值覆盖成占位符 —— 这是「功能看起来能用其实是破坏性的」最典型的一种，因此在 handler 里显式挡掉
  - **RBAC（Role / ClusterRole / Binding / ServiceAccount）始终不开放**，连只读都不给：能看到全部权限绑定本身就是侦察面
- **凭据本身的权限不受平台限制** —— 拿到数据库的人可以用这份 kubeconfig 直接对集群做任何事，白名单只约束平台这条路径。
- **滚动重启不是「重启容器」**：它让控制器用新 Pod 逐步替换旧 Pod，副本数为 1 或没有就绪探针时会有短暂不可用，界面确认框里写明了这一点。重启同样过 `kube:write` 与留痕（action=restart），也支持预检。
- **按对象反查事件用的是 `fieldSelector=involvedObject.name`**，不是把整命名空间的事件拉回来自己筛。事件在集群里有保留期（默认 1 小时），**空列表只说明「最近没有事件」**，界面上照实写，不暗示「一切正常」。
- **关联 Pod 只认等值标签选择器**（`spec.selector.matchLabels` 或 Service 的 `spec.selector`）。用 `matchExpressions` 的对象问不出来时返回空并说明原因，**不按名字前缀猜** —— 猜出来的关联关系比没有更危险。

- **写操作要 `kube:write` 权限**，与「维护集群」的 `kube:manage` 分开：能改资源的人不一定要能换 kubeconfig，反之亦然。前端 `v-perm` 只控制显示，拦截在路由上。
- **每次写操作单独留痕**（`kube_change_logs`）：集群、对象、动作、是否只预检、是否强制接管字段、**提交的 YAML 原文**、成功或失败、API Server 的原话、操作人与来源 IP，失败也落库。留痕会原样存下 YAML 里的一切内容，**别把密钥写进 ConfigMap 再 apply**，那等于把密钥抄进了留痕表。保留天数由「数据留存」的 `retention.kube_change_days` 控制（默认 180 天）。
- **预检（`dryRun=All`）是 API Server 侧的完整校验**（含准入控制）但不落盘，用来在真改之前确认 YAML 能过。预检也记留痕，检索时可用「只看真改过的」排除。
- **强制接管字段（`force=true`）有破坏性**：字段被 kubectl 或其他控制器管理时，不强制会返回 409 并带出冲突字段名；勾了强制就按提交的 YAML 覆盖，并把字段管理者改成 `opsone`。界面上默认关闭。
- **提交 YAML 的限制**：单个对象（多段 `---` 直接拒绝）、必须写明 `metadata.namespace`（不替它猜 default）、`apiVersion` 必须与白名单一致、单次上限 256 KB。
- **读回的 YAML 会清掉 status 与集群自己维护的 metadata**（`resourceVersion` / `uid` / `generation` / `managedFields` / `creationTimestamp` / `ownerReferences`，以及 kubectl 的 `last-applied-configuration`），避免把集群的账本回填进 apply。嵌套的 `template.metadata.creationTimestamp: null` 与 kubectl 输出一样保留，不影响提交。
- **容量与配额是只读汇总**：读节点、全量 Pod、ResourceQuota，再加一次可选的 metrics.k8s.io。
  它会拉全集群的 Pod 列表（比普通列表重，给的是 30 秒超时），大集群上别当成刷新很勤的监控页用。
  metrics-server 不在时「实际用量」显示「未知」而不是 0 —— 用 0 充数会让人得出「还很空」的错误结论。
- **Pod 结构化详情是只读的**，字段全部从对象本身算出来：容器状态与上次退出原因、资源与探针、卷及其来源。**卷里的 Secret 只显示名字**，不去读它的内容（要看键名走资源浏览的 Secret 类型，值一律脱敏）。QoS 直接用 `status.qosClass`，平台不自己推算 —— 推算规则很容易实现得和集群不一致，那种「看起来对」的字段最难排查。

- **容器日志是明文原样返回的**：应用往 stdout 写了什么（token、身份证号、SQL 参数），日志页就能看到什么。日志接口是只读接口，和其它只读集群接口一样**不单独绑权限码** —— 能看到「容器平台」菜单的账号就能看日志，收敛靠菜单 RBAC。单次最多取 1MB、最多 5000 行，超出如实标注截断；不落库、不做 follow 流式跟随，也不提供 exec。取「上一次的日志」（`previous=true`）在容器没重启过时集群会直接拒，平台把原话透出来，不回一份空日志假装成功。

- **集群地址由管理员填写，服务端主动外联**：和 Jenkins、Webhook、证书巡检同一类出站面，拥有 `kube:manage` 的人可以让平台去连内网任意 HTTPS 端口。
- **支持 `insecure-skip-tls-verify`**：kubeconfig 里显式声明时才生效，平台不会自己关校验。开了它就等于接受中间人风险。
- **只接受内嵌凭据**：`client-certificate-data` / `client-key-data` / `token`。指向本地文件路径的 kubeconfig 会被拒绝 —— 平台是集中纳管，依赖某台机器上的文件会让「能不能连上」变得不可预期。
- **不缓存集群资源**：每次查询都现场调 API，页面上看到的就是集群当下的状态；代价是集群慢的时候页面也慢（只读 10 秒超时，写操作 30 秒 —— 准入 webhook 也在这条链路上）。
- **健康检查会写告警**：不可达算 critical、有节点 NotReady 算 warning，指纹按集群固定，恢复时自动关闭。定时检查由 `OPS_KUBE_CHECK_SPEC` 控制（默认每 5 分钟），是代码内置任务，界面上无法停用。
- **移除集群只删平台里的记录**：不会对集群本身做任何改动。

#### 16.1 服务转发（port-forward 隧道）

- **隧道端口不做任何认证**，这是这个功能最大的风险点：平台在自己的机器上开一个 TCP 端口，谁能连到这个端口，谁就能访问被转发的集群服务 —— 不需要平台账号、不经过 RBAC、不留会话记录。开隧道要 `kube:forward` 权限，**但用隧道不要任何权限**。
- **控制手段只有部署时的几个环境变量**，都会在页面上写明：`OPS_FORWARD_BIND`（默认 `0.0.0.0`，设成 `127.0.0.1` 就只有平台本机能用）、`OPS_FORWARD_PORT_MIN/MAX`（默认 30000-30099）、`OPS_FORWARD_MAX`（默认 8 条）、`OPS_FORWARD_CONN_MAX`（单条 32 个并发）、`OPS_FORWARD_TTL_MINUTES`（默认 120 分钟，到点自动关）。内网自用的默认值偏向可用，真要收紧就把 bind 改成回环。
- **转发用的是平台那份 kubeconfig 的权限**，与开隧道的人是谁无关：只要能开隧道，就能借平台的凭据访问集群里任意命名空间的任意 Pod 端口（包括数据库、Redis、管理后台）。**没有数据范围、没有命名空间白名单**。
- **端口区间应当在主机防火墙上收紧**：平台自己不区分来源 IP。既然默认监听 0.0.0.0，就应该在机器的安全组 / iptables 上限制谁能到这段端口。
- **走的是 API Server 的 WebSocket 通道**（`/pods/<name>/portforward`，通道号 + 2 字节端口号前缀的朴素协议），而不是 SPDY。每条本地连接单开一条 WebSocket：并发连接会等量放大 API Server 的连接数，因此有单隧道并发上限，超了直接断开而不是排队。
- **转发内容不留痕**：档案里只有连接数与字节数，**不记录也不落库任何流量内容**（那等于在平台上做中间人抓包）。反过来说，「谁通过隧道做了什么」平台答不出来，只能答「哪个账号在什么时候开了一条到哪里的隧道」。
- **隧道随进程消失**：重启后监听全部丢失，启动时把残留的 running 记录标成 stopped 并写明原因，不在界面上假装还活着。
- **Service 目标每条连接重新解析后端 Pod**：好处是 Pod 重建后隧道还能用，代价是**同一条隧道的不同连接可能落到不同 Pod 上**（有多个副本时），排查有状态服务要注意这点。


### 17. 暴露面监测（端口核对）

- **平台会主动向登记的地址发起大量 TCP 连接**：和拨测、证书巡检同一类出站面，但量级更大（单目标一次最多 1024 个端口）。拥有 `exposure:manage` 的人可以让平台去连内网任意主机的任意端口 —— 这既是功能也是风险面，别把这个权限当成只读权限发。
- **只做 connect 探测**：连上就算开、立刻断开，不发任何探针载荷、不识别服务指纹、不尝试认证。这样做既是为了不把平台变成扫描器，也是为了不被对端的安全设备判成攻击 —— 但**对端的 IDS 仍可能把连续连接记成扫描行为**，给公网目标配节奏时请知会安全同事。
- **不扫 UDP、不做全端口扫描、不自动发现资产**：目标与端口范围都靠人登记。它回答的是「和我登记的一不一样」，不是「这台机器到底开了什么」。
- **扫描结果会写进库与告警摘要**：开放端口清单本身就是敏感信息（等于一份小型资产暴露面清单），任何能看到「公网监测」菜单的账号都能读到，告警摘要也会带上端口号，会随通知渠道发出去（webhook / 邮件）。
- **「登记为基线」是把现状直接当成合规态**：首次纳管方便，但如果当时就已经多开了端口，这一步会把问题固化下来。建议先看一眼开放端口再登记。
- **默认节奏是每天一次**（`OPS_EXPOSURE_SPEC`，默认 04:20）。置空即关闭定时，只能手动扫。

### 18. 指标查询（Prometheus 对接）

- **数据源地址由管理员填写、服务端代为请求** —— 与通知渠道、Jenkins 同源的 SSRF 面：拥有 `metric:manage` 的人可以把地址指向内网任意 HTTP 服务。平台只做超时限制（1-120 秒，默认 15），没有地址白名单。
- **鉴权头值加密落库**（`metric_sources.header_value`，见第 2 节），接口不返回，编辑留空表示不修改。用 Prometheus 前面挂的网关令牌，别直接用能改配置的凭据。
- **查询是代理转发，权限只有「能不能查」这一层**：只要登录且能看到「指标查询」菜单就能对任何已接入数据源跑任意 PromQL——**没有按指标名或标签的细粒度授权**。Prometheus 里如果存了敏感业务指标（订单额、用户数），意味着所有能进这个页面的人都能看到。要收敛就在 Prometheus 侧按数据源拆实例，或用网关限制。
- **重查询会打在 Prometheus 上**：平台限制了表达式长度（4000 字符）、范围查询点数（11000，与 Prometheus 上限对齐）与返回曲线数（60 条），但一条 `{__name__=~".+"}` 这种表达式仍然可能让 Prometheus 吃满内存。生产环境建议在 Prometheus 侧配 `--query.max-samples` 与并发限制。
- **不存时序数据、不改写 PromQL**：查询结果只在内存里整形成图表数据，不落库；报错与警告原样来自 Prometheus。

### 19. 日志查询（Loki 对接）

- **日志比指标敏感得多**：日志行里常有手机号、身份证、token、SQL 参数。平台只有「能不能进这个页面」这一层控制（菜单 RBAC），**没有按标签或日志内容的细粒度授权** —— 能进页面的人就能查该数据源里的任何日志。要收敛就在 Loki 侧按租户拆分，或在网关上限制。
- **鉴权头值加密落库、租户明文存库**（`log_sources.header_value` / `tenant`，见第 2 节），头值不出接口，编辑留空表示不修改。
- **地址由管理员填写、服务端代为请求**，与指标数据源同源的 SSRF 面（`log:manage` 权限）。
- **查询结果不落库、不写审计正文**：只有「谁调了 /monitor/logs/query」这条通用操作审计记录（GET 请求甚至不记），日志内容本身不会被平台留存。下载是浏览器本地生成文件，不经过服务端。
- **重查询会打在 Loki 上**：平台限制了表达式长度（4000）、单次条数（5000）与超时（默认 30 秒），但一条 `{job=~".+"}` 跨 7 天仍可能让 Loki 扫上百 GB。生产环境请在 Loki 侧配好 `max_query_length`、`max_entries_limit_per_query` 与 `split_queries_by_interval`。
- **不做实时 tail**：省掉一条长连接，也避免有人开着 tail 页面就把查询配额吃满。

### 20. 链路追踪（Jaeger 对接）

- **span 标签里什么都有**：SQL 语句、URL 里的参数、用户 ID、内部 IP 与端口。平台把选中 span 的**全部标签**原样展示，只有菜单 RBAC 这一层控制，**没有按服务或标签的细粒度授权**。要收敛就在 Jaeger 侧拆实例或在网关限制。
- **鉴权头值加密落库**（`trace_sources.header_value`，见第 2 节），不出接口，编辑留空表示不修改。
- **地址由管理员填写、服务端代为请求**（`trace:manage`），与指标/日志同源的 SSRF 面。
- **只读，不接收上报**：平台没有 OTLP/Jaeger 接收端口，应用把 span 发给谁与平台无关；平台也不落库链路数据。
- **重查询会打在 Jaeger 上**：列表条数上限 200、单条 trace 最多画 800 个 span、超时 1-120 秒（默认 20）。但「7 天 + 不加操作名」这种查询在大集群上依然很贵，必要时在 Jaeger / 存储侧限流。
- **TraceID 可直接查**：任何能进这个页面的人，只要拿到一个 TraceID（比如从日志里抄的）就能看到那条链路的全部 span 与标签，包括别的业务线的。

### 21. 模型资源池（AI 网关）

- **上游密钥加密落库**（`model_upstreams.api_key`，见第 2 节），不出接口、编辑留空表示不修改。这些密钥通常是**直接对应真金白银的额度**，同时拿到数据库与 `OPS_SECRET_KEY` 就能拿去刷量。
- **平台成了公用额度入口**：拿到 `model:call` 权限的人就能借平台登记的密钥调模型，**平台自己不做配额与限流** —— 没有「每人每天多少 token」这种闸门。要控成本目前只能靠「调用流水 + 事后追人」，或者在上游侧按 key 设额度。
- **检查按钮会真花钱**：探活除了拉 `/models` 还会打一次 `max_tokens=1` 的调用（因为 `/models` 在部分实现上不校验密钥，只探列表会给出「可用」的假结论）。金额极小，但它是真实调用，也会进流水。别把「检查」接到定时任务上反复刷。
- **提示词与回复正文不落库**：流水里只有 token 数、成本、耗时、谁调的。这是有意的 —— 那些内容属于业务数据（可能含客户信息），抄进运维平台的库等于扩大泄露面。反过来说，「谁问了什么」平台答不出来，要审内容得在调用方自己的日志里做。
- **成本是估值**：按每个上游登记的单价算，平台不查供应商账单、不处理阶梯价/缓存命中折扣/免费额度。用它做趋势和分摊可以，用它对账不行。
- **地址由管理员填写、服务端代为请求**（`model:manage`），与指标/日志/Jaeger 同源的 SSRF 面：可以把 baseUrl 指向内网任意 HTTP 服务。平台只限制协议前缀与超时（5-600 秒）。
- **入口侧只有粗保护**：单次最多 64 条消息、提示词总长 128 KB、`max_tokens ≤ 32768`，一次请求最多试 3 个上游。没有并发上限 —— 高并发调用会等量放大到上游与平台自身的连接数。
- **不做流式**：既是产品取舍（流式拿不到完整 usage），也顺带少了一条长连接的暴露面。需要流式的调用方应当直连上游，那部分用量平台看不到。
- **用量页与流水导出没有单独权限码**：能看到「智能与成本」菜单的账号就能看全平台的用量、成本与「谁调了多少」，并能按条件导出 CSV。导出里只有元数据（时间、模型、上游、调用人、token、成本、错误），没有提示词与回复正文，但**「某人某天调了 300 次」本身也是信息**。收敛靠菜单 RBAC。
- **流水删了账就算不出来**：用量与成本完全依赖 `model_calls`，它的保留天数在「数据留存」里（`retention.model_call_days`，默认 365 天）。调小并执行清理是不可逆的 —— 那段时间的用量、成本、谁调的全部消失。

### 22. Agent（只读分析器）

- **Agent 不执行任何东西**，这是这个模块最重要的边界：它只从平台已有的表里读数据（告警、主机指标、执行结果、会话命令），拼成提示词发给模型，把回答存下来。**没有工具调用、没有命令下发、不会改任何对象**。结论是模型说的，不是平台的判断，照着做之前请自行核对。
- **平台数据会被送到模型那边**：这是功能本身的代价，但值得说清楚都送了什么 —— 告警的标题/摘要/标签（可能含主机名、业务名）、主机的性能数字、**执行作业的 stdout/stderr 原文**、**会话里敲过的命令原文**。后两类最敏感：命令行里夹的口令、脚本输出里的连接串都会一起发出去。上游是公网供应商时，这等于把这些内容交给了第三方。要收紧就给这类 Agent 配本地模型（Ollama / llama.cpp 这种）。
- **运行记录存正文**：`agent_runs` 里有完整的结论文本与运行时填的补充说明（不存渲染后的完整提示词）。能进「Agent 运行」菜单的人就能看到所有人的运行结论，**没有按 Agent 或按数据来源的细粒度授权**。保留天数见 `retention.agent_run_days`（默认 365 天）。
- **提示词模板是 `text/template`**，由有 `agent:manage` 权限的人编写。保存时只做语法校验，**没有函数白名单与渲染超时**；模板只能拿到 `context` 与 `input` 两个字符串变量，拿不到平台对象，所以拿不到别的数据 —— 但一个刻意写坏的模板仍然可能生成超长提示词（渲染后有 32000 字符的硬上限兜底）。
- **额度消耗与权限**：运行要 `agent:run`，每次运行都是一次真实的模型调用，并计入「用量与成本」（来源 `agent`）。**没有每人/每 Agent 的配额**，与网关一样只能事后追。目前也**不支持定时自动运行** —— 不想出现无人看管地反复烧额度。
- **上下文条数有上限**（每个 Agent 自己配，1-200，另有 24000 字符的硬上限）。撞上限时运行记录标「已截断」：结论是基于不完整数据得出的，这一点必须能在事后看出来。

### 23. IM 组织同步

- **没有在真实企业租户上验过**。手上没有企业自建应用凭据，接口路径与字段名来自各家公开文档，验证用的是按文档形状写的假上游（验的是平台侧的同步语义）。真实环境里字段名或错误语义若有差异，表现会是「检查失败」并把上游原话带出来，按厂商文档对照即可；`ImApp.BaseURL` 可覆盖地址，便于先对着私有网关或抓包代理调通。
- **应用密钥加密落库**（`im_apps.app_secret`，见第 2 节），不出接口、编辑留空表示不修改。这把密钥能读整个企业的通讯录（姓名、手机号、邮箱、部门结构），泄露的影响面比一个群机器人 webhook 大得多。
- **同步会造出能登录平台的账号**：新建账号带随机口令（本人登不进来），但**角色是配置里的默认角色**。如果默认角色给得太大，一次同步就等于批量发权限。建议默认角色用只读，或干脆留空（留空的账号登录后看不到任何菜单）。
- **同步只补不毁，但它确实会改数据权限**：用户的 `dept_id` 决定他能看哪些主机（数据范围 `dept` / `dept_below`）。IM 侧调整组织架构 → 同步 → 有人的可见主机范围跟着变。执行前先看预演。
- **离职只停用不删除**（可关）。选择停用而不是删除，是因为删了用户，历史审计里按 username 记的那些操作就对不上人了。内置 admin（id=1）永不被停用，避免一次误同步把自己关在门外。
- **同步不碰已有用户的角色与口令**，这是刻意的：角色绑定在代码里是「全量覆盖」语义，如果同步也去写，管理员手工调过的权限会被下一次同步静默抹平。
- **手机号与邮箱落在绑定表里**（`im_accounts.im_mobile` / `im_email`），平台用户模型本身没有手机号字段。能进「IM 集成」菜单的人就能看到全公司的这些联系方式，**没有更细的授权**。

### 24. IM 扫码登录

- **四个接口不带鉴权**（`/public/im-logins`、`/auth/im/authorize`、`/auth/im/callback`、`/auth/im/exchange`）—— 登录之前不可能有令牌。因此 `/public/im-logins` 只回 id / 名称 / 厂商三个字段，**不回 corpid、agentid、密钥与回调地址**；`authorize` 只会给已开启扫码登录的应用发地址。
- **令牌不进 URL**。回调只把一个一次性 ticket 拼在跳转地址上，前端再用 ticket 换 JWT。原因：URL 会进浏览器历史、Referer 与各级反代的 access log，令牌一旦落在那里就等于长期泄露。ticket 2 分钟有效、取出即废；发起时的 `state` 5 分钟有效、同样一次性（回调重放会被拒）。
- **ticket / state 存进程内存**。后果有两条，都得接受或另做安排：**重启会让所有进行中的扫码失效**（用户重新点一次即可）；**多实例部署必须换成共享存储**（Redis 或数据库），否则授权发起与回调落到不同实例就一定失败。
- **必须已经绑定才放进来，绝不自动建号**。IM 里有、平台没绑过的人一律拒绝。自动建号等于把「谁能进平台」的决定权交给企业通讯录 —— 新入职的人、外部联系人、被加进通讯录的合作方都会凭空获得一个账号。同理，**停用的账号扫码一样拒**，换 ticket 时会再查一遍状态（发起与换取之间可能已被停用）。
- **绑定关系是唯一的身份凭据**。`im_accounts` 里 `provider + im_user_id` 对应到哪个平台用户，就以谁的身份登录。也就是说，**能改这张表的人（`im:manage`）等于能把任意 IM 身份指到任意平台账号上**，包括 admin。这个权限应当只给平台管理员。
- **上游返回什么身份就信什么**。平台不校验扫码人是否属于本企业（企微的外部联系人 code 换不出 `userid`，这条会被明确拒绝），但也**没有二次因子**：IM 账号被盗 = 平台账号被盗。**扫码登录绕过平台自己的 TOTP**（双因子是口令登录链路上的一步），对 admin 这类账号建议不要依赖扫码登录。
- **回调地址必须自己登记正确**。保存时只校验它指向平台的 `/api/v1/auth/im/callback`，**不校验域名是否可达、是否与 IM 后台登记的一致** —— 写错的结果是厂商直接拒绝跳转。登录成功后的落地地址（`LoginRedirect`）是前端首页，**不接受来自请求参数的跳转目标**，避免变成开放重定向。
- **失败原因会带上游原话跳回登录页**（`?imError=...`）。这是为了让「没给通讯录权限」「invalid code」这类配置问题能当场看出来，代价是错误文案暴露了一点上游细节。这些串只进前端提示，不写库。
- **没有在真实企业租户上验过**，与第 23 节同因。扫码登录链路用按文档形状写的假上游验了 23 项断言（302 带 ticket、URL 无令牌、ticket/state 各自只能用一次、未绑定/停用/外部联系人/无效 code 全被拒、开关关闭后不再发地址），并在浏览器里跑通了真实的自动登录。











### 25. 生产模式与部署期的安全兜底

- **`OPS_ENV=prod` 会把「不安全的默认值」从警告升级成拒绝启动**：默认 JWT 密钥（仓库里的公开常量）、默认 admin 口令、空或含 localhost/`*` 的 CORS 白名单、显式打开的 `OPS_DEBUG`、短于 32 字节的密钥。这几项以前都只打一行 warn 然后照常跑 —— 而「不改也能跑起来」正是上线事故最常见的来源。`prod` 下 `OPS_DEBUG` 默认关闭。
- **配置本身写错不再静默回退**：`OPS_TOKEN_TTL_HOUR=twelve` 这类非法值以前会悄悄用默认值，现在直接报错退出。配错了却按默认跑起来，比不启动更难排查。
- **来源 IP 不再无条件信任 `X-Forwarded-For`**：gin 的默认行为是信任所有代理，任何人都能伪造审计与会话记录里的来源 IP。现在默认谁都不信（取 TCP 对端地址），要用反代就把它的地址填进 `OPS_TRUSTED_PROXIES`。三点已实测的行为：
  - 信任列表为空时，伪造的 `X-Forwarded-For` 被忽略，审计记 TCP 对端地址；
  - 填了反代地址后，审计取 XFF 里的客户端地址（这正是想要的效果）；
  - **但反代与平台同机时只能填 `127.0.0.1`，这等于信任本机所有进程都能伪造来源 IP**。收敛办法是让平台只监听本机（`OPS_ADDR=127.0.0.1:8080`），把影响面限制在本机内；另外 nginx 侧可以用 `proxy_set_header X-Forwarded-For $remote_addr` 覆盖客户端自带的 XFF（样例里写了）。
  不配这个变量、又确实在反代后面时，审计记的是反代 IP 而不是真实客户端。
- **备份不是可选项**：数据留存清理是真删且不可逆（第 12 节），而全部数据只在一个 SQLite 文件 + 一个录像目录里。现在自带 `ops backup` / `ops restore`，默认每天 03:00 自动备份、早于 03:30 的清理。**备份文件与数据库同等敏感**（里面有明文主机凭据、会话录像），落盘目录与同步目标要按凭据库的级别管权限。
- **备份命令会拒绝备份一个不像 OpsOne 的库**：SQLite 打不开文件时会现场建一个空库，`sudo`/`cron` 清掉环境变量后 DSN 会退回相对路径的 `ops.db` —— 那样会「备份成功」出一个空文件，真出事才发现没东西可恢复。所以备份前会查一次 `users` 表，不对就报错退出。
- **前端由后端托管时的边界**：`OPS_WEB_DIR` 非空时后端直接发 `web/dist` 并做 SPA 回落，但 `/api/` 前缀不回落（拼错的接口仍返回 JSON 404，不会把 HTML 喂给调用方），非 GET/HEAD 的未知路径也不回落。
- **停机不再硬切**：SIGTERM 会先停调度、通知并断开 Web 终端、关闭转发隧道并落库，再等在跑的请求收尾。**仍需注意**：`OPS_SHUTDOWN_TIMEOUT_SEC` 到点会强制结束，正在跑的批量执行可能被截断（作业记录会留在库里，但结果不全）；systemd 的 `TimeoutStopSec` 必须大于这个值，否则收尾没做完就被 SIGKILL。

### 26. 告警静默与维护窗口

- **静默只拦外发通知，不拦入库**。窗口期内的告警照常写库、页面可见，并记下 `silenced_by` / `silence_id`。这条设计是刻意的：维护窗口不该让平台「变瞎」，只该让它「别叫人」。
- **能配静默的人能让告警不外发**。`silence:manage` 权限相当于「临时关掉一部分告警通知」，勾上「匹配全部告警」就是全局静音。防呆做了三层：不填条件必须显式勾选「匹配全部告警」；单条窗口最长 30 天（长期屏蔽应该去改告警规则，而不是永久静默）；列表页固定显示当前有几条生效中。**但没有审批**——这跟资源授权一样，属于「管理员自己对自己负责」（见第 8 节）。
- **窗口到点自动失效**，不依赖任何定时任务：判定发生在告警产生与值班升级扫描的那一刻。好处是重启不影响、不会出现「忘了解除静默」；代价是**已经被拦下的告警不会在窗口结束后补发通知**（它们只是没外发，人要自己去告警列表看）。
- **值班升级也会跳过窗口内的告警**，并且每轮按当下时间重新判定。所以维护窗口里不会半夜叫人，窗口一过下一轮扫描就会照常升级。
- **已拦过告警的窗口不允许删除**，只能提前结束或停用 —— 否则那些告警的 `silenced_by` 会变成查不到出处的孤儿，事后复盘时说不清「为什么当时没人收到通知」。
- **与聚合抑制是两个字段**（`silenced_by` vs `suppressed_by`）。复用同一个字段会让被静默的告警被聚合逻辑当成「已通知过的首条」，从而放过后面本该抑制的告警 —— 这是实现时踩到并刻意避开的坑。

### 27. 数据库只读查询

- **`db:query` 等于「能看业务库里的数据」**。这是全平台数据敞口最大的一个权限：主机凭据、告警、会话录像都是运维数据，业务库里是订单、手机号、工资表。判权只看这一个权限码，**不受数据范围（部门）与资源授权约束**——能进这个菜单的人，能查「数据库资产」里所有 MySQL/PG 实例。给权限时请按「能看生产数据」的标准审，不要按「运维工具」的标准审。
- **只读不等于安全**。平台做了三件事：语句白名单（只放 select/with/show/explain/describe/analyze，剥注释后仍有 `;` 直接拒，`WITH ... INSERT` 这类 CTE 写入单独拦）、会话级只读（PG DSN 带 `default_transaction_read_only=on`，MySQL 连上先 `SET SESSION TRANSACTION READ ONLY`）、危险函数与文件操作的模式匹配（`INTO OUTFILE`/`DUMPFILE`、`COPY ... FROM`、`COPY ... TO PROGRAM`、`pg_read_file`/`pg_ls_dir`、`dblink`、`sleep`/`benchmark`/`pg_sleep`、`FOR UPDATE`/`LOCK IN SHARE MODE`）。**但正则不是解析器**：足够刁钻的写法未必被穷尽。真正的兜底是第三层——**在库上给一个只读账号**，别把 root/postgres 填进资产里。已实测的是「拦下来的 7 条写语句执行后，用库自带客户端确认行数没变」，以及直接问库自己 `show transaction_read_only` / `@@transaction_read_only` 确认会话确实是只读的。
- **凭据加密落库**（见第 2 节）。这个模块的实际效果是让那个一直白存着的 `db_instances.secret` 第一次被真正用起来——也就是说，**同时拿到 SQLite 文件与 `OPS_SECRET_KEY` 的人不只拿到主机 root，还拿到业务库账号**。别为了用这个功能把高权账号填进来。
- **查询流水里存的是语句原文**。这是审计的必要条件（要能回答「谁查了工资表」），代价是 `WHERE phone = '138...'` 这种条件里的敏感值会落进 `db_query_logs` 表，而这张表**能进这个菜单就能看全部**。留存天数由 `retention.db_query_days`（默认 180 天）控制，到点真删不可逆。
- **资源消耗是自限的但不是免疫的**：单条语句 30 秒超时（PG 靠 `statement_timeout`，MySQL 靠 `max_execution_time`——**MariaDB 没有这个变量，设置失败只是 warn，超时只能靠 Go 侧 context 断开**，此时库里的查询可能还在跑）、结果 500 行截断、导出 10000 行、语句长度 20000 字符。一条没有 `WHERE` 的大表全扫仍然会给生产库带去 IO 压力——**这个功能没有做限流与并发上限**。
- **截断是真的判断出来的，不是猜的**：取 `LIMIT n+1` 行、只有看到第 n+1 行才标「还有更多」。早先的实现直接 `LIMIT 500`，于是刚好 500 行时永远显示「未截断」——这类「看起来对」的假信号在审计场景里比报错更危险。
- **报错原文直接回前端**，包括库的原始错误（表不存在、权限不足、语法错误）。这是为了让「为什么查不出来」当场可判，代价是会暴露一点库内结构信息（表名、schema 名）。
- **没有审批、没有二次确认**。与资源授权、静默一样，属于「管理员自己对自己负责」（见第 8 节）。如果需要「查生产库要走单」，当前只能靠不给这个权限来实现。

### 28. 下发闸门（命令规则与生产确认）

- **闸门在服务端，且只有一处**。批量执行、脚本下发、定时任务（立即执行与调度触发）四条路径最终都走 `RunOnHosts`，闸门就挂在那里（`handler/exec_guard.go`）。这样不会出现「新加一个下发入口忘了挂校验」。闸门做两件事：命令规则逐行匹配（命中拦截级规则一律不下发）、目标含生产主机时必须显式确认。
- **这是在补两个真实的口子**，不是新功能包装：此前命令规则只作用于 Web 终端与脚本库，**批量执行与定时任务是两条完全不校验命令内容的直达 SSH 通道**；而「生产环境二次确认」只存在于三个 `.vue` 的弹窗里，后端连 `confirm` 字段都没有——直接调接口就绕过了，而且前端只加载前 200 台主机，超出的生产主机根本不参与判断。
- **正则不是解析器**，能力边界与终端拦截一致：挡得住写在明面上的高危命令，挡不住 `base64 -d | sh`、变量拼接、先下载脚本再执行。它降低误操作概率，**不是强制访问控制**。
- **被拦下来的下发不会产生执行记录**，所以单独有一张 `exec_guard_logs`：记命令原文、命中的规则、目标台数与其中的生产台数、操作人、来源 IP、来源路径。放行且没命中规则的下发不记这里（`exec_jobs` 本身就是记录），命中提醒级规则的放行会记一条。留存键 `retention.exec_guard_days`（默认 365 天），**建议比执行记录留得更久**——「谁试过下发 rm -rf」只有这张表能回答。
- **调度触发用的是保存时的那次确认**（`cron_jobs.prod_confirmed`）。触发时无人在场，要么信任保存时的确认，要么让任务永远跑不了，没有第三条路。代价是：**保存时确认过，之后每次凌晨触发都不再问**；改目标或改命令都会重新走一遍校验与确认。把这一位直接改成 0（比如手工改库）会让下一次触发被闸门拦下并记流水——这条行为是实测过的。
- **升级时存量定时任务按「已确认」处理**（`migration.cron_prod_confirmed_backfilled`，只执行一次）。否则闸门上线后，一批存量任务会在凌晨静默被拦——那比不做这个功能更糟。
- **补了定时任务的两处越权**：编辑任务此前不校验数据范围（可以先建一个合规任务、再把目标改到范围外的主机），立即执行也不复查当前操作人的可见性。现在两处都按 `exec` 动作复查，和创建任务一致。
- **仍然没有的东西**：没有审批流、没有执行窗口（不能规定「只许在变更窗口内下发」）、没有下发限流与并发上限、没有「双人复核」。生产变更的组织流程仍要靠人，平台只提供留痕与阻断。

### 29. LDAP / AD 账号接入

- **绑定即托管，且不自动建号**。能不能进平台由「平台里有没有这个账号、有没有绑定到目录条目」决定，不由目录决定。目录里新增一个人不会凭空得到平台账号——与 IM 扫码登录同一原则（第 24 节）。
- **一旦绑定，本地口令立即失效**。这是这个模块最重要的一条：如果保留「域口令不行就试本地口令」的回落，域账号停用或员工离职后，平台里那份旧口令哈希就是一个真实的后门。所以判定顺序是「先看有没有绑定」，有绑定就只认目录；目录不可达、服务器被停用、关掉域登录、证书校验失败——**任何一种失败都不回落本地口令**，宁可登不上也不留后门。解绑才会回落（解绑提示里写明了这点）。
- **空口令必须显式拒绝**。LDAP 的「unauthenticated bind」在很多目录上对空口令返回成功。如果把空口令直接交给 bind，填个存在的用户名、口令留空就能登录。代码在建连之前就拒空口令，并有单测钉住这条。
- **登录名要转义后才能拼进过滤器**，否则 `*)(uid=admin` 这类输入能改写过滤器语义（LDAP 注入）。相应地，「列一批人」用的通配符是平台自己加的、单独走另一个函数——实现时踩过一次：搜索用了转义后的 `*`，于是过滤器变成「uid 等于字面量星号」，真实目录里一条都搜不出来。
- **服务账号只用于搜索，不参与口令校验**。校验一律用目标条目的 DN 直接 bind。服务账号口令加密落库（见第 2 节），接口只回「配过没有」；解不开时平台直接报「口令不可用」而不是拿空口令去匿名 bind —— 匿名 bind 往往「连上了但搜不到人」，比直接失败更难查。
- **账号停用的表现形式不解析**。AD 用 `userAccountControl`、OpenLDAP 常用 ppolicy，各家不同。平台不去读这些属性，而是**依赖 bind 本身被目录拒绝**——效果是对的，但「为什么失败」只能显示目录返回的原话。平台侧的停用（`users.status`）仍然独立生效：目录认了、平台停用了，照样拒。
- **双因子不被目录替代**。目录只解决「口令由谁管」，TOTP 仍然照原逻辑要第二因子。
- **不做组到角色的映射**。否则「谁是平台管理员」就由目录管理员说了算。角色仍在平台里配。
- **自签证书要显式选择跳过校验**。默认不跳过；打开这个开关等于接受中间人风险（内网自用，见文档开头的定位）。已实测：同一台 StartTLS 目录，关掉跳过校验就连不上（报证书校验失败），此时登录也一并失败且不回落。
- **登录页只回一个布尔**（`/public/ldap-login`），不暴露目录地址、Base DN 或服务账号。
- **没有的东西**：OIDC / SAML、SSO 单点登出、按目录同步组织结构（那条路是 IM 组织同步）、口令策略校验（长度/复杂度由目录自己管）、失败次数锁定（平台不做计数，目录侧的锁定策略会体现为 bind 失败）。

### 30. API 令牌（服务账号）

- **明文只出现一次**，库里只存 SHA-256（`api_tokens.token_hash`）。平台自己也查不回来，丢了只能轮换。已实测：把整张表 dump 出来搜不到明文，且 `token_hash == sha256(明文)`。
- **令牌权限 = 授予的权限码 ∩ 归属人当下的权限**。这条是刻意的：否则「发令牌」会变成一条绕过 RBAC 的提权通道（给自己发一个带 `exec:run` 的令牌）。归属人被降权或停用，令牌同一刻失效——已实测停用归属人后令牌立即 403。副作用要知道：**令牌的数据范围就是归属人的数据范围**，换人负责就要改归属或重发。
- **默认只读**。只读令牌只放 GET/HEAD，写操作在中间件层就被拒（不进 handler）。要写必须同时做两件事：显式关掉只读、授予对应权限码；可写令牌不给任何权限码时直接拒绝创建（那种令牌什么也做不了，留着只会让人误以为有权限）。
- **不能用于 WebSocket 链路**。令牌只认 `Authorization` 请求头，不认 `access_token` 查询参数（那是 Web 终端专用的通道），并且显式拒绝 `Upgrade: websocket`。理由：终端与端口转发必须能对应到一个人，否则会话审计里会出现没有主体的会话。
- **不受强制双因子约束**。`security.totp.mode=required` 只约束人工登录；令牌不是人，没有「输入验证码」这一步。代价必须说清楚：**有 `token:manage` 的人可以给自己发个令牌来绕开这条策略**，所以这个权限要按管理员级别给。令牌侧的约束是另外几条：默认只读、权限取交集、可撤销、来源 IP 白名单。
- **来源 IP 白名单支持 CIDR，写错的条目一律按「不匹配」处理**，并且在保存时就拒绝非法条目——「以为限制住了其实没限制」比不限制更危险。注意白名单比的是 `ClientIP()`，所以在反代后面必须正确配置 `OPS_TRUSTED_PROXIES`（第 25 节），否则比的是反代地址。
- **审计能回答「是谁的哪个令牌干的」**：`audit_logs` 新增 `token_id` / `token_name`，同时保留归属人的 `user_id` / `username`。被 403 拒掉的令牌调用同样留痕；**GET 仍然不入审计**（与人工一致，避免噪声）——也就是说「令牌读了什么」查不到，只能看 `api_tokens.last_used_at` 与调用计数。
- **用过的令牌只能撤销不能删除**，否则审计里的 `token_id` 会变成查不到出处的孤儿。撤销与轮换都是立即生效的（每次请求都查库，不做缓存）。
- **没有的东西**：没有按接口/路径的细粒度 ACL（粒度就是现有权限码，不另造一套只给令牌用的权限模型）、没有调用限流与配额、没有 OAuth2 客户端凭据流、没有令牌级别的数据范围（跟着归属人）。





## 现有安全机制











- **认证**：JWT（HS256），密钥来自 `OPS_JWT_SECRET`，默认 12 小时过期（`OPS_TOKEN_TTL_HOUR`）
- **口令存储**：平台用户口令用 bcrypt 哈希，登录失败不区分「用户不存在」与「密码错误」，避免账号枚举
- **授权**：菜单/按钮两级 RBAC，写操作接口逐个绑定权限码（`server/cmd/server/main.go` 的路由注册），前端 `v-perm` 仅做展示控制，真正的拦截在后端
- **审计**：所有写操作（POST/PUT/DELETE）记录操作人、接口、状态码、来源 IP、耗时；读请求不入库。Web 终端额外记录会话流水（操作人、目标主机、跳板链、来源 IP、时长）、逐条命令与录像
- **跳板机**：主机可关联跳板机（`hosts.proxy_host_id`），连接时先登录跳板机再在其内部拨号到目标，终端与批量执行共用同一条链路；链路层数上限 3 层，配置成环会被拒绝

- **CORS**：来源白名单 `OPS_ALLOW_ORIGINS`，默认仅 `http://localhost:5173`
- **越权保护**：内置管理员账号与管理员角色不可删除，禁止删除当前登录账号
- **生产环境二次确认**：由**后端**强制——目标含 `env=prod` 的主机时，请求必须带显式确认，否则拒绝下发（见第 28 节）；前端弹窗只是把这件事做得好用一点
- **事件复盘**：`review:manage` 权限码控制写操作（保存、归档、改进项维护）；读操作只需登录；归档后字段锁定、改进项不可删只可改状态留痕；证据汇聚只从本库已有数据取（不外发请求）；复盘草稿与改进项随事件级联删除
- **处置剧本**：`runbook:manage` 控制写操作（维护剧本、记录使用、重新预检），读与匹配只需登录；步骤里的命令保存时过命令规则静态预检，命中拦截级规则的剧本不允许启用；命令规则变更后可重新预检，失效剧本自动停用且不会自动恢复启用；剧本只把命令预填到批量执行页，真正下发仍走 `RunOnHosts` 的下发闸门（规则复检 + 生产主机确认 + 拦截留痕）；用过的剧本不可删除，只能停用，保证历史处置记录不指向空
- **主机服务**：`service:manage` 控制纳管与期望态维护，`service:control` 控制启停，读与发现只需登录；启停命令一律走 `RunOnHosts`，因此继承命令规则拦截、生产主机二次确认与 `ExecGuardLog` 拦截留痕；关键服务的停止/重启/取消自启需要抄 unit 名二次确认，被拒的尝试也写入 `HostServiceAction`；采集所需的 root 权限通过 `service.sudo` 配置 + 主机账号的免密 sudo 白名单（建议只放 systemctl 与 ss）获得，平台不要求也不使用 root 登录
- **配置文件**：`configfile:manage` 控制登记与编辑，`configfile:apply` 控制下发与回滚，读与 diff 只需登录；替换动作走 `RunOnHosts`，继承命令规则拦截、生产主机二次确认与 `ExecGuardLog` 留痕；路径拼进 shell 前统一 `shellQuote` 单引号转义（有单测覆盖注入用例）；下发前强制存回滚点、机器上留 .bak 备份、写完回读校验 sha256，读不到真机现状则拒绝下发；关键配置的下发/回滚需抄路径二次确认，被拒尝试写入 `ConfigApply`；配置正文整份入库，内含口令的配置文件请自行评估（平台不对正文做加密）
- **事件 SLA**：`sla:manage` 控制谁能改 SLA 目标（读与倒计时只需登录）。这组配置**不含任何密钥**（8 个整数：三级响应目标、三级恢复目标、临期提前量、重复提醒间隔），所以不进密钥加密体检；它的影响面是消息量——把目标改小会直接放大站内消息（`OPS_SLA_SPEC` 每 2 分钟扫一遍，每条 SLA 在「重复提醒间隔」内只发一次，这个间隔是唯一的节流），改之前看一眼当前未完结事件数。SLA 扫描**只读本地库**：不连主机、不执行任何命令，因此不经过命令规则与下发闸门（也因此不需要）——它能做的最坏的事是发多了消息，而不是动机器
- **安全事件**：`secevent:manage` 管研判与处置（改状态、写结论、维护误报白名单与撤销），`secevent:respond` 管生成封禁规则草稿；读列表与详情只需登录。采集器**只读本地库**：不连主机、不执行任何命令，因此不经过命令规则与下发闸门（也因此不需要）。证据摘要里**会包含被拦下的命令原文**，与会话审计同档敏感；封禁只登记草稿不下发，真机变更仍必须走 `firewall:apply` + 下发闸门。详见第 35 节
- **云资源同步**：`cloud:sync` 管触发同步（意味着「能让平台带着 AK/SK 出公网」并看到整个云账号的资源清单），`cloud:adopt` 管把云资源纳管为主机（会创建主机并写入一份登录凭据，**等价于 `host:create`**）；清单 / 漂移 / 同步记录只需登录。客户端里**没有任何写动作**，拿到密钥也只能读。详见第 36 节
- **域名管理**：`domain:manage` 管台账增删改与「从云资源导入」，`domain:check` 管触发 DNS 核对（会让平台向 DNS 服务器发查询）；列表与概览只需登录。巡检**只查 DNS、不改任何解析记录** —— 这个模块里没有写接口。详见第 37 节
- **主机日志**：`hostlog:view` 管**读主机上的日志内容**（等同于文件管理的读权限，按这一档审），`hostlog:manage` 管维护监控点、触发巡检与占用采集；列表与历史只需登录。全模块只跑只读命令，但**路径由人输入** —— 唯一的边界是 `OPS_LOG_PATH_PREFIXES` 白名单。详见第 38 节
- **安全响应**：安全事件的**原始流水视图**与**安全概览**只需登录；升格为事件工单走 `secevent:respond`；学习建议的通过 / 拒绝走 `suggestion:apply` —— 它能改暴露面基线、加误报白名单、把特征提到拦截态（**会让下一次下发真的被拦**），按「能改安全策略」的标准审。详见第 39 节
- **容器平台的只读专用页**：Helm 应用 / 自定义资源 / Gateway API 路由 / RBAC 账户**都只需登录**（与其它只读容器页一致），但两处敏感度高于其它只读页：Helm 页会读到**未脱敏的 Secret 载荷**（返回字段是白名单式收窄的，不含 values 与 manifest），RBAC 页会摊出**整个集群的提权路径地图**。共享给较多人的部署建议收紧「容器平台」目录的菜单可见性。详见第 40 节






## 部署前必做

最省事的做法是**设 `OPS_ENV=prod`**：下面 1-4 条它会强制检查，不达标直接拒绝启动（见第 25 节）。完整部署步骤见 [DEPLOY.md](DEPLOY.md)。

1. 设置 `OPS_JWT_SECRET` 为足够长的随机值（≥32 字节，`openssl rand -base64 48`）
2. 修改内置 `admin` 账号的初始口令（`OPS_ADMIN_PASSWORD`，登录后再改一次）
3. 把 `OPS_ALLOW_ORIGINS` 改为真实的前端域名
4. 设置 `OPS_DEBUG=false`（关闭 SQL 日志与 gin 调试模式）
5. 收紧数据库文件权限，**并确认备份真的在跑**：`ops backup` 手动验一次，或看「平台健康 → 自动备份」。备份文件与数据库同等敏感
6. 收紧 `OPS_RECORD_DIR` 录像目录权限，并规划保留期
7. 部署在反代后面时，把反代地址填进 `OPS_TRUSTED_PROXIES`，否则审计里的来源 IP 是反代的
8. 平台仅在可信网络内暴露；若需公网访问，前置网关做 TLS 终止与访问控制
9. 用外部监控轮询 `/readyz`：平台自身的告警都跑在自己进程里，进程死了没人叫
10. 用到「防火墙策略」时，给主机账号配**范围最小的免密 sudo**（只放 `iptables` / `ufw` / `firewall-cmd`，不要给 ALL），并确认 `firewall.sudo` 开关与实际情况一致
11. 设置 `OPS_SECRET_KEY`（≥32 字节随机串），否则全部凭据（含主机口令、kubeconfig、各类对外系统密钥）都是明文落库；设好后**与数据库备份分开保管**，之后要换或要退回明文一律走凭证库页的「更换密钥 / 取消加密」（会先备份、再逐行重写），并到「密钥加密体检」点一次「加密存量数据」把历史明文行收进来


## 31. 防火墙策略：改的是真机包过滤，风险等级等同于下发命令

这个模块最终执行的是 `iptables` / `ufw` / `firewall-cmd`，一条写错的规则可以把自己关在门外，
因此它刻意不走「平台自己一套执行逻辑」，而是复用批量执行那条链路：

- **同一个下发闸门**：生成的命令逐行过命令规则（拦截 / 提醒），目标里有生产主机时必须显式二次确认，
  被拦下的尝试进「下发拦截流水」。下发本身产生一条执行记录，逐台输出可查
- **注入面收在入参上**：来源必须是 IP / CIDR，端口必须是数字或区间，服务名只能是字母数字与 `.` `_` `-`，
  三者都不满足就不落库、更不会拼进命令。也就是说不存在「先存进数据库、下发时才发现命令是畸形的」这种窗口
- **需要 root**：非 root 账号下每条命令各自加 `sudo -n`（不是整段包一次）。拿不到权限时如实报错，
  并在界面上提示「请换 root 或配免密 sudo」，绝不静默跳过
- **平台不擅自删真机规则**：真机上有、平台没登记的规则只会被标为「未登记」并出现在清理建议里，
  下发时不会碰它。删平台登记也不会删真机规则，界面上明确写了这一点
- **回滚是真回滚**：每次下发与回滚前后各存一份真机规则原文（`firewall_snapshots`），
  回滚会对比当前与快照，补缺的、删多的，命令同样过闸门。快照含完整规则原文，
  保留期见「数据留存 → 防火墙快照」，删了就回不去那个时点
- **安全组只是规则模板，铺下去也只是登记**：「铺到成员」把模板复制成各主机的登记，**不下发**，
  要生效仍得逐台预检下发。删安全组只删模板，已经铺下去的主机副本解绑（`group_id` 置 0）留在原主机名下 ——
  避免「删一个组顺手清空十几台机器的登记」，副本要不要撤销由人逐台决定
- **不做的部分**：实时流量监控、进程连接、带宽限速、Agent 接入审批。这些需要在主机上装常驻 agent，

  纯 SSH 只能定时采样；与其做一个看起来实时其实是采样的页面，不如不做并在界面上写明

一个容易踩的坑，这里记一笔：**装了 ufw 但没 `ufw enable` 的机器，真正在拦包的是 iptables 链**。
平台按「谁在跑」判定后端，并在提示里点名「ufw 已安装但未启用，它的配置不影响当前包过滤」——
如果这里判错，下发的 `ufw allow` 会写进 ufw 配置却完全不生效，是最危险的一类假象
（这个 bug 在真机验证时真的出现过：`ufw status` 输出 `Status: inactive`，而 `grep -i active` 把它当成了启用）。


## 32. 凭证库：一份密钥多台引用，好处与代价都要说清

凭证库把「同一个运维账号的口令散落在几十台主机记录里」收成一份，改一处、所有引用主机下一次连接生效。
它解决的是口令轮换改漏的问题，代价是**把鸡蛋放进了同一个篮子**，所以这些规则是硬的：

- **密钥永不出接口**：列表 / 详情都不返回口令与私钥，连脱敏版本都不给。界面上能看到的只有公钥指纹、
  存储方式（密文 / 明文）、责任人、最近轮换与最近一次成功登录。要换密钥只能轮换，不存在「查看原值」
- **加密取决于部署**：配了 `OPS_SECRET_KEY` 才是 AES-GCM 密文（`enc:v1:` 前缀），没配就是明文，
  页面顶部会写成「明文」。存量数据不会被自动改写 —— 用体检卡片上的「加密存量数据」（明文转密文）、
  「更换密钥 / 取消加密」（换密钥或解回明文）显式操作
- **解不开一律报错**：库里是密文而进程没密钥（或密钥被改过），连接会直接失败并说明原因，
  不会拿空口令去连主机 —— 那会表现成「认证失败」，把人引向错误的排查方向
- **绝不静默回退**：主机引用的凭据被禁用或删除时，那台主机连不上，且错误里点名是哪份凭据出了问题。
  回退到主机自带的旧口令看起来「更可用」，实际是把「我以为已经换掉了」变成安全事故
- **切过来就清本机副本**：主机改为引用共享凭据时 `hosts.secret` 置空。留一份不会被轮换的旧口令，
  等于给这台机器留了个后门。反过来，从共享凭据切回本机自填必须同时提供新密钥，
  否则会存出一台没有任何凭据、连不上又看不出原因的主机
- **有引用不许删**：还有主机在用的凭据拒绝删除，并告知有几台在用
- **落库前先验密钥**：私钥类型的凭据在保存时就解析一次并算出指纹，解析不了的私钥不落库 ——
  否则要等到某次批量执行才发现「这把钥匙根本不能用」
- **带口令的私钥现在可用**：平台此前用的是 `ssh.ParsePrivateKey`，加密私钥直接报错，等于不支持。
  凭证库补上了 `Passphrase`，并把「缺的是口令」和「口令不对」分成两种错误说清楚
- **不做的部分**：口令借用审批与临时授权、到期自动轮换、SSH CA 签发短期证书；
  数据库实例、云账号、Jenkins、模型上游那些密钥仍各自存在自己的模块里，没有统一到这里

真机验证覆盖了这些行为（WSL 真 sshd + 真私钥 40 项断言全过），其中最关键的一条是：
把凭据轮换成一把目标机器 `authorized_keys` 里没有的钥匙后，引用它的主机必须立刻连不上 ——
这一条不过，就说明「轮换生效」只是界面上的文字。


## 33. 安全意识：签署与判分都在后端，逾期只会被催办

- **确认已读是一条签署记录**（`awareness_records`：人、时间、来源 IP），不是前端一个勾选框。
  记录一人一项唯一，重复发布不会清掉已有记录。
- **正确答案绝不出接口**：`awareness_questions.answer` 带 `json:"-"`，学员侧详情只返回题干与选项，
  判分在后端做。否则「考核」就是把答案先发给浏览器再问一遍。解析只在交卷之后随结果返回。
- **发布会真的产生动作**：给范围内（全员 / 角色 / 部门含子部门）每个**启用中**的账号建待办并投站内消息。
  停用账号不计入必修人数 —— 否则完成率永远到不了 100%。
- **逾期的效果是提醒，不是封禁**：`OPS_AWARENESS_SPEC`（默认每天 09:00）扫逾期未完成的项目，
  给未完成的人投一条 warning 级站内消息，同一项一天只提醒一次。**刻意不做「没做完就禁止登录」**：
  那会把一个提醒问题变成一次可用性事故。
- **记录是凭据，不随开关消失**：已经有人留下记录的项目不允许删除；下线只是不再出现在必修列表里，
  签署与成绩都保留。已发布的项目不允许改必修范围（范围一变，已有记录就对不上人了）。
- **内容不是知识库**：正文只是几条要点、按原样换行展示，不渲染 HTML、不上传课件、不发证书学分。
  长内容应当放公司知识库，这里给链接。
- **权限**：`awareness:manage` 管维护、发布、催办与看完成明细；学员侧接口不绑权限码，
  但每个人只能读写**自己**那条记录（按 `user_id` 约束查询）。

## 34. 特征库：特征必须落到一个真在跑的检测点上

- **不收「只能看」的模式表**。目前只有两类特征，各自对应一个已经在跑的检测点：
  - `command` → 命令规则（`command_rules`）。那张表是下发闸门（批量执行 / 脚本 / 定时任务 /
    防火墙下发）与 Web 终端真正在用的，所以「已应用」等于「真会拦」。
  - `port` → 暴露面扫描结果（`exposure_targets.last_open`，真机 TCP connect 探测出来的）。
- **灰度落在动作上**：observe → 规则 `warn`（命中只提醒、仍会下发）；enforce → 规则 `block`（直接拦下）。
  升灰度就是改那条规则的动作，没有第二套并行的拦截逻辑。
- **对账而不是自我声明**：命令规则可能被人手工改过或删掉，所以列表给
  unapplied / applied / **drift**（被改过）/ **missing**（规则没了）四种状态，并能一键按特征重写 ——
  与防火墙模块「平台登记 vs 真机现读」是同一种思路。显示一个永远绿着的「已应用」才是危险的。
- **正则当场编译校验**：编译不过的特征不落库。存一条编译不过的特征，等于在闸门里留一个永远不生效的洞。
- **端口特征不改基线**：「哪些端口允许开」是人的决定（暴露面模块的 baseline），特征只回答
  「这些机器上现在真的开着哪些我关心的端口」，并指出其中哪些不在该目标基线里。
  从没扫过的目标会被如实列出来，**不算通过** —— 没有数据与没有风险是两件事。
  自 Round 12 起 port 特征多了一个**会落库的消费方**：安全事件采集器遇到未登记开放端口时，
  命中启用中的 port 特征就按特征级别提升事件级别并把特征名写进证据（见第 35 节）。
  在那之前 port 特征的核对结果只出现在一次性的 HTTP 响应里，一个字节都不落库。
- **内置特征可停用不可删**：删了下次启动又会回来，反而更乱。内置 12 条里有 7 条直接挂在内置命令规则上，
  所以特征库一打开就是「已生效」的真实状态，而不是一张等着被应用的空表。
- **删除特征会连带删掉它生成的命令规则**：留一条没人认领的拦截规则比没有更危险。
- **不做的部分**：病毒特征与文件哈希比对（要常驻 agent 扫盘，纯 SSH 采样做出来是假的）、
  特征自动更新源（内网没有可信更新通道）、把特征直接塞进会话录像做内容检测。
- **权限**：`signature:manage` 维护特征、`signature:apply` 应用与撤下（它会改真正参与拦截的规则，
  所以与维护分开给）。

## 35. 安全事件：汇聚的是已有流水，封禁只出草稿

研判台本身不产生新的采集能力，它把平台已经在记的四类安全流水（下发闸门拦截、终端拦截、
未登记开放端口、越权被拒的写操作）按指纹汇聚成可研判的事件。因此这一节的风险面主要在
**「看得到什么」** 和 **「能触发什么」** 两件事上。

- **两个权限码分开给**：
  - `secevent:manage` —— 研判与处置：改状态（待研判 / 研判中 / 已处置 / 忽略 / 误报）、写结论、
    维护**误报白名单**与撤销。它同时意味着「能让一类线索从值班视野里消失」（见下面白名单那条）。
  - `secevent:respond` —— 生成**封禁规则草稿**。它只往防火墙模块写一条待下发的登记，
    不碰真机；真正下发需要防火墙自己的 `firewall:apply`。
  - 读列表与详情只需登录（与其它只读安全页一致，收敛靠菜单 RBAC）。
- **采集器只读本地库**：不连主机、不执行任何命令、不发任何网络请求，所以**不经过命令规则与下发闸门**
  （也因此不需要）。`OPS_SECEVENT_SPEC`（默认每 5 分钟）扫的是四张只追加表，按原始流水的自增 ID
  推进游标（`sys_configs` 的 `security.cursor_*`）。它能做的最坏的事是把噪音抄进事件表，而不是动机器。
- **证据摘要里会包含被拦下的命令原文**，其中可能夹着口令与令牌
  （`mysql -uroot -pXXX`、`curl -H "Authorization: Bearer ..."` 这类键盘输入）。
  这与会话审计的命令明细**同档敏感**（见第 5.1 节）：**看得到安全事件就等于看得到那些命令**。
  给 `secevent` 这组权限时请按「能读全平台命令流水」的标准审，不要按「看看告警」的标准审。
  同理，`exposure` 来源的事件摘要里带着端口号，那是一份小型暴露面清单（见第 17 节）。
- **封禁草稿只登记不下发**：生成的是一条防火墙规则（Origin=platform / State=pending /
  Lifecycle=temporary / 7 天后到期 / action=drop / direction=in），真机变更仍然必须走
  `firewall:apply` + 下发闸门（命令规则复检、生产主机二次确认、拦截留痕，见第 28、31 节）。
  这是刻意的：研判台如果能直接改真机包过滤，一次误判就能把自己的运维通道封掉。
  代价也说清楚 —— **不自动下发，也不做「封禁后自动解封」**，临时规则 7 天到期是唯一的自动收口。
- **封禁必须带端口**：底层规则模型（iptables / ufw / firewalld 三家共有的那部分表达）要求 tcp 规则
  必须带端口，表达不出「封这个地址的所有端口」。端口优先用人填的，其次用事件自己的端口，
  ssh 类事件默认 22，都推不出来就报错要求明确填 —— 不替人猜一个可能封错的范围。
- **误报白名单等于一个「关掉某类告警」的开关**：按指纹加白之后采集器直接跳过，所以它归
  `secevent:manage` 管。防呆有两条：**挡掉的次数照记**（界面按挡掉次数倒序排，挡得异常多通常说明
  当初判错了），**撤销白名单会把对应事件拉回待研判**并在处置链路上写明期间挡掉了多少次。
  与静默窗口同一个思路（第 26 节）：可以让它别响，但不能让它查不到出处。
- **「结案之后又命中」不会被状态盖掉**：采集器不改人判过的状态（那是人的判断），但会单独累加
  `hits_after_close` 并写一条 rehit 留痕，列表能一键筛出、默认排到最前。
  「结案了还在响」要么是判错了、要么是攻击还在继续，这两种都不该被「已处置」这个绿色状态藏起来。
- **让线索消失的三种状态必须写结论**（误报 / 忽略 / 已处置），后端强校验。没有理由的结案
  在事后复盘时等于没有结案。
- **处置链路只追加**（`security_event_logs`，action = collect / status / note / respond / rehit），
  与会话流水、下发拦截流水同一种做法：能回答「谁在什么时候把这条判成了什么、依据是什么」。
- **明确的空白，界面上不假装覆盖**：
  - **没有登录失败 / 爆破来源**。审计中间件只挂在鉴权后的路由组上，登录接口在公开路由上，
    所以平台**从来没有记录过一次失败登录** —— 这是一处真实的检测盲区，要补得先让登录失败进库。
  - **没有读接口的越权来源**。审计中间件跳过 GET（见第 30 节同一口径），`authz` 来源只能看到
    被拒的**写**操作。
  - **没有流量类来源**，平台不采流量，所以做不出「阻断包数」这类看板。
- **没有删除接口**：让噪音消失的正规路径是「忽略」或「误报 + 白名单」，不是删记录。
  也**没有进数据留存清理**（按指纹去重后增长很慢）；但要知道原始流水各自有保留天数，
  被清理之后事件上的 `ref_table` / `ref_id` 会变成**悬空引用**（证据摘要仍在事件行里，点不回原始行）。
- **没有的东西**：多级审批、派发给外部系统（工单 / SOAR）、事件自动处置。
  与剧本、Agent 同一条底线：判断权留给人，平台只负责把线索摆清楚并留痕。


## 36. 云资源同步：密钥第一次真的被用出去，出站目标是公网

前面十几轮里云账号的 AK/SK 只是躺在库里（第 2 节把它纳入了加密清单，但没有消费方）。
这一轮它真的被解密并用于调用阿里云 OpenAPI，风险面因此变了：**这是平台第一个会主动访问公网的功能**，
而且带着一副能读整个云账号资源清单的钥匙。

- **只读，是结构上的保证而不是约定**：`internal/cloudapi` 里**没有任何 Create / Delete / Modify**，
  只有 `DescribeInstances` 与 `DescribeDomains`。就算 `cloud:sync` 被误发出去，
  持有者也只能读，不可能通过这条路改动或释放云上资源。评审这个包时首要一条就是「有没有混进写动作」。
- **出站目标是公网，不再是内网**：与 Jenkins / 证书巡检 / 拨测 / 暴露面那几类出站面（第 12、13、19、
  17 节）不同，那些的目标地址由管理员填、打向内网；这一条的目标是固定的阿里云接入点
  （`ecs.<region>.aliyuncs.com`、`alidns.aliyuncs.com`），**不接受用户指定 Endpoint**
  （代码里那个 `Endpoint` 字段只有单测会用，把请求指向本地 httptest 桩）。所以它不是 SSRF 面，
  但它确实要求平台所在机器能出公网 —— 内网隔离的部署里这个功能会直接超时失败，
  同步记录会照实写明，不会静默看起来像「云上没有资源」。
- **默认不自动跑**：`OPS_CLOUD_SYNC_SPEC` 默认留空（十八个固定任务里唯一默认关闭的一个）。
  默认开启等于替部署方决定了「这台机器可以访问公网、也愿意消耗云 API 配额」，那不该由代码决定。
- **权限分两个码**：
  - `cloud:sync` —— 触发同步。它意味着「能让平台带着 AK/SK 出网」，也意味着能看到整个云账号的
    资源清单（实例名、IP、规格、到期时间）。按「能读全部云资产台账」的标准审，不要按「刷新按钮」审。
  - `cloud:adopt` —— 把云资源纳管为主机。它会**创建一条主机资产并写入一份登录凭据**，
    等价于 `host:create`，请按同一标准发。
  - 清单 / 漂移 / 同步记录的读取只需登录（与其它只读资产页一致，收敛靠菜单 RBAC）。
- **AK/SK 的解密失败会明确报错**：走 `openSecret` 统一路径，解不开就写进同步记录并点名字段，
  不会拿着乱码去调云接口把问题表现成「认证失败」（与第 2 节主机凭据同一口径）。
- **接口里不回传密钥**：`CloudAccount.AccessKeySecret` 带 `json:"-"`，同步记录里也只存云端返回的
  错误 Code 与摘要，不会把签名串或密钥写进 `message`。
- **建议用只读子账号**：这个功能需要的全部权限就是 ECS 与云解析的 `Describe*`。
  给主账号 AK 或给带写权限的子账号，是在为一个只读功能承担不必要的风险。
- **云上资源清单本身是敏感数据**：`cloud_resources` 表里有公网 IP、实例规格、地域分布，
  等价于一份对外攻击面清单（与第 17 节暴露面同档）。它**没有进数据留存清理**，
  并且「已消失」的行会长期保留 —— 这是刻意的（对账需要），但意味着历史 IP 也会一直留着。
- **自动匹配不等于纳管**：`matched_host_id` 是按 IP 算出来的「看起来是同一台」，
  没有任何校验（没连过、没比对过指纹）。它只用来做漂移对照，不参与任何鉴权或连接决策。
  IP 复用（云上释放后被别人拿到、或内网 IP 撞上私网段）会让它匹配错，页面上不拿它当事实。
- **明确的空白**：域名的**注册**到期时间拿不到（云解析是 DNS 托管视角，需要域名注册 API），
  所以平台上的域名到期提醒仍以人工登记为准；DNS 记录的增删改不做（需要写接口）；云账单不对接；
  腾讯云 / 华为云 / AWS 只登记不同步 —— 界面上都写明了，不留想象空间。


## 37. 域名管理：只查不改，但「期望值」本身是一份配置

域名巡检做两件事：查 DNS、算注册到期。风险面比云同步小得多（没有凭据、没有写接口），
但有两处值得写下来。

- **这个模块里没有任何写接口**：`internal/dnsx` 只有 `LookupIPAddr` / `LookupCNAME` / `LookupNS`，
  平台不会去改任何一条解析记录。DNS 记录的增删改需要注册商或解析商的写接口，**刻意不做** ——
  改一条 A 记录的影响面等同于下线一个站点，那类操作不该藏在一个「巡检」页里。
- **出站面**：巡检会向 DNS 服务器发查询。默认走系统 resolver；配了 `OPS_DNS_SERVER` 就打向那一台。
  与 Jenkins / 探测那几类出站面（第 12、13 节）不同，这里的目标**不由使用者逐条指定** ——
  只有一个全局配置项，改它需要能改环境变量（等同于部署权限）。所以它不是 SSRF 面。
  拥有 `domain:check` 的人能做的最坏的事是让平台多发一批 DNS 查询。
- **权限码两个**：
  - `domain:manage` —— 台账增删改、「从云资源导入」。它同时意味着**能改期望值** ——
    把期望值改成当前实际解析结果，就能让一条真实的漂移变成「一致」。这是一个「让告警消失」的开关，
    与误报白名单（第 35 节）同一性质，请按同样标准发。防呆是：改动走标准的审计中间件留痕，
    并且期望值与实际值在详情页**并排展示**，对不上时一眼能看出来。
  - `domain:check` —— 触发单条或批量巡检。
  - 列表与概览只需登录（与其它只读资产页一致）。
- **域名清单本身是敏感数据**：`domains` 表里有域名、解析到的公网 IP、NS，
  合起来是一份对外攻击面地图（与第 17 节暴露面、第 36 节云资源清单同档）。它**没有进数据留存清理**。
- **核对视角取决于用哪台 DNS**：内网 DNS 常把生产域名覆写到测试地址，用它核对出来的
  「一致」在外部用户看来可能根本不成立。界面上会回显每次实际使用的 DNS 服务器，
  这是刻意的 —— 一个看不出视角的核对结论比没有结论更危险。
- **自动匹配的证书关联不参与任何鉴权**：它按 SAN 算出来，只用于「在一个列表里同时看到域名与证书的到期」，
  不代表任何信任关系。
- **明确的空白**：WHOIS 查询（需要外部 WHOIS 服务，且各注册局限流与格式都不统一）、
  注册到期日的自动获取（云解析接口给不出，只能人填，为空时状态是「待补到期日」且**不发提醒**）、
  自动续费、DNSSEC 校验。界面提示里逐条写明。


## 38. 主机日志：只读，但路径来自人输入

这个模块只在主机上跑 `tail` / `grep` / `du` / `find` / `wc` / `ls -i`，
没有一条会改主机上的东西。风险不在「会不会搞坏机器」，而在**能读到什么**。

- **路径白名单是唯一真正的边界**。`OPS_LOG_PATH_PREFIXES`（默认 `/var/log`）决定允许读哪些目录。
  没有它，拥有 `hostlog:view` 的人就能读主机上任意文件 —— `/etc/shadow`、`~/.ssh/id_rsa`、
  平台自己的配置。放开新目录时请按「把这个目录下所有内容对这批人开放」来衡量。
  实现上有三道关，顺序要紧：必须绝对路径 → `path.Clean` → 判前缀。
  **Clean 必须在判前缀之前**：反过来的话 `/var/log/../../etc/shadow` 会通过前缀检查。
  另外 `/var/logother` 这类「前缀相似但不是子目录」也必须拒（判的是 `prefix + "/"`，不是裸前缀）。
- **权限码两个，档位不同**：
  - `hostlog:view` —— **读日志内容**。日志里常有口令、令牌、身份证号、手机号
    （应用把请求体打进日志是常态）。这与会话审计的命令明细、`db:query` 同档敏感，
    请按「能看生产数据」的标准审，不要按「看看日志」的标准审。
    另外它还受主机维度约束：走 `model.ActionFile`（文件管理那一档）判，看不到那台主机就读不到它的日志。
  - `hostlog:manage` —— 维护监控点、触发巡检、采集占用。它能改「读哪个文件、匹配什么关键字」，
    也就是能决定这条监控盯着什么；但仍受同一道路径白名单约束。
  - 清单、巡检历史、占用只需登录。**注意巡检历史里带命中样本**（日志原文一行），
    所以这条「只需登录」实际上让所有登录用户看得到被命中的那一行 —— 这是刻意的取舍
    （不然值班看不到证据），但配关键字时请避开会把敏感行捞出来的词。
- **输出上限在远端，不在平台**。`sshx.Run` 对 stdout 没有任何大小限制，
  一个 `grep` 撞上 GB 级日志会把服务端内存吃掉。所以远端命令一律带 `head -c`：
  查看 1MB、巡检每轮 256KB。这不是体验优化，是可用性防护。
- **注入面**：路径与关键字全部过 `shellQuote`，`grep` 固定 `-F`（字面匹配，不当正则）。
  单测里有一条真的注入尝试（关键字填 `x'; touch /tmp/ops-pwned; #`），跑完断言那个文件不存在。
- **不走下发闸门**，与平台其它只读巡检一致（见第 28 节口径）。但因为路径与关键字来自人输入，
  这里额外过一次 `precheckScript`：命中 `block` 规则直接拒，`warn` 如实带回界面。
- **平台不存日志内容**，只存命中行数与命中的第一行样本（512 字节截断）。
  日志搬进平台的库既贵又没人查，还会让保留策略变成两处维护。
  代价是：想看上下文得回到「实时查看」再 grep 一次。
- **占用采集会对所有纳管主机各开一次 SSH**。这是刻意的（没人管的机器更容易被日志写满），
  但意味着 `OPS_HOST_LOG_SPEC` 配得太密会在主机多的环境里造成可观的连接量。默认 15 分钟。
- **明确的空白**：实时 `tail -f` 流（要长连接）、日志落库与全文检索、正则关键字、
  多行日志（栈追踪）合并、按结构化字段过滤。界面提示里写明。


## 39. 安全响应：原始数据敏感、学习建议能改策略、刻意不做审批

这一节记三件事的取舍：原始流水视图的敏感度、学习建议的权限档位、以及为什么不做处置审批。

- **原始流水视图比证据摘要更敏感**。`GET /security/events/:id/raw` 返回的是**没被截断的原文**：
  完整命令行（可能夹着 `mysql -uroot -pXXX`、`curl -H "Authorization: Bearer ..."`）、
  会话里的操作人与目标主机、审计日志里的请求路径与令牌名。它目前**只需登录**，
  与证据摘要、会话审计命令明细同档（见第 5.1 节）。给 `secevent` 这组权限时请按
  「能读全平台命令流水」的标准审 —— 这一节把它再写一遍，因为原文比摘要更全。
  上一轮记过的「悬空引用」风险仍然存在，只是现在界面上会如实说「原始行已被留存清理删掉」
  而不是留一片空白。
- **RefTable 仍然过白名单**。那个字段是平台自己写进去的，但拿它拼查询之前仍然过一次
  `secSourceTables` 白名单 —— 防的不是现在，是「以后有人往这个字段写别的」。
- **升格为事件工单 = 平台里的「派发」**。走 `secevent:respond`。它不对外发任何东西
  （平台没有对接工单 / SOAR 系统），只是在事件中心建一张单并进入 SLA 计时。
  刻意**不做对外派发**：没有可对接的系统时，派发页只会是一张永远空着的表。
- **学习建议的「通过」是真的改配置**，权限码 `suggestion:apply`。三类改动的后果不同档：
  - 端口基线：把端口并进暴露面基线 → 之后这个端口不再被报为未登记。
    **等价于把一个开放端口声明为合规**，误加就等于把一处真实暴露面永久静音。
  - 误报白名单：采集器直接跳过该指纹（挡掉次数仍照记）。与第 35 节的白名单同一性质。
  - **特征提到拦截态**：改 `Signature.Stage` 并重写命令规则为 `block` ——
    **下一次下发会真的被拦**。这是三类里唯一有真实拦截后果的，界面上单独二次确认。
    实现上有一条硬规矩：阶段改了但规则重写失败必须**报错**而不是当成功，
    否则就是「页面说拦、实际还在放过」。
  
  所以 `suggestion:apply` 请按「能改安全策略」的标准发，不要按「点个采纳」的标准发。
- **应用时重算、不信前端传来的内容**。页面上那份建议可能已经过期（端口关了、特征撤了），
  照它去改就是改错东西。匹配不上的 Key 一律拒绝并说明原因。
- **「拒绝」会被持久化**（`security_suggestion_dismissals`，可撤销）。这是为了让那个按钮是真的 ——
  建议每次现算，不记下来就会下一次刷新又冒出来。
- **安全概览不产生新数据**，只聚合。它最重要的一段是 `gaps`：阻断包数 / 流量统计、
  进程与连接明细、登录失败与爆破来源、读接口的越权尝试、外部威胁情报 ——
  这五项**没有采集**，所以一个数字都不给。**用 0 冒充「没有问题」是最容易骗人的看板**，
  这条口径写在接口返回里，页面直接展示。
- **刻意不做处置审批**。与第 8 节一贯口径一致：内网自用、管理员自己对自己负责。
  加一层点「同意」不会让处置更安全，只会让人绕过它。真正起作用的约束是别的：
  封禁只出草稿、真机变更必须走 `firewall:apply` + 下发闸门（第 28、31 节）、
  让线索从值班视野里消失的状态必须写结论（第 35 节）。
- **明确的空白**：对外派发（工单 / SOAR）、事件自动处置、处置审批、
  按人或团队的处置绩效统计。


## 40. 容器平台的三个只读专用页：Helm / 自定义资源 / RBAC

这一节记两件有安全含量的事：Helm 页**会读到未脱敏的 Secret 载荷**，以及为什么这三页一律只读。

- **Helm 页绕过了 Secret 脱敏，这是刻意的，但返回的东西是收窄的**。
  平台对 Secret 的一贯口径是「只给键名不给值」（第 5.2 节），而 Helm release 的全部内容
  就在 `data.release` 这一个键里 —— 脱敏之后什么都解不出来。所以这一页用了一个**不脱敏**的
  Secret 读取路径。作为补偿，**返回给界面的字段是白名单式的**：release 名、命名空间、状态、
  chart 与应用版本、revision、历史版本数、最近一次操作说明、Secret 名。
  **刻意不返回 values 与渲染后的 manifest** —— values 里常有数据库口令与令牌，
  manifest 是整个渲染结果。审这一页时请按「能看到 Helm 部署元数据」审，
  而不是「能看到 Secret 的值」—— 后者仍然做不到，但代码层面的边界只有那个字段白名单，
  改动 `HelmRelease` 结构体时要想到这一点。
- **三页全部只读，而且是结构上的只读**。`NewReadOnlyKind` 构造出来的资源类型
  `ReadOnly` 恒为真，而 apply / scale / restart 的入口都会先拒绝只读类型（第 31 节）。
  也就是说即使以后有人给自定义资源加了写入口，也必须先改掉这个构造函数 —— 不是一句约定。
  为什么坚持只读：
  - 自定义资源的语义平台不懂。改一条 Gateway / VirtualService 等于切流量，
    改一条 ArgoCD Application 等于改部署源。
  - Helm 的 install / upgrade / rollback 需要真正的 Helm 引擎（模板渲染、钩子、依赖、
    CRD 处理）。半套实现的表现是「界面说成功了、集群里是另一回事」。
  - **改 RBAC 就是改提权路径**。这类操作仍然走 kubectl。
- **RBAC 页会把集群的授权全貌摊出来**，包括「哪个 SA 是 cluster-admin」。
  这对排查是必需的，但它同时是一份**提权路径地图**：知道哪个 SA 有 cluster-admin，
  就知道该去抢哪个 Pod 的 token。这一页目前**只需登录**（与其它只读容器页一致），
  收敛靠菜单 RBAC。在共享给较多人的部署里，建议把「容器平台」整个目录的菜单可见性收紧。
- **为什么 RBAC 必须全集群读**（也是一条安全判断，不只是实现细节）：
  只读某个命名空间的 binding 会漏掉 ClusterRoleBinding —— 而那恰好是最危险的一类授权。
  一个「看起来只有 pod 读权限」的 SA，完全可能被一条 ClusterRoleBinding 绑到了 cluster-admin。
  代价是这一页需要对 `roles` / `clusterroles` / `rolebindings` / `clusterrolebindings`
  有全集群 list 权限；给平台的 kubeconfig 权限不足时，错误信息里会写明缺什么。
- **CRD 与 Helm 的失败信息里写明所需权限**：`apiextensions.k8s.io` 的
  `customresourcedefinitions` list、`rbac.authorization.k8s.io` 的各类 list。
  权限不够时表现是 403 而不是空表 —— 这一点在界面上要能区分，否则「没装 CRD」和
  「没权限看 CRD」会被混成同一件事。
- **实例数上限 500**：有些 CRD（Argo 的 Workflow）实例能上万，全拉回来会把浏览器卡死。
  超出时如实标注「已截断」，不假装这就是全部。
- **明确的空白**：Helm 的 values / manifest / 历史 diff / 回滚、自定义资源的编辑与删除、
  RBAC 的编辑、Gateway / GatewayClass / TCPRoute / GRPCRoute 的专用解析
  （可在自定义资源页看原文）。
- **节点与命名空间清点**同样只读，`/kubernetes/node`。两点值得写下来：
  - 它会**全集群列一次 Pod** 来算分布（不是每个节点查一次）。这要求对 `pods` 有全集群
    list 权限；没有时如实标「未知」而不是 0 —— **0 会被读成「这台机器上没有 Pod」，
    结论正好相反**。同理，「既没有 ResourceQuota 也没有 LimitRange」只在真的读到了
    配额对象之后才判定，否则「没权限看」会被写成「没配」。
  - **不提供 cordon / uncordon / drain / 打污点**：那些直接改变调度行为，
    drain 还会驱逐 Pod。也**不提供命名空间的创建与删除** —— 删一个命名空间
    等于删掉里面的全部对象。这类操作仍然走 kubectl。


## 41. 告警规则版本与通知模板：留痕替代审批，模板不能成为发不出去的理由

- **不做策略审批，做版本 + 回滚**。参考站在改告警策略前插审批节点，这里不做 ——
  与第 8 节、第 39 节一贯口径一致。但**版本必须做**，而且理由是安全性的：
  **审计日志不记请求体**（第 6 节），所以在此之前「谁把这条规则的阈值从 80 改成 200」
  查不出来；而改错一条告警规则的后果是**静默的** —— 监控看着在跑，实际已经不报了，
  之后几周没人知道。能兜住这件事的是留痕 + 回滚，不是事前点一次「同意」。
- **权限分档**：版本列表 / 正文 / 差异只需登录；回滚与「误删恢复」走 `alertrule:manage`
  （与改规则同一个码 —— 回滚就是一次改规则）。
- **误删恢复的两条克制**：恢复出来的是一条**新规则**（新 ID）而不是原地复活；
  而且**默认停用**。后者是安全取舍：直接让它开始评估并发告警，等于在没人确认的情况下
  恢复了一条可能已经不适用的策略。
- **版本表永久保留**，不进数据留存清理（与 `ConfigVersion` 同口径）——
  它是回滚与误删恢复的唯一依据。快照里**只有配置字段**，不含运行态，也不含任何凭据。
- **通知模板的权限是 `channel:manage`**（与通知渠道同一个码）。它能改发出去的内容形状，
  但改不了发给谁 —— 收件人、地址、密钥都在渠道上。
- **模板不能成为「发不出去」的理由**。没配、配了但停用、类型对不上、渲染失败，
  四种情况一律回落到原来的硬编码格式。一条告警发不出去比格式不好看严重得多。
  webhook 渲染结果不是合法 JSON 时回落并**把原因写进投递流水**，
  否则使用者只会发现「模板像是没起作用」，查不到原因。
- **变量白名单在保存时校验**，这一条有实际意义：`text/template` 对 map 的缺失 key
  会**静默渲染成空串**，不校验的话写错变量名要到真发信时才表现成「正文里少了一段」——
  对告警来说那就是漏掉了关键信息。
- **模板正文里不要放凭据**。可用变量表里没有任何密钥类字段，但模板正文是自由文本，
  写死一个 token 进去它会被原样发到 IM 群或 webhook 接收端。
- **值班呼叫邮件的修复也是安全相关的**：在这之前那封邮件和普通告警一模一样，
  收件人**看不出这是在叫自己** —— 叫人叫不到位，等于升级链断了一环。
- **值班大屏只需登录**，但它把「当前值班人、未处理事件标题、SLA 超时情况」摊在一屏上，
  通常是投在墙上的。投屏的场合请留意标题里可能带业务信息；页面不显示任何凭据、
  IP 之外的连接信息与命令原文。
- **明确的空白**：检测规则与聚合策略的版本化（表已多态，接它们不改结构）、
  策略审批、IM 富文本消息、大屏的自定义布局。

## 42. 账号密码库与 2FA 验证码库：明文是给人取走的，所以安全模型和凭证库相反

这是全平台**唯一会把密钥明文返回给浏览器**的两个页面。整节的存在就是为了把这件事说清楚。

- **和凭证库（第 21 节）是两套安全模型，不是同一个功能的两个入口**：
  - 凭证库的密钥只给平台自己用（SSH 登录主机），**明文永不出接口**，连脱敏版都不给；
  - 密码库的口令是**给人用的**（某个后台系统的管理员账号），明文必须能取出来，
    否则这一页只是一份不能用的清单。
  这个区别决定了两张表不能合并：合并之后必然有一边的规则被放宽到另一边的水平。
- **明文能取，就只能靠留痕兜**。取口令 / 出验证码 / 导出种子三个动作都写 `VaultAccess`，
  记下谁、什么时候、从哪个 IP、填了什么理由。**留痕写库失败时接口直接报错，不返回明文** ——
  实现上留痕是前置步骤而不是收尾步骤，写在收尾的版本一旦写库失败明文已经发出去了，
  那张留痕表就不再可信。这一条有专门的测试守着（把留痕表删掉再取一次）。
- **权限分两档**：`vault:manage` 维护条目，`vault:reveal` 取明文 / 出验证码 / 导出种子。
  能看见清单不等于能取明文 —— 这是这一页唯一的访问控制。
- **改口令只能走「轮换」**，编辑接口显式拒绝携带口令。不是洁癖：轮换时间是逾期提醒的基准，
  编辑能改口令的话「最近轮换时间」就是假的，逾期提醒跟着一起失真。
- **取用理由选填**。强制填写只会收到一堆「日常运维」，留痕本身（谁、何时、哪一条）才是有用的部分。
- **不做审批、不做自动填充、不做复制即焚**。审批：内网自用，加一道审批只会让人把口令抄到
  本地记事本里，那比留痕可查更糟（第 8 节同一条理由）。自动填充要装浏览器插件。
  复制即焚是自欺欺人 —— 明文已经到了浏览器，倒计时清剪贴板不构成任何保护。
- **2FA 种子托管是一次明确的降级，必须写在页面上**：种子存在平台之后，
  这些账号的两步验证就退化成「能进这一页的人都能登」。平台的选择是**照实说**，
  而不是把它做成一个看起来很安全的功能。页面顶部第一段就是这句话。
- **验证码用服务器时间算**。时钟偏差超过 30 秒时算出来的码全部无效，而表现是
  「验证码总是不对」，极易被误判成种子存错。所以出码接口一并返回服务器时间并显示在界面上。
- **种子录入时就校验**：base32 解不开当场拒绝；otpauth 地址里带了非默认的位数 / 步长 /
  算法（8 位、60 秒、SHA256、HOTP）也直接拒绝而**不是静默忽略** ——
  忽略的话算出来的码永远对不上，且没人会想到原因在这里。
- **导出 otpauth 地址等于交出第二因子原件**，所以它和取明文同级：同一个权限、同样留痕
  （`action=uri`），页面上用红色告警条说明。平台不生成二维码图片（要引绘图库，链接够用）。
- **两列新密钥都登记进了加密体检清单**（`vault_accounts.secret`、`vault_totps.secret`）。
  漏登记比不加密更糟，因为体检页会显得一切正常 —— 这一条也有测试守着。
  注意这里的加密只防「库文件被拷走」，防不了「有权限的人取明文」，后者是留痕的职责。
- **条目删除后留痕不删**，`target_name` 冗余存了取用当时的名字，所以历史照样读得懂；
  反过来，有 2FA 种子关联的账号条目**拒绝删除**而不是静默连带删掉。
- **逾期提醒只针对显式设了轮换周期的条目**。平台不知道你的口令该多久换一次，
  替用户假设一个 90 天然后天天报警只是制造噪音。没设周期的在事实条里单独计数。
- **明确的空白**：口令强度检查、与目标系统联动改密（要各系统的写接口）、
  按部门做数据隔离（`deptId` 已存但还没接入过滤）、备用码托管。

## 43. 发件邮箱与出口代理：两处「静默降级」被改成了显式失败

这一节主要记两个**安全性质的行为变更**，它们比新增的两张表重要。

- **STARTTLS 不再静默降级成明文**。老实现只有一个 `smtp.tls` 布尔：为 false 时交给
  `smtp.SendMail`，而标准库的行为是「服务端 advertise STARTTLS 就升级，不 advertise 就
  **明文发送**」。也就是说中继改了配置、或者中间有东西吃掉了 EHLO 响应里的 STARTTLS，
  平台就会把 SMTP 口令和告警正文以明文发出去，**而配置界面上看不出任何区别**。
  现在加密方式是显式三选一（ssl / starttls / plain）：选了 starttls 而对方没声明支持
  就直接报错并说明原因，绝不发出去。有专门的测试守着（假 SMTP 不 advertise STARTTLS 时，
  断言接口报错且服务端一封信都没收到）。
- **跳过证书校验是新增的能力，也是一次真实的降级**。内网自签证书的 SMTP 之前根本连不上，
  所以这个开关是必要的；但打开它等于允许中间人冒充这台 SMTP 服务器。因此它
  出接口、在列表里用标签标出来、表单上勾选时立刻显示警告文案。默认关闭。
- **渠道指定的发件邮箱被删或停用时，那个渠道的邮件直接失败并点名原因**，不回落到默认邮箱。
  静默换发件人的后果不是「发不出去」，而是「发出去了但署名是另一个部门」——
  后者更难发现，也更可能触发收件方的规则过滤把整批告警扔进垃圾箱。
- **口令与代理认证信息都加密落库、不出接口**，编辑时留空表示不修改（与系统配置里的
  密钥项同一约定）。两列都登记进了加密体检清单，并有测试守着。
- **中文主题现在按 RFC 2047 编码**。这不是安全问题，但它属于同一类「表现与实际不符」：
  之前主题在部分客户端是乱码，读的人会以为这封告警坏了从而忽略它。
- **出口代理：检测是直连一次 + 走代理一次的对比**。只测代理的话，「网络本来就不通」和
  「代理坏了」返回的是同一个报错，人会按错误的方向排查。结论直接翻译成一句话
  （「问题在代理本身，不在网络」之类）。
- **代理不可用时拨测直接失败，绝不退回直连**。这是这一页最重要的一条：退回直连会让
  「出口代理挂了」表现成「目标一切正常」——监控看着绿的，实际上被监控的那条路径
  已经换了。测试里断言代理停用后目标服务器**一次都没被访问到**。
- **代理的作用范围被写在页面上**：目前只有 HTTP 拨测会真的走它，云 API、IM、Webhook、
  指标 / 日志 / 链路数据源、邮件都还是直连。不写清楚的话，「登记了代理」很容易被
  读成「平台出网都走代理了」，那是一个关于数据流向的错误认知。
- **TCP 拨测不接代理**：HTTP 代理只能代理 HTTP(S)，拿 CONNECT 去测任意端口，
  测到的是代理的放行策略而不是目标的可用性。归一化时直接清掉。
- **代理检测地址默认留空**。替用户默认填一个公网回显服务，等于替他决定了
  「这台机器可以访问公网」并把请求发到第三方 —— 内网自用的平台不做这种默认。
  出口 IP 读不到时照实说读不到。
- **明确的空白**：邮件的 HTML 正文与附件、Cc / Bcc / Reply-To、DKIM 签名、
  全平台统一的出网代理（要改十几处 http.Client 的构造点，且每处的语义都要单独确认）、
  代理的定时健康检查。

## 44. 容器平台授权：把一直开着的门关上，但默认不关

这一节要先承认一件事：**在这一轮之前，所有 K8s 只读接口对任意登录用户开放** ——
节点、命名空间、工作负载、Pod、**Pod 日志**、RBAC 账户（含绑定关系）、Secret 的键名，
只要能登录平台就能看，路由上一个 `RequirePerm` 都没有。主机与数据库早就有
「数据范围 + 资源授权」两层机制（第 20 节），K8s 一直没接进去。这是一个存在很久的缺口。

- **闸门只有一处**：授权校验写在 `requireKubeCluster` 里，全平台 25 个 K8s 读写接口
  都要经过它。放一处的理由不是省代码，是**漏不掉** —— 以后新增只读接口只要走这个函数
  就自动被卡住，而散在 25 个 handler 里的版本一定会漏掉某一个。
  代价是要靠 `c.FullPath()` 判断「这是不是日志接口」，这一点写在代码注释里。
  端口转发的集群 ID 在请求体里、走不了这条闸门，所以单独一个 `kubeForwardGrantCheck`。
- **默认不生效**（`kube.grant_enforce = false`）。这是刻意的：默认打开会让升级瞬间把
  所有非管理员锁在外面，那种"安全"是靠制造事故换来的。页面顶部照实显示当前是哪种状态，
  事实条里数出「有几个集群一条授权都没有」——那些集群一开启就对非管理员完全不可见。
- **拥有 `kube:manage` 的人不受限制**。不是偷懒：授权页本身也在平台里，配错一条就能把
  管理员自己锁死，而平台没有后门可走。诊断接口按**被诊断的那个人**算豁免，不是按当前登录的人。
- **一条授权表达完整的可见范围**（集群 + 命名空间清单 + 资源类型清单 + 三个开关），
  不拆成参照站那样的「授权」与「数据授权」两页。拆开必然出现「两处配置矛盾时听谁的」，
  而那个问题没有直觉正确的答案，任何取舍都会让人算不准自己能看到什么。
- **不支持「全部集群」**。那等于一张空白支票：新接入的集群会被旧授权自动包含进去，
  而没人会回来看这条授权。必须逐个集群写。
- **限定命名空间时，跨命名空间的查询被拒绝而不是静默过滤**。静默过滤看起来更友好，
  但它会让人以为「这个集群里只有这几个命名空间」，从而基于一个残缺的视图做判断。
- **Pod 日志单独一个开关**。日志里常带业务数据、令牌与连接串，「能看到对象」与
  「能读它的日志」不是一件事。写操作与端口转发同理，且与功能权限是 **AND** 关系：
  `kube:write` / `kube:forward` 管「这个人有没有这类操作」，授权管「在哪个集群上」。
- **多条授权取并集**（用户维度 + 角色维度）：命名空间清单取并，三个开关取或。
  并集 + 有效期 + 管理员豁免 + 总开关四件事叠起来，人对着列表一定会算错，
  所以有一个**诊断接口**直接算出「这个人现在到底能看到什么」。
- **集群列表跟着过滤**：授权生效时选择器里只出现能打开的集群。列出来却一点就 403
  比看不见更让人困惑。
- **拒绝原因说清是哪一层拦的**：集群没授权 / 命名空间不在清单 / 资源类型不在清单 /
  这条授权没开日志。「没有权限」四个字帮不了任何人。
- **明确的空白**：按集群做审计过滤（改动留痕表已有 ClusterID，接它不改结构）、
  把授权同步成集群内真实的 RBAC 对象（那需要写集群，与「K8s 只读」的定位冲突）、
  Secret 值的单独授权（平台目前只显示键名，从不显示值）。

## 45. 主机体检报告：宁可留空白，也不写读起来像结论的话

参照站对应的是「Agent 报告」，靠常驻 agent 上报漏洞、补丁、软件包与进程端口清单。
本平台**没有任何常驻采集**，所以这一页不是那一页的实现，而是另一件事：
把已有的几条 SSH 定时巡检链路按主机汇总成一张可以打印的单子。

- **报告不触发任何采集**。打开它不会产生一次 SSH 连接 —— 否则「生成报告」会变成
  一个能被反复点击的批量登录入口。
- **固定列出「没有采集过什么」**：漏洞 / CVE、补丁、已装软件包、进程清单、
  完整监听端口、失败登录记录、硬件序列号，逐条给出为什么没有。
  这一段是这一页诚实性的核心 —— 一份体检报告如果对漏洞一字不提，
  读的人会默认"没写就是没问题"。同时**不使用「未发现漏洞」这类措辞**，
  有一条测试直接断言整份报告里不出现这种字样。
- **「没有数据」与「数据正常」分开**。每一段要么有 `gap`（说明为什么没有），
  要么有明细；空数组不会被渲染成"检查通过"。三条链路失败时留下的东西还不一样，
  报告里照实区分：指标会留一条 `status=failed` 的记录（所以能区分"采过但失败"
  与"从没采过"），服务与配置是更新同一行、`drift=error` 且**实际态沿用上次成功的值**
  （条目上会写明这一点），防火墙**根本没有定时任务**、数据新旧取决于有没有人打开过那一页。
- **每段带采集时间，超过 24 小时标「已过期」**。一个没有时间戳的数字在排查时是危险的。
- **基本信息逐项标注来源**（人工登记 / SSH 采集）。特别是「系统信息」：它来自
  连通性检查里顺带的一条 `uname -srm`，**只在有人点「检查」时更新，没有定时任务**，
  所以它可能是几周前的。
- **权限沿用主机的数据范围与资源授权**：看不到这台主机的人也拿不到它的报告。
  报告里含日志命中样本之外的巡检结论、防火墙规则统计与操作痕迹计数，
  不含任何凭据、命令原文与日志正文。
- **明确的空白**：报告导出成 PDF / Excel（现在靠浏览器打印）、多主机对比、
  报告快照留存（现算不落库：存下来只会多一份会过期的副本）、
  以及所有需要 agent 才能拿到的东西。
