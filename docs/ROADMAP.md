# OpsOne 模块路线图

OpsOne 的目标是把主机与资产、运维执行、容器、监控告警、安全合规、组织权限收敛到一个工作台里，面向中小规模自建环境。本文件是模块清单与实现状态的单一来源。

菜单与权限位已全部就位（`server/internal/db/db.go` 的 `Seed`），未实现的模块指向 `/placeholder/index` 占位页。菜单 ID 按模块分段，新增子项在本段内追加即可。

状态说明：`[x]` 已实现可用 · `[~]` 部分实现 · `[ ]` 仅有菜单占位


## 工作台（ID 10-19）

- [x] 平台总览 `/dashboard/overview` — 主机总数/在线离线、环境分布、最近执行
- [x] 个人工作台 `/dashboard/personal` — 待办（未读消息、未恢复告警）、我的主机与定时任务、我最近的执行与会话
- [x] 我的资源 `/dashboard/my-resources` — 按数据范围过滤的主机统计、环境与部门分布、在线率、离线优先列表
- [x] 我的活动 `/dashboard/my-activity` — 我的操作流水、我的终端会话、我发起的批量执行


## 资产管理（ID 100-199）

- [x] 主机资产 `/asset/host` — CRUD、环境/标签/状态过滤、连通性探测、跳板机关联、CSV 批量导入导出（模板下载、试运行报告、按 address+port 幂等更新，**导出不含登录凭据**）
- [x] 数据库资产 `/asset/database` — 实例纳管（MySQL/PG/Redis/Mongo）、按类型带默认端口；连通性检查对 MySQL/PG **真建连接**并回写版本号，其余类型退化为 TCP 端口探测
- [x] 云账号 `/asset/cloud` — 云账号与密钥台账（AK 列表页脱敏展示）
- [x] 云资源同步 `/asset/cloud-sync` — 阿里云 ECS 与云解析域名的**真实同步**（只读 OpenAPI，签名用标准库自实现、客户端里没有任何写操作）、按私网/公网 IP 自动匹配主机、漂移对照三视图、未纳管 ECS 一键纳管（凭据人工填）、同步记录（成功失败都留痕）。默认**不自动同步**（`OPS_CLOUD_SYNC_SPEC` 留空，这一项会真的出网）；腾讯云 / 华为云 / AWS 只登记不同步；DNS 记录增删改、域名**注册**到期时间、云账单均未实现
- [x] 域名管理 `/asset/domain` — 台账（注册商/注册与到期日/自动续费/责任人/用途）+ **真实 DNS 核对**（A/AAAA、CNAME、NS 与人填的期望值对照，`internal/dnsx` 仅标准库、带超时、三类并发、可指定 DNS 服务器）+ 注册到期提醒 + 按证书 SAN 自动关联证书 + 云解析托管域名一键导入。解析漂移与注册到期分开告警，走证书巡检那条既有告警链。`OPS_DOMAIN_SPEC` 默认 `0 8 * * *`、`OPS_DNS_SERVER` 可指定解析服务器。**不实现**：DNS 记录增删改、WHOIS、自动续费、注册到期日的自动获取（云解析接口给不出，只能人填）

- [x] 标签管理 `/asset/tag` — 标签字典、分类与配色、主机/数据库用量统计，表单内可选可新建
- [x] 固定资产 `/asset/fixed` — 设备台账、SN/型号/位置/使用人、关联主机、采购与保修、到保提醒与原值合计

- [x] 资产盘点 `/asset/inventory` — 批次快照、逐条登记（正常/缺失/位置变更）、完成时未盘按缺失处理、进度与结果统计
- [x] 采购记录 `/asset/purchase` — 单据 + 明细、金额自动汇总、收货入库可按明细生成固定资产


## 运维执行（ID 200-299）

- [x] 导航与可发现性 — 侧边栏递归渲染（支持三级及更深），「运维执行 → 堡垒机」把 Web 终端 / 会话审计 / 文件管理收成一组（这三件事合起来才是大家认知里的堡垒机，散在一级列表里会让人以为平台没这个能力）；顶栏菜单搜索（Ctrl+K，按标题跳转并显示所属分组）；占位页明确写「功能尚未实现」并给出路线图位置与当前可替代的能力。**内置菜单的标题/图标/排序仍由管理员在菜单管理里维护，代码升级不覆盖**
- [x] Web 终端 `/execute/terminal` — SSH PTY、窗口自适应、跳板机隧道、会话录像、命令拦截

- [x] 批量执行 `/execute/batch` — 并发下发（上限 10）、单机超时、生产二次确认（后端强制，不是只有前端弹窗）、下发前预检、执行历史
- [x] 会话审计 `/execute/session` — 会话流水（操作人/登录账号/主机/状态/风险/时间范围筛选）、跨会话命令检索（关键字 + 风险 + 操作人 + 主机 + 时间范围，命中即可跳到录像对应时间点）、会话内命令明细分页、命中规则描述快照、按条件导出 CSV、录像回放（倍速 + 命令定位）；**不做击键级录制、不对录像做 OCR/全文检索，检索也不按数据范围过滤**（能进这个菜单就能看到所有人的命令）
- [x] 文件管理 `/execute/file` — SFTP 目录浏览、上传、下载、新建目录、重命名、删除空目录，动作全留痕（含连接失败的尝试）
- [x] 定时任务 `/execute/scheduler` — 标准五段 cron、多主机并发下发、启停与立即执行、运行记录复用批量执行历史
- [x] 脚本库 `/execute/script` — 分类/说明/参数化（`${PARAM}` + 必填 + 默认值）、命令规则静态预检（拦截级禁止下发）、渲染预览、下发复用批量执行链路、使用计数；**不做版本管理与审批流**
- [x] 构建发布 `/execute/build` — Jenkins 服务器登记与连通性测试、参数化触发构建、构建记录手动同步状态（平台不轮询）
- [x] 下发闸门 — 所有命令下发路径（批量执行/脚本/定时任务）在 `RunOnHosts` 处统一拦截：命令规则逐行匹配（拦截级不下发）+ 生产主机显式确认（后端强制）；定时任务保存时就校验命令与生产确认；被拦下的下发不产生执行记录，独立记入拦截流水（`exec_guard_logs`）；补了定时任务编辑与立即执行的两处数据范围缺口。**不做审批、双人复核、变更窗口与限流**

- [x] 数据库查询 `/execute/db-query` — 复用「数据库资产」里的实例（MySQL/PG）浏览库/表/字段/索引（含注释、行数估算、视图标记）并执行**只读 SQL**；三层防线 = 语句白名单（只放 select/with/show/explain/describe，拒多语句、注释绕过、`INTO OUTFILE`/`FOR UPDATE`/`pg_read_file`/`COPY ... TO PROGRAM`/`sleep`/`benchmark`）+ 会话级只读（PG `default_transaction_read_only`、MySQL `SET SESSION TRANSACTION READ ONLY`）+ 库侧只读授权；500 行截断并标注、30s 语句超时、CSV 导出（BOM，≤10000 行）、执行前预检、全量查询流水（语句原文/操作人/来源 IP/耗时/行数/拦截原因，留存天数可配）。**不做写操作、结果集编辑、Redis/Mongo、BI 报表与 AI 生成 SQL**


## 容器平台（ID 300-399）

- [x] 集群接入 `/kubernetes/source` — 粘贴 kubeconfig 纳管（解析上下文后选用哪个）、连通性与版本检查、节点就绪明细（角色/容量/kubelet/cordon）；不可达或有节点 NotReady 自动写告警并可恢复，定时检查由 `OPS_KUBE_CHECK_SPEC` 控制。**只接受内嵌凭据**，不支持路径式 kubeconfig；**kubeconfig 明文存库**，见 docs/SECURITY.md 第 16 节
- [x] 工作负载 `/kubernetes/workload` — 按命名空间看 Deployment / StatefulSet / DaemonSet 的副本就绪情况、Pod 状态与容器异常原因、集群事件（可只看 Warning）；Pod 行可直接看**容器日志**（多容器/init 容器切换、行数 200~5000、时间戳、上一个容器、每 5 秒自动刷新、下载，单次 1MB 上限并标注截断）。**不做 follow 流式跟随**、**不提供 exec**；资源改动走「资源管理」
- [x] 资源管理 `/kubernetes/resource` — 按类型列资源（带类型相关摘要）、看单个对象的可编辑 YAML（自动清掉 status 与 resourceVersion / uid / managedFields 等集群自维护字段）、服务端 apply（`fieldManager=opsone`）并可先 `dryRun=All` 预检、Deployment / StatefulSet 直接改副本数（`/scale`，同样可预检）；字段冲突返回 409 并带出冲突字段，可显式「强制接管」；每次改动（含预检与失败）写 `kube_change_logs` 留痕，记录提交的 YAML 原文与 API Server 原话，写操作绑 `kube:write`。**类型白名单**（Deployment / StatefulSet / DaemonSet / CronJob / Service / ConfigMap / Ingress），**不提供删除**，**不开放 Secret / Namespace / RBAC**，**一次只提交一个对象**（多段 YAML 拒绝），也**不做版本回滚与 diff**
- [x] Helm 应用 `/kubernetes/helm` — release 从集群里 `type=helm.sh/release.v1` 的 Secret 解出来（两层 base64 + gzip + JSON），**不依赖 helm 二进制、不访问 chart 仓库**；给出状态、chart 与应用版本、第几次发布、历史版本数、最近一次操作说明。同名 release 只显示最新 revision。**不做 install / upgrade / rollback / uninstall**（需要真正的 Helm 引擎），**不返回 values 与渲染后的 manifest**，**只认 secret driver**
- [x] 自定义资源 `/kubernetes/crd` — CRD 清单运行时从集群读出（不是内置白名单）；served 与 storage 版本分开显示、常见组给中文说明、按版本列实例、详情**保留 status**；CRD 未就绪（`Established≠True`）在查实例前就拦下并说明。同页含 **Gateway API 路由**：把 HTTPRoute 的三层嵌套拍平成「什么流量 → 送到哪」，没装 Gateway API 时明说没装并指路 Ingress。**一律只读**，不提供自定义资源的编辑
- [x] RBAC 账户 `/kubernetes/rbac` — 反查每个 ServiceAccount 的实际权限（binding → role → rules，k8s 里没有这样一个现成对象）；Role 与 Binding **一律全集群读**（命名空间里的 SA 可能被 ClusterRoleBinding 授权）；`cluster-admin` / 通配符 / 无授权 / **孤儿绑定**单独标出并可筛选，危险的排最前。只反查 ServiceAccount（User / Group 由集群外认证系统管）。**只读** —— 改 RBAC 就是改提权路径
- [x] 节点与命名空间 `/kubernetes/node` — 只看它们自身的健康与约束（**资源账本仍然只在「容量与配额」页算一遍**）。节点：Ready 与各压力条件（判断方向相反）、污点及效果说明、cordon、容量与可分配分开给、节点上活着的 Pod 数与上限、**kubelet 版本偏斜**提示；排序按严重程度而非问题条数。命名空间：Pod 分布、ResourceQuota 已用/上限（只列 hard 里设了上限的项）、有没有 LimitRange、**Terminating 时列出 finalizer**。「既没配额也没 LimitRange」只在真读到配额对象后才判定；Pod 数读不到时显示「未知」而不是 0。**只读**，不提供 cordon / drain / 打污点与命名空间增删
- [x] 服务转发 `/kubernetes/forward` — 把 Pod / Service 端口映射到平台上的一个 TCP 端口（相当于把 `kubectl port-forward` 挪到平台跑）；走 API Server 的 **WebSocket** 通道（不引 client-go，也不自己实现 SPDY），每条本地连接单开一条 WebSocket；Service 目标每条连接重新解析后端 Pod，Pod 重建/扩缩容后隧道仍可用；实时展示活跃与累计连接、双向流量、剩余时长、拨号失败原因，到期自动关闭并把计数写回档案。约束由环境变量定死（监听地址、端口区间、隧道数、单隧道并发、TTL）。**隧道是进程内的活物，重启即消失**（启动时把残留记录标为已关闭）；**隧道端口不做认证**，见 docs/SECURITY.md 第 16 节；**不做 UDP 转发、不做多端口一条隧道、不做长连接复用（每条连接一条 WebSocket）**

> 实现方式：手写 Kubernetes REST 客户端（`server/internal/k8s`），不引入 client-go —— 只读列表与服务端 apply / scale 都是普通 HTTP 请求（`application/apply-patch+yaml`、`application/merge-patch+json`），不值得为此背上几十兆依赖树。port-forward 也没走 SPDY：kubelet 还支持一套朴素的 WebSocket 通道协议（通道号 + 2 字节端口号前缀），各语言客户端库用的就是它，已在 k3s v1.31 上实测打通。

## 监控告警（ID 400-499）

- [x] 告警态势 `/monitor/situation` — 趋势折线（24h/7d/30d 分桶）、级别与来源分布、Top 标签、平均确认与恢复时长

- [x] 告警列表 `/monitor/alerts` — 概览卡片、级别/状态/关键字筛选、确认与恢复、投递流水
- [x] 告警规则 `/monitor/alert-rules` — 11 个内置指标（全部取平台自身数据，不依赖 Prometheus）、比较符 + 阈值 + 统计窗口 + 连续命中降噪、定时评估与手动试跑、命中写告警并自动恢复；**不含 PromQL 与外部指标源**
- [x] 检测规则 `/monitor/detection-rules` — 多告警关联：并发窗 / 顺序链 / 窗口 Join（按标签对齐到同一对象），每步按标题摘要关键字 + 接入源 + 级别 + 标签匹配；窗口内发生过的告警都算（含已恢复），命中写告警并自动恢复，草稿可「预演」看每步命中明细；排除自身产生的告警以防自激。**不做跨平台事件流接入**，只关联本平台告警表
- [x] 通知路由 `/monitor/routing` — 优先级 + 级别/标签匹配、兜底路由、选路预演

- [x] 聚合策略 `/monitor/aggregation` — 按接入源/级别/标题/任意标签维度实时归桶、成桶阈值、归桶预览、策略重叠检测；可选「抑制通知」（同桶窗口内只通知首条，其余仍入库并在告警上记录抑制来源）
- [x] 静默与维护窗口 `/monitor/silences` — 时间窗（右开区间、单条最长 30 天）+ 匹配条件（级别 / 来源 / 标题关键字 / 标签，填了的都要命中；不填必须显式勾选「匹配全部告警」）；**只拦外发通知、不拦入库**，被拦的告警记 `silenced_by` / `silence_id`（与聚合的 `suppressed_by` 分开存，否则会把被静默的告警当成「已通知过的首条」而破坏聚合语义）；保存前可试算命中范围；支持提前结束、停用、命中计数与命中告警列表；**值班升级按当下时间重新判定**，窗口里不叫人、窗口一过自动恢复；已拦过告警的窗口禁止删除。**不做周期性静默**（每周三 2:00 这类），一次性窗口 + 提前结束够用；也不按主机/服务对象静默——用标签条件表达
- [x] 事件中心 `/monitor/events` — 从告警或聚合桶升格为事件、指派负责人（附站内消息）、处置时间线、状态流转（待处理/处理中/已解决/已关闭）、解决时可联动恢复关联告警、诊断上下文（按标签反查主机/拨测/证书/规则的当前状态）；**平台不自动建单**
- [x] 指标查询 `/monitor/metrics` — 接入已有 Prometheus（兼容实现同理）：多数据源 + 默认源、连通性检查（buildinfo + tsdb 状态，展示版本与序列数）、即时查询（表格）与范围查询（折线图，步长按范围自动算、点数上限对齐 Prometheus 的 11000）、指标名补全、常用查询收藏。PromQL 错误与警告原样透出（带 errorType）。**平台不存时序数据**、**不改写 PromQL**、**不做告警规则联动**（那是 Prometheus / Alertmanager 或平台自己的「告警规则」的事）、曲线超 60 条截断
- [x] 日志查询 `/monitor/logs` — 接入已有 Loki：多数据源 + 默认源 + 多租户（`X-Scope-OrgID`）+ 鉴权头、连通性检查（用 labels 接口，顺带报最近一小时标签数）、LogQL 查询（时间范围、条数上限 5000、最新/最旧在前）、标签与标签值下拉直接拼出 `{k="v"}` 选择器、跨流按时间归并成一条时间线、单行超 8000 字符截断并标记、结果可下载、显示 Loki 扫描的行数与字节数。Loki 的报错常是纯文本（不像 Prometheus 有 JSON 信封），已按这一点处理并原样透出；聚合类表达式返回 matrix 时明确提示去「指标查询」页。**不做实时 tail**（要长连接；真要盯日志更适合 `kubectl logs -f` 或 Grafana）、**不做日志落库**、**不做标签级细粒度授权**
- [x] 链路追踪 `/monitor/traces` — 接入已有 Jaeger（Query API）：多数据源 + 默认源 + 鉴权头、连通性检查（服务列表，顺带报服务数）、按服务/操作/最小耗时/时间范围/标签搜 trace、列表给出入口服务与操作、总跨度、span 数、涉及服务与出错 span 数（可只看有错的）、按 TraceID 直查；详情是 span 瀑布图（深度优先排列 + 相对偏移，点 span 看全部标签），span 超 800 个截断并告知。出错判定同时认 `error=true`、HTTP 5xx、`otel.status_code=ERROR`。Jaeger 的错误体**有时带着 HTTP 200**，已按这一点处理。**不接收上报、不存链路数据**、**不做服务依赖拓扑图**（Jaeger 自带）、**不做 Tempo/Zipkin 适配**（可后续按同一套 source 模型扩）
- [x] 主机日志 `/monitor/host-logs` — **不依赖任何日志系统**，直接 SSH 跑 `tail`/`grep`/`du` 读主机文件。实时查看（末尾 N 行 / grep -F 关键字，远端 `head -c` 截断到 1MB）、关键字巡检（inode + 字节偏移增量、轮转与 truncate 自动归零水位、首次只记水位不回溯历史、命中与「读不到」分别告警）、日志目录占用（总量 + 最大文件 Top 15，`find -printf` 不可用时退回 `du -a` 并标注含目录）。路径白名单 `OPS_LOG_PATH_PREFIXES`（默认 `/var/log`）是唯一的安全边界。**不实现**：实时 tail -f 流、日志落库与全文检索、正则关键字、任何写操作

- [x] 事件复盘 `/monitor/reviews` — 事件标记已解决时自动建复盘草稿；时间里程碑给建议值并说明每个值是从哪条记录推出来的，推不出来的（止血时间）就明说只能人填；证据按事件时间窗汇聚通知流水/升级记录/静默命中/被抑制告警/下发拦截/主机指标/拨测记录，并列出取数口径；归档前强制补齐根因、影响面、恢复时间与至少一条改进项；改进项独立跟踪（负责人 + 截止日 + 状态），逾期由 `OPS_REVIEW_SPEC` 催办。详见 Round 7
- [x] 处置剧本 `/monitor/runbooks` — 按标签（全部命中 +3）/ 关键词（任一 +2）/ 级别（+1）给固定权重打分并给出每条匹配理由，在告警与事件详情里出推荐；步骤命令过命令规则静态预检，命中拦截规则的剧本不许启用；使用要留结果，用过的剧本不许删只能停用；复盘可一键沉淀成剧本草稿。详见 Round 8
- [x] 监控设置 `/monitor/sla-settings` — 按事件级别分设响应 SLA 与恢复 SLA 目标（分钟，填 0 表示这一级不设）、临期提前量与重复提醒间隔；响应 SLA 从建单时间起算且**指派不算响应**；事件列表有 SLA 列与「已超时 / 临期」筛选（翻成 SQL，在分页之前执行），临期与超时由 `OPS_SLA_SPEC` 扫出来给负责人发站内消息。**SLA 不落库**，每次按当前时间重算。详见 Round 11

- [x] 模型资源池 `/ai/model-pool` — 把多个供应商的模型收成一个网关：一条记录 = 某供应商的某模型，同 Alias 的多条互为备份（权重即优先级，主用失败自动切下一条，最多试 3 条）；`POST /api/v1/ai/chat/completions` 与 OpenAI chat 接口同构（`model` 传 Alias），每次调用含失败与切换都落流水（token 取上游 usage，成本按登记单价算），界面可试调用、可指定某条上游试（停用的也能试）。「检查」= 拉 `/models` + 真打一次 `max_tokens=1` 的最小调用（**`/models` 在部分实现上不校验密钥**，只探列表会给出假结论），探活本身也计入流水。**只支持 OpenAI 兼容的非流式**、**不落提示词与回复正文**、**不做按比例分流的加权轮询**（权重是优先级，事故好复盘）、**不做配额与限流**、**成本是估值不是账单**

  - **刻意不做的事**：**Agent 只读，不执行命令、不改任何东西**（在能连生产机器的平台里放一个会自己动手的东西，收益远不及风险）；**不做工具调用 / 多步工作流 / 评测集**；不做定时自动运行（避免无人看管地烧额度）；上下文只从平台已有的表里取，不新增采集
  - 与网关共用同一条派发路径，因此运行会计入「用量与成本」（来源标 `agent`）；上下文取不到时先落失败记录再报错，且**不会去调模型**

## 已落地：防火墙策略 `/security/firewall`

原先是占位页，现已实现「SSH 读真机 + 平台登记 + 对账 + 预检 + 下发 + 快照回滚」。
两个设计决定值得记下来：

- **不做平台镜像**：真机规则每次现读（`internal/fwx`），平台只存期望状态与运维元数据
  （责任人 / 生命周期 / 到期时间）。防火墙规则谁都能上机器手改，镜像一定会过期，
  只落库不对账的功能等于骗人
- **不装 agent**：因此实时流量监控、进程连接、带宽限速、Agent 接入审批这四项明确不做
  （参考站那四页是 agent 方案）。纯 SSH 只能定时采样，做一个「看起来实时」的页面比不做更糟

下一步如果要继续加深：Kubernetes 按集群下钻（参考站有约 30 个资源页 + 按集群 RBAC 授权）。

## 已落地：凭证库 `/security/credential`

主机凭据原先内嵌在主机记录里，换一次口令要逐台改、改漏的那台静默失效。现在共享凭据独立成表，
主机通过 `hosts.credential_id` 引用，解析点收在 `buildTarget` 一处，六条 SSH 链路（终端 / 批量执行 /
文件 / 采集 / 防火墙 / 探测）自动跟着生效，跳板链也天然继承。

三个设计决定：

- **加密是可选的，但必须说实话**：配了 `OPS_SECRET_KEY` 才是 AES-GCM 密文（`internal/cryptox`），
  没配就是明文，页面顶部照实标注。历史明文记录不自动重写，轮换一次才转密文 ——
  偷偷改写存量数据，出问题时没人解释得清楚
- **绝不静默回退**：凭据被禁用 / 删除 / 解不开密时，引用它的主机连不上并点名原因
  （`sshx.Target.PrepareError`）。回退到主机自带的旧口令看起来更可用，实际是把
  「我以为已经换掉了」变成安全事故
- **顺序是先测再铺**：测试连接用目标主机的地址与跳板链、认证强制用被测凭据，绑定前就能验；
  轮换后不自动逐台复验（几十台串行要几分钟），而是明确告诉人「影响 N 台，挑一台点测试连接」

顺带补上了一个一直缺的能力：**带口令的私钥**。此前用的是 `ssh.ParsePrivateKey`，加密私钥直接报错，
等于平台完全不支持这类钥匙。

下一步：其它类型的密钥（kubeconfig、数据库实例、云账号、Jenkins Token、模型上游 Key）目前仍各自
明文存在自己的模块里，可以逐步收进凭证库；再往后是 SSH CA 签发短期证书的「凭据不落地」方案。

## 已落地：Kubernetes 按集群下钻（资源管理页扩容）

参考站按集群铺了约 30 个资源页，这里没照抄页面数量，而是把**一页能下钻**做通：
资源类型从 7 种扩到 17 种（按工作负载 / 网络 / 配置 / 存储 / 集群分组），对象详情除 YAML 外
增加「它自己的事件」与「关联 Pod」两个页签，工作负载增加滚动重启。

几个决定：

- **类型分三档而不是一刀切**：可写 / 只读 / 脱敏只读。Pod、ReplicaSet、Node 这些由控制器维护的
  对象给只读（编辑入口干脆不给，而不是点了再报错）；Secret 给「脱敏只读」——
  「这个 Secret 里有没有 tls.key 这个键」是真实需求，值本身谁都不需要在平台上看。
  脱敏过的 YAML 必须禁止提交，否则会把真实值覆盖成占位符，那比不做这个功能糟糕得多
- **RBAC 连只读都不开**：能看到全部权限绑定本身就是侦察面
- **关联关系只认集群自己的选法**：按 `spec.selector` 的等值标签查 Pod，`matchExpressions`
  问不出来时返回空并说明原因，不按名字前缀猜 —— 猜出来的关联比没有更危险
- **滚动重启说清它是什么**：给 Pod 模板打 `kubectl.kubernetes.io/restartedAt`（与 kubectl 同一个注解键，
  两边看到的是同一回事），界面明说这不是原地重启容器、副本为 1 时会有短暂不可用

真集群验证（WSL 里的 k3s v1.31.5，41 项断言全过）里最关键的一条：重启之后不只看接口返回，
而是等控制器把 Pod 换掉、确认旧 Pod 名字已经消失 —— 否则「重启成功」就只是一句话。

下一步如果继续加深容器平台：Pod 的 exec（需要先想清楚审计怎么做，
不能像终端那样只录 SSH）、以及告警与容量的联动。

## 已落地：密钥落库加密推广 + 加密体检

凭证库那一轮只加密了 `credentials` 表，而权限最大的两份凭据其实在别处：
`kube_clusters.kubeconfig`（通常等同 cluster-admin）和 `hosts.secret`。这一轮把它们
和 `db_instances.secret` 一起纳入同一套 AES-GCM。

两个决定：

- **不用 GORM 钩子，在读写点显式调用**。钩子看起来更保险（"没有一条写路径能绕过"），
  但它在 `Save` 全列写回、`Updates(map)`、`Select(...).Updates(struct)` 这几种形态下行为差别很大，
  一处理解错就会把密文再加密一次或把明文写回去 —— 这种 bug 在库里是不可逆的。
  显式调用的代价是「可能漏一条写路径」，所以配了**加密体检**：按前缀直接数每列还有多少明文行，
  漏了就看得见，而不是靠人盯代码。体检里还把**尚未纳入加密**的 7 个字段一并列出来，
  避免「以为已经全加密了」
- **存量数据不自动改写**：启动时悄悄改库，出问题时没人解释得清。界面上给一个「加密存量数据」，
  幂等、值不变，点了才动

最危险的一处是集群更新：原来它把「库里读出来的值」和「用户新传的值」混在同一个变量里再写回去。
加密之后这条路必须拆开 —— 库里那份是密文要先解开才能解析，新传的那份是明文解析完再加密。

验证 26 项全过，核心是「先证明明文能用 → 迁移成密文 → 再证明还能用」：
真 k3s 集群检查在 kubeconfig 变成密文后仍 healthy、也能正常列资源；主机私钥变密文后 SSH 仍在线；
重复迁移重写 0 行；只改备注 / 只改属性（密钥字段留空）之后两条链路都还能用（没把密文二次加密）。
CDP 9 项覆盖体检区块。

**没验到的**：`db_instances.secret` 这条路只过了编译与体检计数 ——
这台机器上没有可连的 MySQL / PostgreSQL 服务，所以「密文口令能真连上库」这一条本轮没有真机证据。


## 已落地：对外系统凭据全部纳入加密（含 SMTP 口令），体检清单补全

上一轮只覆盖「登录到主机 / 集群 / 库」那几列，对外系统的密钥还都躺在库里。这一轮把它们全收进来，
覆盖面从 5 列到 16 列：LDAP 服务账号口令、IM AppSecret、云账号 AK/SK、Jenkins Token、
模型上游 Key、通知渠道签名密钥与鉴权头、指标 / 日志 / 链路三个数据源的请求头、SMTP 口令。

几件比「多加密几列」更值得记下来的事：

- **上一版「尚未纳入」清单自己是错的**。补字段时发现 4 处从未被登记过：`notify_channels.header_value`、
  `log_sources.header_value`、`trace_sources.header_value`，以及 `sys_configs` 里 `key='smtp.password'`
  那一行。**清单漏登记比字段没加密更危险** —— 体检页会显得一切正常。所以体检项加了一个 `Where` 维度，
  好让「一张表里混着密钥与普通配置」这种形态（sys_configs）也能按行纳入，而不是把平台名称一起加密掉
- **顺手修掉一处真实泄露**：配置列表接口以前把 SMTP 口令原文回传给前端，任何能打开配置页的人都能
  从响应里读到。现在密钥类配置项只回 `hasValue`，提交空串表示「不修改」，前端按密码框渲染
- **解密统一放在读取漏斗上**（`ldapTarget` / `jenkinsRequest` / `openUpstream` / `openChannel` /
  `requireMetricSource` / `requireLogSource` / `requireTraceSource` / `configSecret`）。
  这么做安全的前提是 `cryptox.Open` 对没有前缀的值原样返回 —— 多解一次不会坏，
  所以「新建后立刻探活」这种拿着刚落库密文的路径也能安全地再解一次
- **解不开一律报错并点名字段**，绝不拿空值去连。LDAP 这条尤其要紧：空口令在多数目录上是匿名 bind，
  表现成「连上了但搜不到人」，比直接失败更难查
- **刻意留了两项没动**：`users.totp_secret`（动它就动了登录路径，迁移中途出错会让所有绑过 2FA 的人
  一起登不进来，要连备用码与解绑兜底一起单独做一轮）、`alert_sources.token`（是给别人推送用的令牌，
  界面上必须能看原文复制，加密了也得解回来展示）。体检页照实标成「尚未纳入」

验证 72 项全过。这一轮的做法是**给每个外部系统起一个真的服务端，并且让它真的校验凭据**：
Jenkins 侧比对 Basic Auth、模型上游比对 `Bearer`、三个数据源比对请求头、钉钉机器人**重算 HMAC 验签**、
SMTP 走真实 `AUTH PLAIN`、企业微信按真协议用 corpsecret 换 token 再读部门。
LDAP 更进一步：在 WSL 里跑了一个**真的 slapd**（非 root、1389 端口、mdb 后端、灌了一条 inetOrgPerson），
所以「密文服务账号口令能真的 bind 上目录并搜到人」是真机证据，错口令那次 slapd 回的是 `invalid credentials`。
每条链路都按「落库即密文 → 对端认这个值 → 留空改其它字段后仍然认 → 换成错值对端会拒」四步走，
第四步是为了证明不是「对端谁都认」造成的假通过。迁移路径也验了：把 4 列改回明文 → 体检数出 4 行 →
明文照旧可用 → 迁移重写 4 行 → 对端仍然认 → 再迁移重写 0 行；`platform.name` 没被 sys_configs 的迁移误伤。
UI 15 项覆盖体检卡片的新增行与配置页的口令字段（密码框、不回填、占位文案说明留空语义）。

**没验到的**：IM 那条用的是本地按企业微信协议实现的服务端，不是真的 qyapi.weixin.qq.com；
Jenkins / Prometheus / Loki / Jaeger / SMTP 同理 —— 它们真在校验凭据、也真在网络上，但不是那几个真产品。
（云账号 AK/SK 当时还**没有任何消费方**，只有「落库即密文 + 反复留空编辑不会被二次包裹」两条证据；
这一条已经在下面的「云资源同步」一轮里补上了：密文解回来真的打到了 ecs.cn-hangzhou.aliyuncs.com。）


## 已落地：换密钥 / 取消加密（加密不再是单向路）

之前 `OPS_SECRET_KEY` 是一条**单向路**：设过之后既不能换、也不能退回明文，改一下环境变量就等于
把库里所有凭据作废。文档只能写「设好就不要再改」—— 那是把一个功能缺口说成了纪律要求。
这一轮补上 `POST /api/v1/secrets/rekey`，两种模式：换成另一把密钥、或者**解回明文**。

几个决定：

- **「不加密存储」是被支持的选择，不是缺省的失败态**。内网自用、不想额外保管一把密钥的部署，
  留空 `OPS_SECRET_KEY` 就行；体检卡片把当前状态写成「不加密存储」并说清代价，
  但不用安全顾虑去堵它（也不再把明文行当成必须消灭的告警）
- **先备份，备份失败就不动数据**。值不变，但这是唯一能把人从「新旧密钥各一半」里救回来的东西
- **解不开的行原样留着并计为失败**。把它覆盖成空值，会让「密钥填错」变成「凭据被清空」的
  不可逆事故 —— 单测专门盯这一条（拿另一把密钥造一行，断言它原封不动、且提示里点明有行解不开）
- **进程内的密钥热切换**（`cryptox.Box` 的密钥改放 `atomic.Pointer`）。否则「库里换完了、进程还拿着旧的」
  这段时间里所有凭据都用不了，只能靠人立刻重启去补 —— 那是半截功能。并发读写有单测覆盖
- **改不了环境变量这件事要说出来**：接口返回里明确要求把 `OPS_SECRET_KEY` 同步改成新值（或删掉），
  不改就重启会用回旧设置。启动时若发现「库里有密文但进程没密钥」，日志直接点出来、给出修复路径，
  而不是等有人点「连接主机」时才报单条记录的错

验证 29 项，按四个阶段跑，每次重启都换一种环境变量，验的就是「重启之后还认不认」：
1. 带原密钥 → `mode=plain` 解回明文：12 行密文全部重写、备份文件生成、**不重启**就能连主机与集群
2. **不带 `OPS_SECRET_KEY` 重启** → 主机仍在线、两个 k3s 集群仍 healthy、体检标注「不加密存储」
   —— 这一条就是「允许不加密存储」的真机证据
3. `mode=encrypt` 换成 `demo`：16 行明文全部加密，**不重启**主机与集群照常可用（热切换生效）
4. 带 `OPS_SECRET_KEY=demo` 重启 → 一切正常、体检 plainTotal=0

## 已落地：安全意识 + 特征库（500 段最后两个占位没了），demo 作为演示默认密钥

500 段的两个 `/placeholder/index` 终于换成真页面。这两个模块都容易做成「纯表单」，所以各自定了一条硬规矩。

### 安全意识 `/security/awareness`

规矩：**只做能被查证的三件事** —— 谁读了、谁答对了、谁到期还没做。

- 确认已读是签署记录（人 + 时间 + 来源 IP），不是前端勾选框
- 题目的正确答案带 `json:"-"`，**绝不下发到浏览器**，判分只在后端。否则「考核」就是把答案先发过去再问一遍
- 发布会真的给范围内每个启用账号建待办 + 投站内消息；逾期由 `OPS_AWARENESS_SPEC`（默认每天 09:00）
  再催一次，同一项一天只提醒一次
- 记录是凭据：有人留下记录的项目不允许删除、下线只影响列表不影响记录、已发布不允许改必修范围
- **刻意不做**「没做完就禁止登录」：那会把提醒问题变成可用性事故。逾期的效果是被催办、在明细里被点名

### 特征库 `/security/features`

规矩：**特征必须能落到一个真在跑的检测点上**，不收只能看的模式表。

- `command` 类应用后在命令规则里生成 / 维护一条规则 —— 那张表是下发闸门与 Web 终端真正在用的
- 灰度就落在动作上：observe → `warn`（只提醒）、enforce → `block`（真拦）。没有第二套并行拦截逻辑
- 命令规则会被人手工改：所以给 unapplied / applied / **drift** / **missing** 四种对账状态并能一键重写，
  而不是显示一个永远绿着的「已应用」
- `port` 类**不改暴露面基线**（那是人的决定），只拿真机 TCP 探测结果核对，并指出哪些命中端口不在基线里；
  从没扫过的目标如实列出、不算通过
- 内置 12 条特征，其中 7 条直接挂在内置命令规则上 —— 一打开就是「已生效」的真实状态

### demo 成为演示默认密钥

`OPS_SECRET_KEY` 之前默认空（= 不加密）。改成默认 `demo` 之后：带演示数据的库文件开箱可用，
而「不加密」有了显式说法 `OPS_SECRET_KEY=off`（也接受 none / plain / disabled）。
`demo` 写在仓库里等于公开，所以 **prod 模式带着它启动会被直接拒绝**，与 JWT 密钥、admin 初始口令同一处理。

这一页本来很容易做成一个误导人的页面，因为「已分配」和「实际用量」是两件事：
调度器看 requests，OOM 看实际用量。只给其中一个、或把两者混在一栏里，
都会让人得出错误结论（「用量才 20%，为什么调度不上去」）。所以两个都给、分栏摆。

几条口径写在页面上，因为它们决定了数字对不对：

- **已结束（Succeeded / Failed）的 Pod 不计入**：它们还在 API 里，但资源早就还回去了
- **init 容器按「单个最大值」与普通容器之和取较大者**，与调度器规则一致。这条算错会让
  统计值偏大、让人以为节点比实际更满 —— 真集群验证时正好能对账：k8s 的 ResourceQuota
  自己就是按这个规则算 used 的，拿它当标准答案，平台算出的 1100m / 576Mi 与集群完全一致
- **占比分母用 allocatable 而不是总容量**：调度看的是可分配量（k3s 这台机器 8Gi 容量、
  7Gi 可分配，分母选错就能差出一截）
- **没配 limits 的 Pod 单独计数**：它们能把节点吃满，是容量事故的常见来源
- **命名空间筛选只影响命名空间表**，节点账本始终是全集群的 ——
  按命名空间过滤过的「节点已分配量」是个会让人做出错误判断的数字
- **metrics-server 不在时「实际用量」显示「未知」而不是 0**，并说明原因。
  本轮验证用的 k3s 恰好没装 metrics-server，所以真集群跑的是降级路径；
  metrics 可用时的分支由单测覆盖（mock 掉 metrics API，断言用量与已分配各算各的）

验证：单测 8 组（CPU/内存量的两套后缀、格式化、调度规则、已结束 Pod、配额占比按资源类型、
两种 metrics 状态下的汇总），真集群 28 项断言全过，CDP 15 项全过。
CDP 还抓到一个真 bug：没有配额的命名空间后端返回 `null`，前端一次 `map` 就把整张配额表打空了

## 已落地：Pod 结构化详情与按容器看日志

上一轮的资源详情只有 YAML，排查「这个容器为什么挂」还得自己在 spec 与 status 之间来回找。
这一轮把 Pod 单独做成结构化视图（`internal/k8s/pod.go` 的 `DescribePod`，纯函数、不发请求）。

两个决定：

- **只算不编**：字段取不到就留空，界面显示「—」。QoS 直接取 `status.qosClass` 而不是自己按
  requests/limits 推算 —— 推算规则很容易实现得和集群不一致，那种「看起来对」的字段最难排查
- **把最难找的那条摆到前面**：CrashLoopBackOff 时当前状态只会说「在等下一次重启」，

  「上次退出」。另外 requests/limits/探针没配时显示「未配」而不是留白 ——
  没配 limits 决定了 QoS 与被驱逐的顺序，这是事实不是缺省

另外补了两处下钻的连贯性：spec 里有但 status 里还没有的容器照样出现在列表里
（否则「少了一个容器」会变成新的疑问）；从工作负载的「关联 Pod」能直接点进 Pod 详情，
不用退回列表重选类型。

## Round 9 — 主机服务（2026-09-22）

**做了什么**
- 新增 HostService / HostServiceAction 两张表。平台库不全量存机器上的几百个 unit（那是噪音），只存人纳管的那几个 + 期望态；没纳管的通过「发现服务」实时列出，不落库
- 期望态三件事：该不该在跑（ExpectActive）、该不该开机自启（ExpectEnabled）、是不是关键服务（Critical）
- 漂移判定六态：ok / inactive 该跑没跑 / unexpected 该停在跑 / disabled 该自启没自启 / missing unit 不存在 / error 巡检失败。static / indirect / generated 这类本来不能 enable 的 unit 不算漂移；自启状态没采到（空值）也不算漂移
- 漂移产告警走既有通道（内部告警源「服务巡检」），关键服务是 critical 级，恢复后发 resolved
- 端口归属走 /proc/<pid>/cgroup 而不是 MainPID：nginx 这类 master/worker 模型下监听套接字由 worker 持有，只看 MainPID 会漏
- 归不到任何 systemd service 的监听端口单列为「无归属端口」——手工起的进程、脱管容器、别人偷偷跑的东西
- 采集需要的 sudo：ss -p 要看别人家的进程必须 root。非 root 账号下自动加 sudo -n（service.sudo 配置项），sudo 不可用时退回不带 sudo 再采一次，并如实报出「读到端口但拿不到归属」
- 启停六动作 start / stop / restart / reload / enable / disable，全部走 RunOnHosts，自动继承命令规则拦截、生产主机二次确认、拦截留痕
- 关键服务的 stop / restart / disable 要把 unit 名抄一遍才放行；被拒的尝试也写进留痕（「谁想停这个关键服务」本身就是要留的信息）
- 每次启停前后各读一次真机状态存进留痕——光记「执行了 restart」回答不了「到底起来了没有」
- 改期望态会用上次采到的实际态立刻重判漂移，不重新连机器（改个备注不该触发 SSH）
- 采集失败时不清空实际态字段，保留上次真值并标 error——把状态清空会让人以为「服务停了」
- 定时巡检 OPS_SERVICE_SPEC（默认每 10 分钟），体检页新增「主机服务巡检」项

- 端口归属依赖 /proc/<pid>/cgroup：容器内进程、老内核读不到 cgroup 的会缺端口，UI 会标明
- 没有 root 也没有免密 sudo 时，端口拿不到进程归属，界面会明确提示原因而不是把端口列留空
- 服务的启停超时固定 60 秒，重启很慢的服务（大数据库）可能超时；超时后留痕里 afterState 仍会去读一次真机状态
- 采集是「每次巡检全量读一遍」，没有做增量；一台机器 254 个 unit 的采集实测在 20 秒超时内
- 没做服务之间的依赖关系（systemd 的 Requires/After 没读）


## Round 10 — 配置文件（2026-09-22）

**做了什么**
- 新增 ConfigFile / ConfigVersion / ConfigApply 三张表。ConfigVersion 存内容原文（与防火墙快照同一理由：解析器会变，原文不会），只追加不修改，它是回滚的唯一依据
- 基线从真机抓：登记时默认抓一份当 v1，并把这次抓取写进留痕（基线是谁在什么时候从哪台机器抓的，必须答得出来）
- 巡检：SFTP 现读 → sha256 对比基线 → 八种判定（ok / drift 内容不一致 / missing 文件不存在 / no-desired 还没定基线 / too-large 超出可管大小 / binary 不是文本 / error 读取失败 / unknown 未巡检）
- 漂移产告警走既有通道（内部告警源「配置巡检」），关键配置是 critical 级，恢复后发 resolved
- diff：基线 vs 真机现读，或任意两版之间；长段相同内容折叠，给出差异行数
- 平台上编辑新版本：只存版本不碰机器，先看 diff 再决定下发。编辑与下发刻意分成两步
- 下发六步不可调换：现读真机 → 存成 pre-apply 版本（回滚点）→ SFTP 写临时文件 → RunOnHosts 做「备份 .bak + chmod --reference 保权限 + mv 原子替换」→ 回读校验 hash → 可选 reload。读不到真机现状就拒绝下发（没有回滚点不动机器）
- 远端也留一份 .bak 备份：平台挂了人还能自己在机器上拷回去
- sudo 由远端 shell 自己判断：目标文件（或其目录）当前账号写得进去就不用 sudo。平台侧猜不准——/home 下不需要 root，/etc 下需要
- 临时文件优先写目标同目录（同文件系统 mv 才原子）；写不进去退到 /tmp，并在留痕与响应里如实标注「替换非原子」
- 回滚到任意历史版本，默认把该版设为新基线（否则回滚完机器和基线又不一致，下次巡检立刻报漂移）
- reload 钩子：登记「改完要 reload 哪个 unit」，下发后自动执行并如实报结果。reload 用 reload-or-restart（不支持 reload 的 unit 退回 restart，比失败后什么都没发生好）。reload 失败会弹窗明说「配置已落地但还没生效」
- 关键配置的下发/回滚要把路径抄一遍确认，被拒的尝试也写进留痕
- 幂等：真机内容已与目标一致时直接返回 changed=false，不碰文件
- 下发过的文件不给直接删（会连历史版本一起丢，之后无法回滚），要带 force=1
- 定时巡检 OPS_CONFIG_SPEC（默认每 30 分钟），体检页新增「配置文件巡检」项

- 只管文本文件，含 NUL 字节的一律拒绝

## Round 11 — 监控设置 / 事件 SLA（2026-09-22）

**做了什么**
- 新增「监控设置」页（菜单 440，`/monitor/sla-settings`，维护权限 `sla:manage`）：按事件级别（紧急 / 警告 / 提示）分别设响应 SLA 与恢复 SLA 目标（分钟），另有临期提前量（分钟）与重复提醒间隔（小时）。默认响应 15/60/480 分钟、恢复 60/240/1440 分钟、临期提前量 5 分钟、重复提醒间隔 4 小时
- 8 个配置项落在 sys_configs 的新 `monitor` 分组，系统配置页也能改 —— 同一批行、两个入口，不是两套数据
- 响应 SLA 从「事件建单时间」开始算。平台无法知道故障真正开始于几点（那是事件复盘里人填的），所以只承诺「从平台上有这张单开始算」
- 响应时间的落点只认两件事：状态离开「待处理」（接手 / 直接解决 / 判定关闭），或写下第一条处置记录。**指派不算响应** —— 否则值班的人可以靠互相转单把响应 SLA 刷成全绿
- 恢复 SLA 从建单算到状态变成「已解决」；标记「已关闭」（判定无需处理）的事件不计 SLA。目标填 0 表示这一级不设 SLA
- 列表筛选与看板统计只算「还没做到且已超时 / 临期」的单子；历史上超时但已经做完的不在这里记账（那是事件复盘看耗时的口径）
- SLA 不落库：每次输出按当前时间重新算；前端用后端给的绝对「到点时间」自己走倒计时，页面不刷新也准
- 事件列表新增 SLA 列（响应 / 恢复两个 tag，带实时倒计时）、SLA 筛选（已超时 / 临期）、快筛 chips「SLA 已超时」「SLA 临期」；事件详情新增「响应 SLA / 恢复 SLA」两行；事件统计接口新增 slaBreached / slaRisk
- SLA 筛选是翻成 SQL 在分页之前执行的，不是查出来再过滤
- 新增定时任务 OPS_SLA_SPEC（默认 `*/2 * * * *`）扫未完结事件，对临期 / 超时的给负责人发站内消息（没有负责人就退回建单人）；两条 SLA 各自独立提醒、各自记上次提醒时间，重复提醒间隔内不再发；找不到可提醒的人时仍在事件时间线留痕并说明原因。时间线新增 `sla` 类型记录，体检页新增「事件 SLA 扫描」固定任务项
- events 表新增 responded_at / sla_respond_alerted_at / sla_recover_alerted_at
- 启动时一次性回填存量事件的 responded_at：从只追加的事件时间线里取最早一条 status / note 记录；连时间线都没有的已解决事件退一步用解决时间。目的是避免存量单子在新界面上被凭空判成「响应已超时」。回填只跑一次，靠内置配置键 `migration.event_responded_backfilled` 记住
- 顺手统一了一处会打脸的口径：事件复盘的「开始响应」建议值原来在没有告警确认记录时**退到事件指派时间**，这跟本轮「指派不算响应」直接矛盾（同一个词两套算法，复盘算出来的 MTTA 会比 SLA 宽一截）。现在改成退到 `events.responded_at`，两处都没有就退到建单时间并如实说明「没人在这张单上动过手」。Round 7 的 `EventReview.RespondedAt` 字段注释同步改了，新增一个专门盯这件事的单测


**已验证**

- 可证伪的几条：指派后响应时间仍为空；写处置记录后响应时钟停住（6 秒后已用时长不变）；响应与恢复各自独立提醒且重复间隔内不重发；目标填 0 后该级不计 SLA 也不给到点时间；已关闭事件恢复 SLA 不计；已解决的单子不再进超时筛选

## Round 12 — 安全事件与研判台（2026-09-22）

**做了什么**
- 新增「安全事件」页（菜单 517，`/security/events`，研判与处置权限 `secevent:manage`、生成封禁草稿权限 `secevent:respond`）。它是个研判台：把平台**已经在产生**的安全类流水汇聚成可研判的「安全事件」，带源地址 / 目标 / 协议 / 证据摘要 / 命中次数
- 新增 `security_events` / `security_event_logs`（只追加的处置链路，action = collect / status / note / respond / rehit）/ `security_event_mutes` 三张表
- 四个采集来源，全部来自平台已有的只追加流水表，界面上**不提供手工新建事件**：
  - `exec-guard` — 下发闸门拦下的高危命令（`exec_guard_logs`，只取 `action=block`）
  - `terminal` — Web 终端里被拦下的命令（`session_commands.risk=blocked`，join `sessions` 拿客户端 IP / 目标地址 / 登录账号）
  - `exposure` — 真机 TCP 探测到的未登记开放端口（`exposure_scans.unexpected`，一个端口一条事件）
  - `authz` — 越权被拒的写操作（`audit_logs.status=403`）
- **只取 `exec_guard_logs` 里 `action=block` 的行**。`status=blocked` 还包含「目标里有生产主机需要二次确认」这种流程拦截，那是工作流保护不是安全事件，混进来会把研判台变成噪音场
- 指纹只认「谁 / 从哪 / 对谁 / 干了什么」（source + actor + actorIP + target + port + 业务键），**不含时间与原始流水 ID**。不去重的研判台第二天就没人看了
- **结案之后又命中**单独计一列 `hits_after_close`：采集器**不会**把状态改回待研判（那是人的判断），但会在处置链路上写一条 rehit，列表可以一键筛出来、排序默认把它顶到最前。「结案了还在响」要么是判错了、要么是攻击还在继续，这个信号不能被「已处置」这个状态盖掉
- 判为「误报 / 忽略 / 已处置」这三种让线索从值班视野里消失的状态时**必须写结论**，后端强校验
- 判误报时同时把指纹加入**误报白名单**，之后采集器直接跳过；但跳过不等于装作没发生 —— 挡掉的次数照记，界面按挡掉次数倒序排（挡得异常多通常说明当初判错了）。撤销白名单会把对应事件拉回待研判，并在链路上写明期间挡掉了多少次
- 采集游标按**原始流水的自增 ID** 推进（落在 `sys_configs` 的 `security.cursor_*`），不用时间戳水位：这四张表都是只追加 + 自增主键，按 ID 推进不会因为时钟回拨或同一秒内多行而漏采或重采。单来源单次最多消费 500 行
- **特征库 port 类特征第一次有了持久化的消费方**：未登记开放端口命中启用中的 port 特征时，事件级别按特征的 high / medium / low 提升，并把命中的特征名写进证据。在此之前 port 特征只能靠人点「按扫描结果核对」看一眼，结果一个字节都不落库
- 「封禁源地址」只生成**防火墙规则草稿**（Origin=platform / State=pending / Lifecycle=temporary / 7 天后到期 / action=drop / direction=in），**刻意不下发**：下发要走防火墙自己的 `firewall:apply` 与下发闸门（命令规则复检、生产主机二次确认、拦截留痕）。研判台如果能直接改真机规则，一个误判就能把自己的运维通道封掉
- 封禁必须带端口：底层规则模型（iptables / ufw / firewalld 三家共有的那部分表达）要求 tcp 规则必须带端口，做不出「封这个地址的所有端口」。端口优先用人填的，其次用事件自己的端口，ssh 类事件默认 22，都推不出来就报错要求明确填，不替人猜
- 批量研判是平台**第一个真正的后端批量接口**（`{ids: []uint}`，单次上限 200）。此前平台的「批量」都是前端循环调单条接口
- 新增定时任务 `OPS_SECEVENT_SPEC`（默认 `*/5 * * * *`），只读本地库、不连主机、不执行任何命令；平台健康页新增「安全事件采集」固定任务项
- **刻意没有的来源**：登录失败爆破。审计中间件只挂在鉴权后的路由组上，登录接口在公开路由上，所以平台**从来没有记录过一次失败登录** —— 这是诚实的空白，界面上不假装覆盖了。同理，审计中间件跳过 GET，所以读接口的越权尝试也查不到

  - 转「研判中」不强制填结论，但 updates 里无条件写 `verdict`，会把之前写好的研判结论清空
  - 存在性判断用 `len(events) != len(req.IDs)`，ids 里有重复值（详情页按钮 + 列表勾选指向同一条）时整批被误判成「有事件不存在」；改成先去重、报错点名具体缺哪几个 ID
  - cron 与手动「立即采集」两条路径调同一段「读游标 → 消费 → 写游标」，无任何互斥：并发跑会重复消费同一批流水、游标互相覆盖。加 `sync.Mutex` + TryLock，第二个调用直接返回「上一次采集还在跑」而不是排队（排队只会把同一批再消费一遍），前端按钮也加了 loading 防连点
  - `hit_count` / `hits_after_close` / 白名单 `hit_count` 都是 Go 侧读出来加一，并发会丢更新，而这三个数正是列表排序与「是不是当初判错了」的依据；改成 `gorm.Expr("... + 1")` 原子自增
  - 落库失败时只打日志却照样推进游标，那条线索就永久丢了（游标只前进，流水表只追加）。改成 `upsertSecCandidate` 返回 error，出错就把游标停在该行之前等下轮重试；查询存在性也改用 `errors.Is(gorm.ErrRecordNotFound)` 区分「没找到」与「查库出错」
  - 顺带按复用建议把自造的 sha1 指纹换成仓库已有的 `internalAlertFingerprint`
  - 复核里被标成「Critical」的前端格式项（分号、对象花括号内空格、尾逗号、每行属性数）是通用 JS 规则集与本仓库既有风格的冲突，**没有采纳** —— 全仓 100 多个文件都是这个写法，只改新文件反而破坏一致性


**未验证 / 已知局限**
- `terminal` 采集器在这套库里**没有真实数据**（没有被拦下的终端命令），所以只有单元测试覆盖；它的 join 写法照抄自生产在用的 `session_search.go`
- 没有登录失败 / 爆破来源（平台不记失败登录），也没有读接口的越权来源（审计跳 GET）
- 没有流量类来源（平台不采流量），所以做不出参考站那种「阻断包数」看板
- 安全事件**没有删除接口**：让噪音消失的正规路径是「忽略」或「误报 + 白名单」，不是删记录
- 也**没有进数据留存清理**（按指纹去重后增长很慢，原始流水各自已有保留天数；但 `ref_table` / `ref_id` 指向的原始行被留存清理删掉后会变成悬空引用）
- 封禁草稿不自动下发，也不做「封禁后自动解封」—— 临时规则 7 天到期是唯一的自动收口
- 研判没有多级审批、没有「派发给外部系统」


## 已落地：云资源同步 —— 存了十几轮的 AK/SK 终于有了消费方

云账号页从第一版起就存着 AK/SK，上几轮还给它加了密，但平台里**没有任何地方用过它**。
这是典型的「能存不能用」：保护一份没人消费的数据，加密体检表上那一行看着很像回事，
实际证据只有「落库即密文」，连「这把钥匙是不是还有效」都答不出来。这一轮把链路接通。

**为什么不用官方 SDK**：阿里云一个产品一个模块，装完几十兆依赖，还把「构建时能出网拉依赖」
变成前置条件。我们只要几个 `Describe`，RPC 风格签名算法本身二十行 —— `internal/cloudapi`
只用标准库实现，`go.mod` 一个新依赖都没加。这个包里**没有 Create/Delete/Modify**，
平台拿着 AK/SK 也只能读；云上资源的变更不从这里走，这是结构上的保证，不是约定。

覆盖：ECS `DescribeInstances`（2014-05-26）、云解析 `DescribeDomains`（2015-01-09），都自动翻页
（每页 100，50 页保护上限，防止接口返回固定 TotalCount 时无限翻）。

几个刻意的决定：

- **云上消失的资源标 `Gone` 而不是删**。「那台机器什么时候不见的、谁释放的」是对账时最需要的线索，
  删掉就永远查不回来了。清单默认仍显示它，标成「云上已消失」。
- **ECS 同步必须指定地域**。地域为空直接失败而不是静默查默认地域 —— 后者会让「云上有、平台没有」
  的对照凭空少一批机器，比报错危险得多。
- **`ExpiredTime` 空串必须解析成 `nil`，不能是零值时间**。`time.Time{}` 落到「到期时间」上
  会被当成 1970 年到期，在页面上变成一条假的到期告警。按量付费实例和域名本来就没有到期时间，
  页面上分别显示「按量付费」和「接口不提供」，不留空格让人以为是漏采。
- **漂移的 `hostOnly` 只在成功同步过 ECS 之后才统计**。从没同步过就把全部主机列成「云上没有」
  是纯噪音——那时候云上清单本来就是空的。即使同步过，这一栏里也可能是自建机房或别家云的机器，
  页面上照实标注，不假装它们都是漂移。
- **纳管为主机时凭据必须人填**。云 API 拿不到主机口令；自动建一台连不上的主机，
  等于往资产表里放假数据。校验规则直接复用 `CreateHost` 的那一套（引用凭证库 or 自带凭据二选一）。
- **默认不自动同步**（`OPS_CLOUD_SYNC_SPEC` 留空，与其它十七个固定任务相反）。这一项会真的出网，
  默认就开等于替用户决定了「这台机器可以访问公网、也愿意消耗云 API 配额」。
- **失败也落一条同步记录**。清单页上的数字如果来自三天前一次失败后的残留，没有这张表根本看不出来。
  认证失败单独识别（`InvalidAccessKeyId.NotFound` / `SignatureDoesNotMatch` 等），
  提示是「去改云账号」而不是「重试」。

**验证**：`internal/cloudapi` 10 条 + `internal/handler` 10 条单测全绿。签名实现拿**阿里云文档里
那个示例请求**对过（`testid`/`testsecret`/`DescribeRegions` → `OLeaidS1JvxuMvnyHOwuJ+uX5qY=`），
这是外部基准而不是拿自己的实现验自己；httptest 桩会按规则重算签名后才返回数据，
另有一条用错密钥的用例证明桩真的在验签、前面那些「成功」不是因为桩没检查。

**真打到了云上**：起一个后端、登记一个假 AK（`LTAI5tFAKEKEYFORSMOKE`）、点同步，
阿里云返回 `InvalidAccessKeyId.NotFound`。也就是说请求真的出网到了 `ecs.cn-hangzhou.aliyuncs.com`、
被网关正常解析了公共参数，只是这把钥匙不存在——签名与传输链路是通的，
只差一副真钥匙才能看到真实例。上一轮「云账号 AK/SK 没有消费方」那条诚实空白到此补上。

**仍然没有的**：域名的**注册**到期时间（云解析接口是「DNS 托管」视角，给不出注册到期，
需要 `domain.aliyuncs.com` 的域名注册 API）、DNS 记录的增删改（同样需要写接口，而这个包不做写）、
云账单（另一套账单 API）、腾讯云 / 华为云 / AWS（各家签名方式不同，逐家接）。


## 已落地：域名管理 —— 台账 + 真去查一次 DNS

上一轮把云上的托管域名拉回来了，但那只是「有哪些域名」。运维真正关心的两件事它都答不了：
**解析有没有被人改过**、**域名什么时候到期**。这一轮补上，并且两件事**分开判断、分开告警** ——
「解析被改了」和「忘续费了」是完全不同的两类问题，混成一个状态就没法分别处理。

`internal/dnsx` 是这一轮的新包：带 context 超时、三类记录并发查、可指定 DNS 服务器，只用标准库
（不引 `miekg/dns`）。仓库里此前只有一处裸 `net.LookupHost`（`handler/exposure.go`），
超时完全靠系统 resolver 的默认值 —— 那在「批量核对几十个域名」的场景里会把一轮巡检拖成几十秒。

**为什么要能指定 DNS 服务器**：内网 DNS 经常把生产域名覆写到测试地址。用它核对出来的是内网视角，
跟外部用户看到的不是一回事。`OPS_DNS_SERVER` 指一个公共 DNS 就能核对「外面看到的解析」，
而且界面上会回显每次实际用的是哪台 —— 否则「为什么和我 dig 的不一样」会变成一个查不清的问题。

几个刻意的决定：

- **期望值留空 = 不核对那一类**。不填就判漂移，等于每条域名一上来都是红的，那种告警没人会看。
- **三类都没填时状态是 `nocheck` 而不是 `ok`**。「没检查」和「检查通过」在值班视角里完全不是一回事，
  不能共用一个绿色。概览里「未设期望」单独一栏。
- **只有 NS、没有 A 记录不判异常**。那是很多域名的正常形态（没做网站的、只用来发邮件的）。
  只有「A/CNAME/NS 一条都查不到」才判 `unresolved`。
- **每类记录各自记错误**。NS 查不到不该让已经对上的 A 记录作废，但也不能默默吞掉 ——
  对上了就是 `ok`，NS 的查询错误以附注的形式挂在结论后面。实测里就撞上了这种情况：
  某次 `example.com` 的 NS 查到了、A 记录超时，结论如实写成「NS 少了…（A/AAAA 查询: 解析超时）」。
  也因为这次实测把默认超时从 5s 提到 8s，与证书探测对齐。
- **注册到期日只能人工登记**，为空时状态是 `unknown`（界面显示「待补到期日」）而不是 `valid`。
  没登记不等于还很久 —— 那正是最容易忘续费的一批。`unknown` 不产生告警（那是台账没补全，不是域名出事），
  但会在概览里单独数出来催人补。
- **填上到期日立刻重算状态**，不等下一轮巡检。否则「刚把到期日填上、列表里还显示待补」看着像没保存成功。
- **删台账要把它名下的三类告警一并 resolved**，不然值班列表里会留一条点不进去的告警。
- **证书关联是算出来的，不落外键**：按 `Certificate.DNSNames`（SAN）反查，支持精确、子域与通配符
  （`*.example.com` 覆盖 `example.com`），证书增删改后下一轮巡检自然更新。

**顺手挖出并修掉的一个坑**（值得单独记一笔）：`AlertEnabled bool` 如果带 gorm `default:true`，
GORM 会把零值（false）从 INSERT 里省掉、让数据库填默认值 —— 于是**用户在表单里把告警开关关掉，
落库之后又被翻回「开」**，而界面上完全看不出来。`Select("*")` 不解决这个问题；
正解是去掉 `default` 标签、默认值由 handler 显式给。单测刻意走 HTTP 接口而不是直接 `Create`，
否则就绕过了真实写入路径、测不到这个坑。**同类写法在 `Certificate.AlertEnabled`、
`CloudAccount.Enabled` 等处仍然存在**，属于既有问题，这一轮没动。

**验证**：`internal/dnsx` 8 条 + `internal/handler` 11 条单测全绿。`dnsx` 的解析用例走真实解析路径
但不需要联网（拿 `localhost` 与保留 TLD `.invalid` 当目标），另有一条指向死掉的 DNS 服务器的用例
证明超时真的生效、三类记录真的是并发查的（总耗时接近单次超时而不是三倍）。

**真去查了公网 DNS**：起一个后端登记两条域名，一条期望值故意填错、一条填对。
`iana.org` 查到真实的 `192.0.43.8` 与 `a/b/c.iana-servers.net`、`ns.icann.org`，
期望填 `203.0.113.1` 时结论是「解析地址 少了 203.0.113.1，多了 192.0.43.8」并产生一条 critical 告警；
把期望改成实测到的地址再巡检一次 → 状态变 `ok`、那条告警变 `resolved`。
`example.com` 则暴露出一个真实变化：它的 NS 现在在 Cloudflare 上，不是记忆里的 iana-servers ——
核对逻辑如实把这当成漂移报了出来，这正是它该做的事。

**仍然没有的**：DNS 记录的增删改（要注册商/解析商的写接口）、WHOIS 查询、自动续费、
注册到期日的自动获取。这几项都明确写在页面提示里，不留想象空间。


## 已落地：主机日志 —— 没有 Loki 也能看日志

`/monitor/logs` 是个纯 Loki 代理：没部署 Loki 的环境里，那一页点开只有一个空工具栏。
「日志」这件事对运维的重要程度显然不该取决于有没有装某个组件。这一轮补一条完全不依赖
日志系统的路：**直接 SSH 在主机上读文件**。

三件事，都是只读命令（`tail` / `grep` / `du` / `find` / `wc` / `ls -i`），
整个模块里**没有一处会改主机上的东西**：

1. **实时查看** —— 看末尾 N 行，或用关键字 grep。不落库。
2. **关键字巡检** —— 登记「哪台主机上的哪个文件 + 哪些关键字」，定时增量扫，命中就告警。
3. **日志目录占用** —— 总占用 + 最大的几个文件。磁盘被日志写满是最常见的一类故障，
   而它在「主机指标」里只表现为根分区使用率上升，看不出是谁写的。

几个刻意的决定：

- **路径白名单是唯一真正的安全边界**。路径由人在界面上填，没有 `OPS_LOG_PATH_PREFIXES`
  （默认 `/var/log`）这道限制，有这个页面权限的人就能读主机上任意文件 —— 包括 `/etc/shadow`
  与主机私钥。校验顺序也要紧：`path.Clean` 必须发生在前缀判断**之前**，先判前缀再 Clean
  等于没判（`/var/log/../../etc/shadow` 会过）。
- **关键字是固定字符串、不是正则**。`grep` 固定加 `-F`，Go 侧也只做 `strings.Contains`。
  让人在界面上填正则，迟早会有一条灾难性回溯把巡检卡死在某台机器上。
- **输出必须在远端截断**。`sshx.Run` 对 stdout **没有任何大小限制**（stdout 直接进
  `bytes.Buffer`），一个 grep 撞上 GB 级日志就能把服务端内存吃掉。所以远端命令一律带
  `head -c`：查看 1MB、巡检每轮 256KB（可按目标配）。
- **增量按 inode + 字节偏移**，而不是「每次看最后 N 行」。后者会让同一条旧错误每轮都算命中，
  告警永远不会恢复。判定放在远端脚本里（把上次的 inode 与 offset 传过去，它自己决定要不要
  从头读），这样一次往返就够；放本地要先问一次 inode 再读，多一轮 SSH。
  轮转的两种形态都覆盖了：`inode` 变了（rm 后重建）、当前大小小于上次水位（truncate）。
- **首次巡检只记水位、不回溯历史**。一个跑了半年的 `/var/log/messages` 里成千上万条 ERROR
  不是「刚出的问题」，一上来就报只会让人把这个功能关掉。这是日志采集器的通用做法，界面上写明。
- **「读不到文件」也告警**。一个本该一直在写的日志突然消失或没权限读了，等于这个监控点已经瞎了；
  静默失败比没有监控更糟。同时把「命中」那条告警收掉 —— 读不到就没法再确认命中还在不在。
- **失败时不推水位、不清上次的样本**。一次 SSH 失败不该让「上次命中了什么」这条线索消失，
  也不该让下一轮把失败期间的日志当成新增内容漏掉。
- **平台不把日志内容搬进库**。监控点只留命中行数与命中的第一行样本（截断到 512 字节）。
  搬进来既贵又没人查，还会让日志的保留策略变成两处维护。
- **`find -printf` 是 GNU 扩展**，精简镜像与 BSD 用户空间没有。脚本先探一下，不支持就退回
  `du -a` 并在输出里标 `__OPS_FALLBACK__`，界面照实写「清单含目录，别照着它去删」——
  假装那是纯文件清单会让人删错东西。
- **只读巡检不走下发闸门**，与平台既有惯例一致（主机服务巡检、指标采集、连通性探测都不走）。
  但日志查看和那些固定模板命令有个本质差别：**路径与关键字来自用户输入**。所以这里仍然过一次
  `precheckScript`（成本极低、无副作用），`blocked` 直接拒、`warn` 如实带回界面显示。

**验证**：`internal/handler` 新增 17 条单测全绿。其中 4 条**把生成的 shell 脚本丢给真 Linux
shell（WSL2）跑了一遍** —— 这是这个模块最该被真实验证的一段，`tail -c +N` 的偏移语义、
`ls -i` 取 inode、轮转后归零、字节/KB 换算，任何一处写错表现都是「日志监控看着在跑但内容是错的」，
拿字符串比对根本查不出来。实测覆盖：首轮读全文 → 追加两行只读到新增两行 → 没有新内容时
正文为空但状态仍是 ok → `> file` truncate 后从头读 → `rm` 重建（inode 变）后从头读；
`grep` 无匹配时退出码 1 但脚本必须 `exit 0`；以及一条**真的注入尝试** ——
关键字填 `x'; touch /tmp/ops-pwned; #`，跑完断言那个文件不存在。
占用采集也在真 shell 上验了：造一个 200KB 的文件，Top 榜第一条就是它、大小约 200KB
（字节/KB 换算搞反的话这里会是 200 或 204800）。

**踩到并记下来的一个坑**：Windows 上 WSL 的 `bash.exe` 会把 `-c` 参数里的换行吃掉，
多行脚本被拼成一行之后 `f='/tmp' if [ ... ]` 变成了带前缀赋值的命令、`$f` 是空的 ——
表现成「/tmp 不存在」这种看不懂的失败。改成从 stdin 喂 `bash -s` 就好了。

**没验到的**：真实 SSH 链路上的端到端。冒烟时用一台假主机触发巡检，
SSH 确实打到了本机 sshd 并走到认证（`unable to authenticate`），说明传输链路是通的，
但没有可用凭据去完成一次真正的远端读取 —— 脚本本身已经在真 Linux shell 上逐条验过，
缺的是「这两段拼在一起」的最后一步。

**仍然没有的**：实时 `tail -f` 流（要长连接，真要盯日志更适合直接 ssh 上去）、
日志落库与全文检索、正则关键字、按标签/结构化字段过滤、多行日志（栈追踪）合并成一条。


## 已落地：安全响应的剩余三块 —— 原始数据、升格工单、学习建议

研判台上一轮做完之后还差三块：点不回原始流水、没有「派发」、没有安全概览。
这一轮补上，但其中两项的落法与参考站不一样，理由写在下面。

### 原始数据视图

事件上的证据摘要截断到 2000 字（命令原文常常更长），而 `RefTable`/`RefID` 在界面上
只是一行纯文本 —— 上一轮在 SECURITY.md 里把这记成了「悬空引用」的已知风险。
现在 `GET /security/events/:id/raw` 按来源 switch 到四张表取原始行，
拍平成「字段名 → 值」的有序列表。三个细节：

- **原始行没了不是错误**：绝大多数情况是被数据留存清理删掉了，如实说明并仍然返回证据摘要
  （那是采集那一刻抄下来的，还有用）。界面上一片空白比一句解释更让人困惑。
- **父表也可能没了**：`session_commands` 自己不带「谁在哪台机器上敲的」，那在 `sessions` 上。
  会话被清理时明说「查不到是谁敲的」，而不是留一片空白让人以为没人操作。
- **RefTable 仍然过白名单**：那个字段是平台自己写进去的，但拿它拼查询之前还是过一次
  `secSourceTables` —— 防的是「以后有人往这个字段写别的」。

### 升格为事件工单（这就是「派发」）

参考站有「派发记录」页。平台**没有对接任何外部工单 / SOAR 系统**，照着做一个
只会是一张永远空着的表。而事件中心是**已经在跑**的那套机制：负责人、处置时间线、
SLA 计时与超时提醒。所以「派发」在这里的诚实落法就是升格到它。

- 为此把 `createEvent` 拆出一个不碰 HTTP、**不要求必须关联告警**的内核 `newEvent`：
  安全事件的线索来自流水表，没有 alert，而原路径刻意强制「至少一条告警」。
  `Event.Origin` 新增第三个取值 `secevent`。
- **工单自动带 SLA**，不需要额外挂接 —— SLA 是按级别与时间戳实时算的。
  实测升格一条 critical 事件，工单的响应目标就是 15 分钟、状态 pending。
- 摘要把研判上下文一次性带过去（来源、首次/最近、命中次数、发起方、目标、原始流水位置、
  证据摘要），免得接手的人还得回研判台翻一遍。
- **状态联动**：升格同时把安全事件从「待研判」推进到「研判中」——
  建了单却还挂在待研判队列里，两边的计数都会不可信。已经是「已确认」的不动。
- **重复升格被拒**：同一条线索两张单，处置记录会分叉。

### 学习建议

三类，全部基于已有真实数据，而且**通过就真的去改配置**：

1. **端口基线** —— 数据源是 `security_events` 里 `source=exposure` 的行：采集器对每个端口
   单独建一条事件，`HitCount` 就是它被扫到的次数。用它而不是 `ExposureTarget.LastUnexpected`：
   后者只是最后一次扫描的快照，**推不出「反复」**。通过 = 把端口并进该目标的 `Baseline`，
   而且只 `Update` 基线一列 —— 不走 `UpdateExposureTarget`，那个接口是全量覆盖，
   批量应用时很容易把 name/ports/timeout 一起改没。
2. **误报白名单** —— 判了「忽略」却还在累加 `HitsAfterClose` 的指纹。「忽略」只改这条事件的
   状态，采集器该记还是记（这是刻意的），但如果它已经又响了很多次，说明判断是稳定的。
3. **特征提到拦截** —— `stage=observe` 但生成的命令规则已经 warn 过多次的 command 特征。
   通过 = 改阶段 **并** 复用特征库自己的 `writeSignatureRule` 重写规则为 block。
   这是三类里唯一有真实拦截后果的一个，前端单独二次确认。
   **阶段改了但规则重写失败必须报错而不是当成功** —— 那种状态是「页面说拦、实际还在放过」。

几条刻意的设计：

- **建议不落库，每次现算**。存下来就会过期：端口关掉了、特征撤下了，那条建议还挂着。
  只有「被拒绝过」这件事需要持久化 —— 否则那个按钮点了等于没点，下次刷新又冒出来。
- **应用时重算、不信前端传来的建议内容**。页面上那份可能已经过期，照它去改就是改错东西。
  Key 匹配不上就进 `failed` 并说「这条建议已经不成立了」。
- **复现少于 3 次的不进建议**。1 次不算规律，拿单次命中去劝人改基线是在制造噪音。

### 安全概览

只聚合，不产生任何新数据。最该被认真读的是最后一块 **gaps**：阻断包数 / 流量统计、
进程与连接明细、登录失败与爆破来源、读接口的越权尝试、外部威胁情报 ——
这五项平台**没有采集**，所以一个数字都不给。用 0 冒充「没有攻击」是最容易骗人的看板。

### 刻意没做：处置审批

参考站有这一页。这里不做，理由与 `docs/SECURITY.md` 第 8 节一贯的口径一致：平台定位是
内网自用、管理员自己对自己负责，研判台上一轮也已经写明「不做多级审批」。
加一层点「同意」的流程不会让处置更安全，只会让人绕过它。真正起作用的约束是别的：
封禁只出草稿、真机变更必须走 `firewall:apply` + 下发闸门、让线索消失的状态必须写结论。

**验证**：新增 13 条单测全绿（`go vet` / `vue-tsc` / `vite build` 干净），并且在**真后端上跑通了
完整一条链**：故意下发 `rm -rf /` → 闸门拦下并写流水 → 采集成安全事件 →
原始数据视图取回真实的命令原文与命中规则（`#1 rm\s+(-[a-zA-Z]*[rf][a-zA-Z]*\s+)+/\s*$`）→
升格出工单 #1（`origin=secevent`、`severity=critical`、`alertIds=[]`、响应 SLA 15 分钟 pending）→
安全事件状态推进到「研判中」并在处置链路留下 respond → 再次升格被拒 →
概览计数同步（待办 1、已升格 1、近 24h 下发被拦 1）。

**仍然没有的**：处置审批（上面说了为什么）、对外派发到工单 / SOAR 系统、
事件自动处置、按人/团队的处置绩效统计。


## 已落地：容器平台的三个专用页 —— Helm、自定义资源、RBAC 账户

通用「资源管理」页是按白名单 18 种类型的 YAML 浏览器。有三类东西它结构上答不了：

- **Helm release 藏在 Secret 里**，而 Secret 在平台上是脱敏只读的 —— 看得到有 `release` 这个键，
  看不到值，等于什么都没看到。
- **CRD 每个集群都不一样**，编译期的白名单列不出来。
- **「这个 ServiceAccount 能干什么」不是一个字段**，要反查 binding → role → rules。

这一轮补这三块，新增 `internal/k8s/discovery.go`（+ 11 条单测）与 `handler/kube_extra.go`（+ 9 条端到端测）。

### 一个结构上的障碍：ResourceKind 的 apiRoot 是未导出的

白名单表里每条 `ResourceKind` 都带一个小写的 `apiRoot` 字段，包外构造出来的 `ResourceKind`
那个字段是空串，路径会拼成 `/namespaces/x/foos` 这种查不到任何东西的形状。
所以先加了一个 `NewReadOnlyKind(apiVersion, resource, kind, group, namespaced)`：
由 `apiVersion` 推出 `/api/v1` 还是 `/apis/<group>/<version>`，并且**一律 ReadOnly**。
「一律只读」不是偷懒 —— 平台不懂自定义资源的语义，改错一条 Gateway 可能让整个入口断掉。

### Helm：两层 base64 + gzip

Helm 3 把 release 存成 `type=helm.sh/release.v1` 的 Secret，`data.release` 的解码链是
k8s 的 base64 → Helm 自己的 base64 → gzip → JSON。第二层 base64 与 gzip 都不是一定有
（老版本没有），所以实现上是「解不开就当已经是原文」+「按 gzip 魔数判断而不是硬解」。
单测把四种编码组合都试了一遍。

几个刻意的决定：

- **用 `fieldSelector=type=helm.sh/release.v1` 让 API Server 帮我们筛**，不是把全部 Secret
  拉回来过滤 —— 后者在大集群里是几十兆的传输。为此把 `ListQuery.FieldSelector`（本来就在
  k8s 包里、只是 handler 没透出）用上了。
- **同名 release 只留 revision 最大的那个**，但报出一共有几个历史版本。
- **不返回 values 与渲染后的 manifest**：values 里常有数据库口令，manifest 动辄几百 KB。
  列表接口顺手摊出来就是一次数据泄露。
- **只读**。install / upgrade / rollback 需要真正的 Helm 引擎（模板渲染、钩子、依赖、CRD 处理），
  半套实现比没有更危险。

### CRD：发现 + 动态 GVR

`served` 与 `storage` 版本分开给：多版本 CRD 很常见，「能查哪些版本」和「实际存的是哪个」
是两件事，混在一起会让人查错版本。查一个未在服务的版本会被拦下并列出可选项，而不是拼出
一个 404 的路径。

- **`Established≠True` 的 CRD 在查实例之前就拦下**并说明「那是 CRD 没装好」——
  否则表现是一个莫名的 404，很容易被当成权限问题查半天。
- **详情保留 status**（用新加的 `ToFullYAML` 而不是 `ToEditableYAML`）：自定义资源不提供编辑，
  而它们的 status 往往才是要看的那部分 —— Argo 的同步状态、cert-manager 的签发结果。
- 认得的 18 个常见组给一句中文说明（Gateway API / cert-manager / Prometheus Operator /
  Argo / Istio / Flux / Calico / Knative …），**认不出的照样能浏览** —— 不认得不等于不支持。

### Gateway API：折进 CRD 页，但单独解析 HTTPRoute

没有单独做一个 Gateway API 页：装了 Gateway API 之后，它的对象本来就能在自定义资源页浏览。
真正缺的是「这条 HTTPRoute 把什么流量送到哪」—— 那在 YAML 里嵌三层，得来回翻。
所以在 CRD 页加了一个页签专门把 HTTPRoute 拍平。四处照实说明：

- 没有 `matches` 的规则按 Gateway API 的默认语义写成「所有请求（未设匹配条件）」，不留空 ——
  留空会让人以为这条路由没配好。
- 没有后端的规则写成「不会把流量送到任何地方」。
- `path` 没写 `type` 时补成默认的 `PathPrefix`。
- 跨命名空间的后端标出「需 ReferenceGrant」：平台只提示，不代为核对那个 grant 在不在。

集群**没装 Gateway API 时明说没装**并指路去看 Ingress，不给一张空表。

### RBAC：反查，而且必须全集群读

最值得写下来的一条：**即使只看某个命名空间，Role 与 Binding 也一律全集群读**。
命名空间里的 SA 完全可能被一条 ClusterRoleBinding 绑到 `cluster-admin` 上，
只读本命名空间的 binding 会**恰好漏掉最危险的那一类**。

- 为什么一次读齐五类对象而不是按需查：binding 的 `subjects` 不是可选择字段，
  API 层没有「谁绑到了这个 SA」这样的过滤条件，只能全量拉回来在内存里连。
- **孤儿绑定**（绑了但引用的 Role 不存在）单独数出来：那种配置的表现是「绑了却什么权限都没有」，
  很容易被当成权限不够去加一个更大的角色。
- 危险的排最前：`cluster-admin` → 通配符 → 有授权 → 其它。
- 只反查 ServiceAccount。User / Group 主体由集群外的认证系统管，平台里没有对应对象，
  造一个假的出来只会误导。

### 验证

`internal/k8s` 11 条 + `internal/handler` 9 条单测全绿，`go vet` / `vue-tsc` / `vite build` 干净。

**handler 那 9 条是端到端的**：起一个**假 API Server**，把集群 kubeconfig（加密落库）指向它，
再打真实的 HTTP 路由 —— 链路上 gin → handler → 解密 kubeconfig → k8s 客户端 → 解码
每一段都是真的，只有集群那一端是桩。覆盖：Helm Secret 真的被解出 chart/版本/revision 且
**fieldSelector 真的带上了**；CRD 清单认出 Gateway API 版本并数出未就绪的那条；
自定义资源实例按动态 GVR 列出；未就绪 CRD 被拦下且错误信息点名 `Established`；
详情 YAML 里 `status: Synced` 在；HTTPRoute 拍平出 `api-svc:8080`；
命名空间里的 SA 被 ClusterRoleBinding 绑到 cluster-admin 被正确标出。
假 API Server 还对任何未预期的请求路径直接让测试失败 —— 拼错路径不会被静默吞掉。

**没验到的**：真实集群。手上没有可用的 k8s 集群，`internal/k8s` 此前的 port-forward 是在
k3s v1.31 上实测过的，这一轮的三个能力只在桩上验过。Helm 的解码链、CRD 的路径拼装、
RBAC 的反查逻辑都是纯数据处理，桩能覆盖；真集群上最可能出问题的是**权限不够**
（CRD 需要 `apiextensions.k8s.io` 的 list，RBAC 需要 `rbac.authorization.k8s.io` 的 list），
所以这两处的错误信息里都写明了需要什么权限。

### 这一项还剩什么

原计划里的 **节点视图** 与 **Namespace 视图** 这一轮没做。它们比上面三个便宜得多
（`KubeNodes` / `KubeNamespaces` 接口早就有了，缺的是 allocatable / taints / conditions
与命名空间配额这些字段的补全，以及两个页面），但也确实还没做 —— 不算在这一轮里。

### 补完：节点与命名空间（同一轮的后半段）

上面那句写完之后紧接着做掉了，合并进 `/kubernetes/node` 一个页面两个页签
（新增 `internal/k8s/inventory.go` + 7 条单测，handler 侧 +2 条端到端测）。

最重要的一条设计是**与「容量与配额」页划清界线**：那一页回答「还能不能再塞」（已分配 /
limits / 实际用量那本账），这一页回答「这些节点/命名空间自身健康不健康、有没有被什么卡住」。
资源账**只在一处算**——两处各算一遍迟早会对不上，而对不上的数字比没有数字更糟。

几个刻意的决定：

- **conditions 的判断方向是反的**，这是整块最容易写错的地方：`Ready` 应当为 `True`，
  而 `DiskPressure` / `MemoryPressure` / `PIDPressure` / `NetworkUnavailable` 应当为 `False`。
  写错的表现是把健康节点报成异常，或者更糟 —— 把有磁盘压力的节点报成正常。
  单测把八种组合都钉住了。
- **Pod 分布全集群列一次再归组**，不是每个节点/命名空间查一次（N 次请求）。
  已结束（Succeeded / Failed）的 Pod 不计入「这台机器上有多少 Pod」——资源早还回去了。
- **读不到 Pod 列表时 `PodCounted=false`，界面显示「未知」而不是 0**。
  0 会被读成「这台机器上没有 Pod」，那是完全相反的结论。同理，拿不到 Pod 数时
  也不会凭空给出「Pod 数已达上限」这种结论。
- **「既没有 ResourceQuota 也没有 LimitRange」只在真的读到了配额对象之后才判定**。
  没权限看配额和没配配额是两件事，混成一个结论会让人去加一个本来就有的配额。
- **Terminating 时把 finalizer 一起列出来**：命名空间删不掉几乎总是因为有 finalizer 没清，
  光说「卡在 Terminating」等于没说。
- **ResourceQuota 只列 hard 里设了上限的项**：`status.used` 里会带一堆没设上限的零值，
  全列出来是噪音。status 还没算出来时退回 `spec.hard`，至少能看出设了什么上限。
- **容量与可分配分开给**：调度看的是 `allocatable`，两者的差值是预留给系统组件的部分。
- **kubelet 版本偏斜单独提示** —— 升级做到一半停下来是很常见的现场。

**单测抓到的一个真问题**：两处排序原本都是「按问题条数降序」，结果一个卡在 Terminating
的命名空间（1 条问题）被一个「有 Pending Pod + 没配额」的命名空间（2 条问题）压到了后面。
按条数排是本末倒置，改成先按严重程度：节点 `NotReady` 优先、命名空间 `Terminating` 优先，
再按条数。这条是写测试时发现的，不是事后想到的。

**仍然是只读**：不提供 cordon / uncordon / drain / 打污点，也不提供命名空间的创建与删除 ——
前者直接影响调度，后者等于删掉里面的全部对象。


## 已落地：监控告警剩余三块 —— 规则版本、通知模板、值班大屏

参考站这一段还差三页：策略审批、监控大盘、跨渠道通知模板。其中第一项换了做法，理由写在下面。

### 一：不做策略审批，做规则版本 + 字段差异 + 回滚

参考站在改告警策略之前插一个审批节点。这里不做审批，理由与 `docs/SECURITY.md` 第 8 节
一贯的口径一致（内网自用、管理员自己对自己负责），上一轮的「处置审批」也是同样理由没做 ——
加一层点「同意」不会让改动更正确，只会让人绕过它。

但**必须做版本**，而且这一项比审批更要紧：审计日志只记「谁在什么时候 PUT 了哪个接口」，
**不记请求体**。所以在这之前，「谁把这条规则的阈值从 80 改成 200、改之前是什么样」
是查不出来的。而改错一条告警规则的后果是**静默的** —— 之后几周没人知道出了问题。
真正能兜住这件事的是「改动留痕 + 一键回滚」。

做法照搬平台已有的 `ConfigVersion`（存原文快照、只追加不修改），但有两处刻意的差别：

- **不需要 pre-apply 那一版**。配置文件有「机器上的现状」这个第三方，所以那边要在下发前
  专门存一版当回滚点。告警规则的生效态就是数据库里那一行本身，没有第三方 ——
  所以每次变更之后存一版就够，「改之前的样子」天然是上一版。
- **差异做字段级，不用行级 `unifiedDiff`**。两版快照都是 JSON，按行比对的话加一个字段
  就会让后面全部错位显示成「改了」，而且说不出「阈值 80 → 200」这种话。
  字段还带中文标签与人话取值（比较符翻成「大于」、布尔翻成「启用/停用」）。

几个踩点：

- **快照只含配置态**。`HitStreak` / `LastValue` / `LastStatus` / `LastDetail` /
  `LastEvalAt` / `LastFireAt` 这六个是每轮评估都在变的运行态，混进快照会让定时评估
  每 5 分钟「产生一个新版本」。单测专门钉了这一条。
- **内容与上一版相同时不产生新版本**。否则「点了保存但什么都没改」会在历史里留下
  一串一模一样的版本，把真正的改动淹掉。
- **hash 必须稳定**，所以按固定字段顺序序列化而不是直接 `Marshal` map ——
  map 的遍历顺序是随机的。单测跑 20 次断言 hash 不变。
- **版本功能上线前就存在的规则**：第一次改动时先把「改之前的样子」补成第一版，
  否则历史里只有改完的结果，diff 不出改了什么。
- **删除也留一版**（`source=deleted`）。规则是硬删的，这一版快照是「误删恢复」的唯一凭据。
  恢复出来的是一条**新规则**（新 ID）而不是原地复活 —— 旧 ID 上挂过的告警与评估状态
  已经结束了，硬塞回同一个 ID 只会造成更难解释的状态。而且**默认停用**：
  直接让它开始评估等于在没人确认的情况下恢复了一条可能已经不适用的策略。
- 回滚沿用配置文件那两条保障：必须显式指定版本、版本必须属于这条规则。
  回滚本身也记一版，中间那几版不会因为回滚而消失。

**顺手修掉的一个真 bug**：`AlertRule.Enabled` 带 gorm `default:true`，于是
「新建一条停用的规则」或「恢复出一条默认停用的规则」都会被数据库默认值翻回启用 ——
这是 Domain / HostLogTarget 之后的**第三处**同一个坑。单测在恢复那条用例上红了才发现。

### 二：跨渠道通知模板，顺带把变量表收口

改之前：只有邮件能配模板；IM 的文本是 `imAlertText` 硬编码拼串，webhook 的 JSON 是
`alertMessage` 里的字面量。更要紧的是**变量表在四个地方各写一遍**（真实发信的
`alertMailVars`、预览用的 `sampleAlertVars`、内置模板种子里的 `Variables` 提示串、
用户自己手填的 `Variables`），对得上是人工维护的巧合，而且前端拿不到权威清单。

现在 `notifyScenes` 是**唯一的权威定义**，真实变量、样例变量、界面清单、模板校验
全部从它派生，加一个变量只改一处。单测直接断言这三处的 key 集合完全相同 ——
以后谁把它们改歪了会立刻红。

几条设计：

- **模板是可选的覆盖，不是前置条件**。没配、配了但停用、类型对不上、渲染失败 ——
  四种情况全部回落到原来的硬编码格式，而不是发不出去。一条告警发不出去比格式不好看
  严重得多。单测把四种回落都钉住了。
- **变量白名单在保存时就校验**。`text/template` 对 map 的缺失 key 会**静默渲染成空串**，
  不校验的话写错变量名要到真发信时才表现成「正文里少了一段」。错误信息会列出这个场景
  可用的变量。这是相对邮件模板的实质改进（那边只校验语法）。
- **webhook 模板保存时用样例变量试渲染一遍**，结果必须是合法 JSON **对象**。
  运行期仍然可能被变量值里的引号破掉（比如 summary 里有 `"`），那时回落到默认报文
  **并把原因写进投递流水** —— 否则使用者只会发现「模板像是没起作用」，查不到原因。
- webhook 的默认报文形状是对接收端的契约，模板化没有动它。

**顺手修掉的第二个真 bug**：值班呼叫的邮件。`notifyOnCall` 精心拼了标题
「值班呼叫（第 N 级）」与正文「值班表把这条告警派给你 / 已累计 N 次 / 确认后不再升级」，
但那些**只进了站内消息**；邮件走的是 `alertMailVars` + 回落到 `alert.default` 模板，
于是收到的是一封和普通告警一模一样的信，**看不出这是在叫自己**。
现在新增了 `oncall.call` 内置邮件模板与 `oncall` 场景变量
（`scheduleName` / `level` / `assignee` / `alertTitle` …），邮件里能看到是谁在叫、第几级。

### 三：值班大屏

与「告警态势」的分工要先说清：那一页是**运营统计**（按天按源按级别的分布，用来复盘
「这周哪里在响」）；这一页是**当下**（现在有什么没人管、哪条快超时、哪些关键面出问题）。
两者数据源相同但问题不同，所以刻意不互相抄。

- **一屏能看完**。大屏上塞二十个数字等于没有大屏，所以只留「现在要不要动手」这一类，
  趋势只留一条 24 小时的线，SLA 超时/临期的单子最多列 8 条（超时最久的在前）。
- **「被抑制」的告警必须出现在大屏上**。它们仍然在响，只是被静默或聚合抑制、没有外发。
  不显示的话「告警数为 0」会被读成「一切正常」。
- **通知投递失败数放进大屏**是刻意的：告警发不出去是最隐蔽的一种故障 ——
  平台看着在告警，实际没人收到。
- 30 秒自动刷新 + 一键全屏，纯 CSS 柱状图（不为了一条 24 小时趋势引图表库）。
- 只聚合，不产生新数据；没采集的东西（流量、阻断包数）一个数字都没有。

**验证**：新增 19 条单测全绿（规则版本 10 条 + 通知模板 9 条），
全量 `go test` / `go vet` / `vue-tsc` / `vite build` 干净。真后端上跑通了完整链路：
建规则 → 改阈值与级别 → 版本历史 2 版 → 差异如实报「阈值 80 → 200、级别 warning → critical」
→ 回滚（阈值与级别都回去了、连续命中归零）→ 删除留下 `source=deleted` 且 `targetAlive=false`
→ 恢复出新 ID 且**启用=false** → 大屏返回 5 条口径说明；
内置模板种子核对：邮件 `alert.default` + `oncall.call`，IM/webhook 两个内置模板
**默认停用**（启用它们会改变现有渠道发出去的内容形状）。

**仍然没有的**：检测规则与聚合策略的版本化（表已经做成多态的 `target` 字段，
接它们不用改表结构）、大屏的自定义布局与多屏轮播、IM 的 markdown / 卡片消息
（三家富文本语法互不兼容，仍然只发纯文本）、策略审批（上面说了为什么）。
